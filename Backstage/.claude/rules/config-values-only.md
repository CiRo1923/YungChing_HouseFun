# 專案設定檔只改值,不新增項目

**優先順序:第 6 順位。** 低於「無法判斷就一律問」、「動手之前先讀一次規範」、
「規範自己也不能有兩份」、「修問題要治根」、「註解與文件的寫法」,
高於每一條命名與樣式規範。

**規範工具的專案設定檔(`.tools/lint/project-config.mjs`),
每一個專案只做一件事:把裡面既有的項目改成自己專案的值。**

不可以自己新增一項、刪掉一項,也不可以把某一項改名。
項目有哪些、叫什麼名字,由規範工具的來源決定,不由個別專案決定。

## 為什麼

**這支檔案是規則與專案之間的介面。** 一邊是規則(換專案完全不動),
另一邊是這個專案的資料夾怎麼擺。介面的形狀由規則那一側決定 ——
規則讀什麼,這裡就有什麼。

自己多加一項會發生兩件事,而且兩件都不會報錯:

- **沒有任何規則會讀它。** 加上去之後什麼都不會發生 ——
  不是「設定沒生效」的錯誤訊息,是完全的安靜。
  下一個人看到它,會以為某一條規則吃這個值,照著改卻沒有任何反應。
- **來源更新時會對不上。** 規範工具是整套複製過來的,
  之後也會整套更新。自己加的那一項不在新版裡,更新時不是被蓋掉,
  就是變成一段沒有人知道該不該留的差異。

刪掉或改名更直接:規則 import 的名稱不存在,那條規則整條失效,
或是工具在載入時就壞掉。

## 需要一個新的設定項時

**那代表規則本身要改** —— 有一段判準現在寫死在規則裡,而它其實會隨專案不同。
規則與設定是一起改的:規則那一側要 import 它、用它做判斷,
設定這一側才有必要多一項。

所以做法是**停下來說明,不要自己動手加**:

- 是哪一條規則、哪一段判斷,在這個專案上判錯了
- 那段判斷裡的什麼東西會隨專案不同(目錄層數、命名慣例、有沒有做響應式)
- 建議的設定項名稱與預設值

由開發者決定要不要加進來源,加了之後每一個專案都會拿到那一項。

## 來源是哪裡,工具怎麼判斷

**來源是這套規範工具長出來的那個專案。** 設定檔裡的 `SOURCE_PROJECT_NAME`
寫的就是它的名字,工具拿這個名字與這個專案自己的名稱(`PROJECT_NAMES`)比對
—— **對得上就是來源。**

安裝到新專案時,本來就要把 `PROJECT_NAMES` 換成新專案的名字
(不換的話,「不寫死專案名稱」那條會去抓一個與新專案無關的字),
換掉之後兩者自然對不上,那個專案就不是來源了。
來源之後換人時,新的來源把 `SOURCE_PROJECT_NAME` 填成自己的名字,舊的那邊自動退回一般專案。

兩種身分的行為不同:

| 身分 | 設定檔多出沒人讀的項目時 | 為什麼 |
| --- | --- | --- |
| 來源 | 只提醒,不擋 | 規則與設定是一起長的,先加設定、再改規則去讀它,中間必然有一段「還沒有人用」的狀態 |
| 其他專案 | 擋下來 | 那一項在這裡永遠不會有作用,而且來源更新時會對不上 |

全專案檢查時,工具會在開頭講出這次算哪一種身分 ——
不講的話,同一個違規在兩個專案的行為不一樣,而看的人不知道為什麼。

判斷的依據不是「檔案放在哪」,而是**這一項的存在與否由誰決定**:

| 東西 | 誰決定 | 在專案裡可以做什麼 |
| --- | --- | --- |
| 設定項有哪些、叫什麼名字 | 規範工具的來源 | 不能動 |
| 每一項的值 | 這個專案的資料夾怎麼擺 | 照實際情況填 |

判斷方式:**改完之後,別的專案要不要跟著改?** 要,那就是來源的事;
只有這個專案要改,那就是值。

## 只有這個專案需要的規範,放專案自己的規則檔

有些規範只有這個專案需要 —— 別的專案沒有那種寫法,或有但做法不同。
那種東西**不要加進每個專案都拿到的那一套**,放在專案自己的規則檔:
`.tools/lint/rules-project.mjs`。有就讀、沒有就跳過。

這與「設定檔只改值」不衝突,兩者管的是不同的東西:

| 位置 | 放什麼 | 換一個專案 |
| --- | --- | --- |
| 設定檔 `project-config.mjs` | 每個專案都要回答的**同一批問題**的答案(頁面放哪、色票怎麼命名) | 項目一樣,值不一樣 |
| 專案規則檔 `rules-project.mjs` | 只有這個專案要問的問題本身 | 整支不搬過去 |

**代號一律以 `project:` 開頭。** 不加前綴的話,專案自己的規則有一天會與
來源的規則撞名 —— 那時同一個代號底下有兩種判準,而看訊息的人分不出是哪一種。
前綴也讓人一眼看出「這條只有這個專案有」。

**每一條都要有驗證案例**,寫在同一支檔案的 `PROJECT_CASES` 裡(用 `rule` 指定是哪一條)。
規則與案例放在一起,改了規則忘了改案例才不會沒有人發現。
沒有案例的規則會被自我驗證當場擋下來 —— 那一道是整套工具裡最有效的:
規則改壞了、漏了 import、判準寫反了,都是靠案例失敗才被發現的。

**來源整套覆蓋時不會動到這支檔案**(它不在來源裡),所以專案自己的規則不會被蓋掉。
反過來也一樣:這支檔案裡的東西不要複製回來源 —— 那是這個專案的需求,
每個專案都拿到的話,不需要的那幾個會被迫標例外。

## 共用規則只有來源能改

**設定檔與專案規則檔以外的東西,在非來源專案一律不要動。**
規則、檢查引擎、共用工具都是每個專案拿到的同一套;在某個專案改了它,
那個專案的檢查結果就與別人不同,而且改動會在下一次整套更新時被蓋掉 ——
蓋掉的當下沒有人會發現,只知道「本來不報的東西怎麼又開始報了」,
而原因在幾個月前的另一次更新裡。

工具會認出這件事:來源封存了每一支共用規則的指紋,清單跟著規則一起複製過去。
非來源專案的檔案與指紋對不上時,規則 `ruleTampered` 會報出來。

| 要調整什麼 | 改哪裡 |
| --- | --- |
| 某個值(目錄位置、命名慣例、要不要分斷點) | `project-config.mjs` 的既有項目 |
| 只有這個專案要的規範 | `rules-project.mjs`(代號以 `project:` 開頭) |
| 共用規則本身的判準 | **回到來源改**,改完跑 `npm run rules:seal` 重新封存 |

來源那邊不比對 —— 規則本來就在那裡長,每改一行都報一次等於不能工作。
改完規則忘了封存的話,自我驗證會擋下來:那份清單一到別的專案就會全部對不上,
每一支都被報成「被改過」,而那邊其實一個字都沒動。

## 與相鄰規範的界線

「規範自己也不能有兩份」管的是**同一個值不要寫在兩個地方** ——
目錄位置、清單這類東西只留一份來源,其他地方 import 它。

這一份管的是**設定項的清單本身不由專案決定**:值可以照專案改,
項目不可以自己增刪改名。

兩件事在同一支檔案上相遇,但問的問題不同:
前者問「這個值是不是被抄了第二份」,後者問「這一項本來就該存在嗎」。
