# 註解與文件的寫法

**優先順序:第 4 順位。** 低於「無法判斷就一律問」、「規範自己也不能有兩份」、
「修問題要治根」,高於每一條命名與樣式規範。

適用於所有寫出來的文字:程式註解、文件、skills、
commit 訊息以外的一切說明。

這個專案會與客戶共同開發、也會被客戶閱覽。看的人不一定是工程師,
也不一定經歷過這段開發過程。文字要為那樣的讀者寫。

## 一、只寫邏輯,不寫過程

寫**現在的規則是什麼、為什麼這樣設計**;不寫什麼時候改的、誰改的、以前出過什麼問題。

| 不要 | 改成 |
| --- | --- |
| 「2026-08-31 移除了 A 與 B,因為全案沒有使用端」 | 直接不提,或寫「目前不支援 A 與 B」 |
| 「這裡踩過坑,少一道防線就會刪到程式碼」 | 「這裡必須同時滿足三個條件,否則會刪到程式碼」 |
| 「回歸測試:早期版本的判斷式漏了行尾比對」 | 「驗證:結尾不在行尾時不視為空區塊」 |
| 「之前是寫在 A,後來搬到 B」 | 「這段定義在 B」 |

因果要保留,事件要拿掉。「因為出過什麼事」對讀者沒有幫助,
「不這樣做會發生什麼」才有 —— 後者讀者當下就能判斷,前者只是舊聞。

**歷程有它該放的地方,只是不在程式碼旁邊。**

| 想知道什麼 | 去哪裡看 |
| --- | --- |
| 現在是什麼樣子、為什麼這樣設計 | 程式註解與規範文件(也就是這條規則管的地方) |
| 這個功能後來怎麼調整的、為什麼決定那樣做 | 專案文件 `docs/` |
| 哪一次動了哪幾行、誰改的、什麼時候 | 版本控制(git) |

三個地方各司其職。混在一起的後果是:註解愈寫愈長,
而讀的人要從一堆「以前怎樣」裡面撈出「現在怎樣」——
偏偏他打開這個檔案就是為了知道現在怎樣。

程式註解與規範文件只講現況;需要交代來龍去脈時寫進專案文件,
那裡是為了記錄而存在的,篇幅也放得下。

**例外:標示資料有效期限的日期要留。** 對照表、清單這類文件會隨著程式碼變動,
「這份是哪一天比對的」是讀者判斷「還能不能信」的依據,不是開發過程的紀錄。
例如路由對照表開頭的「比對日期」就要保留。

分辨方式:那個日期是在講**文件內容的有效範圍**(留),
還是在講**某次改動什麼時候發生**(拿掉)。

### 程式與頁面內容:只說明邏輯,不贅述

程式註解與頁面裡寫給人看的文字,同樣只講邏輯,而且**話要少**。
每多一句沒有作用的話,真正要緊的那句就被稀釋一次。

這些都是贅述,一律不寫:

| 贅述 | 為什麼不要 |
| --- | --- |
| 把程式碼原樣翻成中文(`// 把 status 設成 200`) | 讀程式碼就看得到,重複一次沒有增加任何資訊 |
| 「這裡先做 A,再做 B,最後做 C」的流程複述 | 照著讀一遍程式碼的順序,不如直接讀程式碼 |
| 「暫時這樣寫」「之後再優化」「先這樣」 | 沒有說明暫時到什麼時候、之後要怎麼改,等於沒寫 |
| 「很重要」「特別注意」沒有下文 | 只說了語氣,沒說內容 |
| 被註解掉的舊程式碼 | 那是死程式碼,版本控制裡找得回來 |

要寫的是程式碼**看不出來**的那一部分:

- 為什麼選這個做法,而不是另一個看起來更直覺的
- 這段有什麼前提,不滿足的話會發生什麼
- 哪些值是刻意的,改掉會壞在哪裡

一句話能講完就不要寫三句。

## 二、讀者不必離開現在這一段

**原則是:讀到任何一個區塊,不用跳頁、不用往回捲、不用開另一個檔案,
就能知道這一段在講什麼。**

所以「同上」「同 1」「同前述」「見上一節」「同理」這類寫法不行 ——
它們把資訊留在別的地方,強迫讀者跳走。讀者多半是從搜尋結果、
從某個檔案的中段、從一份文件的第三節開始看的,沒有「上一段」可以參照;
跨檔案的指涉(「規則同 api 那份」)更是直接斷掉。

**內容重複完全沒問題,重複遠比指涉好。** 同一句話在三個地方各寫一次,
讀者三次都讀得懂;寫成「同上」則是三個地方都讀不懂。

### 可以重複的是說明,不是判準

這條講的是**說明文字**:同一個規則的解釋、同一段背景、同一個例子,
在需要的地方各寫一次,讀者才不必跳頁。

**判準與設定值只能有一份。** 判準是「怎樣算違規」的那個判斷本身,
設定值是目錄位置、副檔名清單、名稱清單這類資料。
這兩種東西寫成兩份,不是讓讀者方便,是讓兩份開始各自演化 ——
改了一處忘了另一處,規則就靜靜失效,或者兩份互相矛盾。

| 東西 | 重複 | 為什麼 |
| --- | --- | --- |
| 規則的解釋、背景、例子 | 可以,而且鼓勵 | 讀者從任何一段讀起都要能懂 |
| 「怎樣算違規」的判斷邏輯 | 不行,只能一份 | 兩份會有一天對不上,修好一邊另一邊還在報 |
| 目錄位置、清單、檔名這類設定值 | 不行,只能一份 | 改一處忘了另一處,規則不會報錯,只是不再檢查任何東西 |

判斷方式:**改動的時候要不要兩處一起改?** 要,就是判準或設定值,收成一份;
不用,那就是說明文字,重複無妨。

| 不要 | 改成 |
| --- | --- |
| `/* lint-exempt: 同上,日曆浮層 */` | `/* lint-exempt: 日曆是元件自己排版的浮層,使用端沒有管道可傳 */` |
| 「命名規則同第 3 點」 | 把第 3 點的規則在這裡再寫一次 |
| 「錯誤處理見 api 那份文件」 | 先寫清楚這裡要怎麼處理,需要更多細節時再指路 |

**指路可以,但不能代替說明。** 「完整清單見 X」是有用的補充,
前提是這一段自己要講的已經講完了 —— 讀者不去看 X 也不會漏掉重點。

### 同一件事出現在很多地方時

一份規則、一個欄位、一個流程,常常會在好幾個地方被提到。
那時**挑一個地方寫完整,其餘的地方各自寫一段短的**,
而不是在其餘的地方寫「同上」把讀者送回去。

| 位置 | 怎麼寫 |
| --- | --- |
| 主要說明的那一處 | 完整寫:是什麼、為什麼這樣設計、怎麼做、不這樣做會發生什麼 |
| 其他提到它的地方 | 一兩句講清楚「這裡在做什麼、要注意什麼」,不必重述全部理由 |

判準是:**其他地方那一段,讀者不去看主要說明也要能照著做。**
短可以,但不能只剩一個指標。

讀文件的人多半是帶著一個具體問題來的,從搜尋結果或某一節的中間開始看。
被送去另一個地方之後,還要自己找回原本在看什麼 —— 跳兩次就放棄了。

## 三、讓非工程師讀得懂

這個專案會與客戶共同開發、也會被客戶閱覽。看的人不一定寫程式。

- 專有名詞第一次出現時用一句話說明它是什麼,再繼續往下寫
- 說明「這是做什麼的」而不只是「這行程式在幹嘛」
- 避免只有團隊內部聽得懂的簡稱與玩笑
- 例子比抽象描述有效 —— 給一段輸入與對應的結果
- 一句話講一件事。條件很多時拆成幾行或做成表格,不要堆成一長句

## 四、用詞

- 中性、平實。不寫情緒性的描述(「很雷」「爛掉」「炸了」)
- 不評論人,只描述程式碼與規則
- 不用誇張語氣強調重點,需要強調就把理由寫清楚
- 繁體中文(台灣用語);程式碼、識別字、檔名、指令、套件名稱保持原文

### 不用 emoji 與裝飾符號

**寫給人讀的文字裡不放 emoji,也不放拿來裝飾的符號。**
客戶會看到這些文字,那是正式的工作文件,不是聊天訊息。

要強調就把理由寫出來,那比一個圖示有用 ——
圖示只說「這裡很重要」,理由才說得出「為什麼重要、不照做會怎樣」。

| 不要 | 改成 |
| --- | --- |
| `⚠️ 這裡必須同時滿足三個條件` | `注意:這裡必須同時滿足三個條件` |
| `✅ 正確的寫法` / `❌ 錯誤的寫法` | `正確的寫法:` / `錯誤的寫法:` |
| `🔧 已自動排序` | `已自動排序` |
| `👉 看這裡` | 直接寫要說的事,或用粗體 |

**兩種情況不算裝飾,可以留:**

一、**工具在終端機印出來的狀態**(通過用 `✔`、違規用 `✗`)。
那不是文件,是程式跑起來當下的回饋;一排訊息裡要能一眼分出哪幾筆有問題。

二、**對照表裡表示「變成」的箭頭**(`舊名稱 → 新名稱`)。
那是資訊本身,不是裝飾 —— 換成文字反而讓整欄對不齊、更難讀。

檢查:規則 `plainText`(擋)。

## 五、不寫專案名稱

**規範系統自己的檔案裡不出現專案名稱** —— skills、hooks、檢查工具、規則、
驗證,以及規範自己的說明文件(`.claude/docs/`)。

這些檔案會整批複製到下一個專案。名稱寫進去之後,搬過去就變成錯的敘述,
而且從內容看不出哪幾句是「本專案限定」。要指稱這個專案時就寫「本專案」。

網域、路徑、識別字一律走環境變數或設定檔,不寫在規範系統的檔案裡。

**原始碼不在這條的範圍內。** 頁面標題、頁尾品牌名、會員條款裡的品牌名稱
是內容本身,不是被寫死的設定 —— 那些檔案不會複製到別的專案,寫出品牌名是正確的。
專案自己的文件(專案根的 `docs/`)同理,那是寫給這個專案的內容。

範圍之內仍有一種例外:用來記錄**實際服務位置**的清單(網址對照表那類),
那裡的網址是要記錄的資料本身。這種檔案在檔頭標
`lint-project-name-exempt` 並寫明理由,規則就會跳過整份。

檢查:規則 `projectName`(擋)。

## 六、不寫絕對路徑

**任何地方都不寫某一台電腦上的路徑** —— 註解、文件、錯誤訊息、指令範例都算。

| 不要 | 改成 |
| --- | --- |
| 磁碟機代號開頭的路徑 | `src/components/mForm/Input.vue` |
| 家目錄開頭的路徑 | `.tools/lint/lint.mjs` |
| `file://` 開頭的位址 | `.claude/docs/待辦事項.md` |

每個人的專案擺在不同位置,作業系統也不一定一樣(有人用 Windows 的磁碟機代號、
有人用 macOS 的家目錄)。寫死之後,照著文件操作的人會找不到檔案,
而且看不出正確的位置該是哪裡。**一律寫相對專案根目錄的路徑。**

例外是「為了定義規則而必須寫出路徑形狀」的檔案(規則本身、測試案例):
在檔頭標 `lint-absolute-path-exempt` 並寫明理由。

檢查:規則 `absolutePath`(擋)。

## 適用範圍

上面這幾節都是**寫的時候要守的原則**,適用於所有寫出來的文字:
程式註解、頁面上給人看的內容、skills、hooks、檢查工具、說明文件。

其中三條有工具在擋,而三條的範圍不一樣,不要混在一起記:

| 規則 | 範圍 | 為什麼是這個範圍 |
| --- | --- | --- |
| **不用 emoji 與裝飾符號**(`plainText`) | 原始碼與規範系統 | 這兩處的文字客戶都會看到:畫面上的文案、交接時對方讀的註解 |
| **不寫「同上」那類寫法**(`selfContained`) | 原始碼與規範系統 | 讀的人從哪一段開始看都要能懂 |
| **不寫絕對路徑**(`absolutePath`) | 原始碼與規範系統 | 絕對路徑只在某一台機器上成立,寫在哪裡都會讓別人 clone 下來就壞掉 |
| **不寫專案名稱**(`projectName`) | 只管規範系統自身 | 只有這些檔案會整批複製到下一個專案。頁面文案裡的品牌名是內容,不是設定 |

四條都不碰專案自己的文件(專案根的 `docs/`)—— 那一層有自己的檢查工具,
詳見下一節。

實際的目錄清單定義在 `.tools/lint/project-config.mjs`,
規則自己讀的是同一份設定 —— 每個專案的資料夾擺法不一樣,這裡不另外寫死一份。

### 專案自己的文件

專案根的 `docs/` 放的是寫給這個專案的內容:規格、對照表、會議紀錄、
改動的來龍去脈。那是交付給客戶的成品,也是最多人讀的一份。

**上面這幾節的原則,寫那一層的時候一樣要照著做。**
不用 emoji 與裝飾符號、不用「同上」把讀者送去別處、只寫邏輯不寫贅述、
讓非工程師讀得懂 —— 那是給客戶看的文件,這些事在那裡只會更重要。

**但檢查那一層的工具不是這一套。** 文件有自己的檢查機制
(連結有效、側欄一致、排版慣例那些),`.tools/lint/` 完全不碰 `docs/`。

兩套工具掃同一層的話,判準會各自演化:同一份文件被兩邊報不同的東西,
修好一邊另一邊還在報,最後兩邊都被忽略。文件的事歸文件的工具管。

不必守的只有兩條:**不寫專案名稱**與**不寫絕對路徑**。
那一層本來就要寫出這個專案叫什麼、檔案實際放在哪 —— 那是要記錄的資料本身。
