# ⛔ 不要自己發明 —— 結構與邏輯一律沿用現有的

本規則每次對話都必須遵守,**優先於任何「這樣寫比較好」的判斷**。

## 兩條硬規則

| # | 規則 | 判斷不出來時 |
|---|---|---|
| 1 | **不要自己判斷新增結構** —— 元件、資料夾層級、props 形狀、檔案切分 | **停下來問** |
| 2 | **不要新增邏輯** —— 一律用現有結構處理 | **停下來問** |

兩條的例外只有一個:**使用者明確要求的那件事本身**。
「為了做到他要求的事,我順手多做了 X」——**X 就是違規**。

## 什麼算「自己發明」

這幾種都實際發生過,而且當下都覺得「很合理」:

| 類型 | 實例 |
|---|---|
| **從規格推導出使用者看得到的文案** | API 規格寫「手機每日上限 2 次」→ 就在畫面上寫「每天只能使用 2 次」。規格是後端的限制,**不等於設計稿要顯示它** |
| **自己決定互動行為** | 「手機格式不對就停用發送按鈕」—— 既有做法是**按鈕永遠可按、按下去才驗證**,錯誤顯示在欄位上 |
| **自己抽常數、自己寫正則** | 抽一個 `PASSWORD_RE` 常數,而既有的同類欄位是**正則內聯**在 rules 裡、錯誤訊息用 `{ minlength }` 插值 |
| **自己補設計稿沒說的東西** | 提示行、預設值、限制說明、空狀態文案 |
| **自己開新結構** | 新元件、新資料夾、新的 props / config 形狀,而既有已經有可用的板 |
| **自己選了一種寫法** | 既有有兩種做法,自己挑了「看起來比較好的」那個 |

## 動手前的三步

1. **grep 既有的同類頁面 / 元件**怎麼做 —— 同一個欄位、同一種提示、同一個流程步驟
2. **找到了 → 照抄那個板**。連**文案、錯誤訊息、config 欄位名、正則寫法**都照抄,
   不要「順手改好一點」。既有板的不一致由使用者決定要不要收斂,不是你
3. **找不到,或找到兩種以上做法 → 停下來問**。列出你找到什麼、差異在哪、
   你會怎麼選,讓使用者決定

## 為什麼

**代價不對稱。**

自己發明一個結構或邏輯,當下省下一次提問;但它會:

- 讓同一件事在專案裡有兩種做法,下一個人不知道該跟哪個
- 把「設計沒決定的事」變成既成事實,而且**看起來像已經確認過的**
- 出錯時很難發現 —— 它不會報錯,只是行為與別的頁面不一樣
- 要收回來時得改元件、改 template、改每一個使用端

而問一句的成本只有一次往返。

## 問的方式

直接說「這個我判斷不出來」,把選項與各自的後果列出來。

**不要**假裝有把握然後埋一句「暫時這樣」或「之後可以調整」——
那等於把自己的猜測寫進程式碼,而且沒有人會回頭看那句註解。
