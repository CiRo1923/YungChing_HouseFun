# 規範自己也不能有兩份

**優先順序:第 3 順位。** 低於「無法判斷就一律問」與「動手之前先讀一次規範」,
高於「修問題要治根」、「註解與文件的寫法」,以及每一條命名與樣式規範。

高於「修問題要治根」的理由:治根的做法如果會讓同一件事變成兩份,
那個「治根」本身就製造了新的問題 —— 先確認不會重複,再談怎麼治根。

**新增或修改任何 skills、hooks、工具、規則、檢查、驗證之前,
先把現有的全部看過一遍,確認沒有另一處在講同一件事。**

**這件事每一次都要做,沒有「這次改得很小所以跳過」。**
規則衝突不是一次大改造成的,是很多次小改累積出來的 ——
每一次都覺得只動一行不必全部看過,於是每一次都沒看,
直到兩份規則開始互相矛盾,而沒有人記得是哪一次開始的。

改動範圍再小也要完整走一遍下面「新增之前要做的事」與
「全面檢查怎麼做」兩節,並在改完後把檢查結果說出來 ——
包含「這次確認過哪些地方、有沒有找到相近的規則」。

發現兩處講同一件事、但說法對不上時,**不要自己決定哪一份才對** ——
那是在揣測原本的意圖。把兩份的差異列出來問開發者。

規範系統會長大。每加一條的當下都覺得是新的,但半年後回頭看,
同一件事常常已經被寫在三個地方 —— 而且三份的措辭略有出入。
那時沒有人知道哪一份才算數,通常的結果是三份都被忽略。

## 這條管的是判準與設定值,不是說明文字

**說明文字重複沒有關係,而且是被鼓勵的** —— 同一個規則的解釋、同一段背景、
同一個例子,在需要的地方各寫一次,讀者從任何一段讀起都能懂,不必跳頁。

**這條規則管的是另外兩種東西:**

- **判準** —— 「怎樣算違規」的那個判斷本身
- **設定值** —— 目錄位置、副檔名清單、名稱清單這類資料

這兩種只能有一份。寫成兩份不是讓讀者方便,是讓兩份開始各自演化:
改了一處忘了另一處,規則就靜靜失效,或者兩份互相矛盾,兩邊都過不了。

| 東西 | 重複 | 為什麼 |
| --- | --- | --- |
| 規則的解釋、背景、例子 | 可以,而且鼓勵 | 讀者從任何一段讀起都要能懂 |
| 「怎樣算違規」的判斷邏輯 | 不行,只能一份 | 兩份會有一天對不上,修好一邊另一邊還在報 |
| 目錄位置、清單、檔名這類設定值 | 不行,只能一份 | 改一處忘了另一處,規則不會報錯,只是不再檢查任何東西 |

判斷方式:**改動的時候要不要兩處一起改?** 要,就是判準或設定值,收成一份;
不用,那就是說明文字,重複無妨。

## 兩份會出什麼事

| 狀況 | 後果 |
| --- | --- |
| 兩份規則說法不一致 | 照 A 改會違反 B,照 B 改會違反 A,兩邊都過不了 |
| 同一個設定值寫在兩處 | 改了一處忘了另一處,規則靜靜失效 —— 不會報錯,只是不再檢查任何東西 |
| 同一條規則實作兩次 | 修好一邊的誤報,另一邊還在報 |
| 說明文件與檢查工具各寫一份判準 | 文件說可以、工具說不行,寫的人只好照工具改,文件就沒人維護了 |

## 新增之前先判斷這條屬於哪一類

**動手寫任何一條新規範之前,第一件事是先說出它屬於哪一類。**
分類決定了「該去哪一份既有的檔案找有沒有人在講同一件事」——
不先分類就搜尋,等於用幾個關鍵字碰運氣,碰不到就以為沒有,於是又開一份新的。

本專案目前的分類與各自的位置:

| 分類 | 管的是什麼 | 規範寫在哪 |
| --- | --- | --- |
| **css** | 樣式檔自己怎麼寫:色票命名、模組變數、模組的 class 範圍 | `.claude/skills/` 的 color-naming、css-module-variables |
| **component** | 共用元件的檔案形狀:載入了什麼、開頭那幾行怎麼排 | `.claude/skills/component-conventions` |
| **頁面** | 頁面怎麼取資料、怎麼包裝 api 呼叫、元件與資料的關係 | `.claude/skills/page-conventions` |
| **stores** | store 與 actions 自己怎麼寫、分層、宣告順序 | `.claude/skills/` 的 store-conventions、composable-order |
| **api** | api 檔案與函式的命名、端點怎麼對應 | `.claude/skills/api-conventions` |
| **js** | 不分檔案類別的程式寫法,例如 import 路徑 | `.claude/skills/import-alias` |
| **一般** | 工作方式本身:怎麼判斷、怎麼修、文字怎麼寫。不限某一類檔案 | `.claude/rules/`(這一層) |

判斷方式:**這條規則看的是哪一種檔案?** 只看 `.css` 就是 css 類,
只看共用元件目錄底下的 `.vue` 就是 component 類,哪一種檔案都適用、
講的是做事的方式,那就是「一般」類,寫進 `.claude/rules/`。

**分不出屬於哪一類、或同時像兩類時,停下來問**,不要挑一個看起來比較接近的放進去。
放錯類別的規則不會報錯,只是以後沒有人會在那裡找到它 ——
下一個人遇到同一件事,會在他以為正確的那一類再寫一份。

分完類之後才做下面那幾件事。

## 新增之前要做的事

1. **先說出這條屬於哪一類**(css / component / 頁面 / stores / api / js / 一般),
   決定要去哪一份既有的檔案找
2. **搜尋關鍵字**,確認沒有現成的規則在管同一件事
3. 找到相近的就**擴充那一份**,不要另開新的
4. 真的要獨立成新的一份時,在兩邊都寫清楚**各自負責什麼、界線在哪**
5. 同一個值(目錄位置、檔名、清單)只留**一份來源**,其他地方 import 它

## 界線要寫清楚

規則之間有相鄰的地帶,那不算重複,但要講明白誰管什麼。
不要留給讀者自己猜,也不要兩份都含糊帶過。

寫法是在各自的檔案裡說明自己的範圍,例如
「這支管 store 與 actions 自己怎麼寫」與「這支管頁面怎麼使用它們」——
兩句話擺在一起,界線就清楚了。

## 修改之前也一樣

改一條規則的判準或訊息時,先確認**沒有第二處在做同樣的判斷**。
只改一邊的話,兩邊就開始不一致,而不一致的那天不會有人通知你。

## 全面檢查怎麼做

每一次動到規範系統都跑這六項。範圍是規範所在的全部位置:
規則檔、skills、hooks、檢查工具、驗證,以及說明文件。

| 檢查 | 要確認的事 |
| --- | --- |
| **一份判準** | 同一條規則沒有被實作兩次(工具一份、hook 又一份)。判斷邏輯只寫在檢查引擎裡,其他層呼叫它。 |
| **一份設定** | 同一個值(目錄位置、副檔名清單、候選檔名)只有一處定義,其他地方 import。無法 import 的位置(編輯器設定、commit 用的指令稿)要寫註解指回來源。 |
| **文件與工具一致** | 說明文件寫的判準,與工具實際檢查的內容相同。文件說可以、工具說不行,寫的人只能照工具改,文件就沒人維護了。 |
| **優先順序不打架** | 每一份規則都寫了自己的優先順序,而且彼此對得上。兩份都自稱「最高」就是矛盾。 |
| **不寫死專案細節** | 規則、工具與說明裡不出現專案名稱、絕對路徑,也不出現只有這個專案才有的資料夾路徑 —— 那些會隨專案而不同,寫死之後換一個專案就是錯的敘述。 |
| **前提缺了會說出來** | 規則依賴的東西(目錄、設定檔)不存在時,要明講「這幾條這次沒有作用」,不能安靜地顯示通過。 |

檢查完把結果寫出來:**確認了哪些位置、有沒有找到相近的規則、
有沒有發現對不上的地方**。沒有發現問題也要說,那本身就是結論。

**檢查出「某條規則講得不夠、範圍要擴大、說法要修」時,一律去改那一份既有的,
不要為了同一件事再開一份新的。** 規則檔如此,檢查工具與說明文件也一樣:
同一個判斷已經有實作了就去改它,不要在另一層再寫一次;
同一件事已經有段落在說明了就改那一段,不要在別處再寫一段講法略有出入的。
既有的說法與現在要的相反時,不要自己決定哪份才對,把差異列出來問開發者。
