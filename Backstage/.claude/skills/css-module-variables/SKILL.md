# CSS 模組變數分層:值進 Variables、樣式留模組

模組樣式放在兩種位置,規則兩邊都管:

| 位置 | 放什麼 |
| --- | --- |
| 元件資料夾底下的樣式子資料夾(名稱見 `MODULE_CSS_DIR_NAME`) | 那一支元件自己的樣式與變數 |
| 集中目錄(`CSS_MODULES_DIR`) | 兩個以上元件都要用的共用變數 |

**界線是問「這支屬於哪一個元件」** —— 答得出來就放那個元件的資料夾,
答不出來(兩個以上在用)才放集中目錄。放進其中一個元件的資料夾的話,
另一個元件就得去 import 別人的檔案,而刪掉那個元件時會連帶弄壞它。

集中目錄底下也先分一層類的時候,要答的仍然是「哪一個元件」,
不是那一層分類 —— 分類底下有好幾支元件,答成分類的話,
那幾支的樣式會全部搬進同一個資料夾,誰的樣式是誰的就看不出來了。

兩種位置底下的每個模組,都成對存在兩種檔案:

| 檔案 | 放什麼 |
| --- | --- |
| `***Variables.css` | `:root` 的**原始值** + **級距覆寫 class**(同一屬性有多個可選值者) |
| `***.css`(模組樣式) | **樣式規則**(顏色、圓角、排版)+ **斷點變數對應**(`--x: var(--x-pc)`) |

**`***` 是變體名,不是模組名。** 一個模組底下有好幾支元件時才會用到它
(`mForm/.css/selectionVariables.css` —— `selection` 是那個變體)。

**模組底下沒有變體(只有一支 `Index.vue`)時,檔名就是 `variables.css`。**
照字面把模組名填進去會變成 `mStepCard/.css/mStepCardVariables.css`,
資料夾名重複了一次 —— 那不對,而且不會報錯,所以每個單一元件的模組
都會各自猜一次。

判準是**「這個屬性有幾個可選值」**:

- **兩個以上** → 是一組級距,覆寫 class 必須寫在 `***Variables.css`。
- **只有一個固定值** → 直接寫在模組 css 即可,不需要抽出來。

## 一、先決定這個值由誰定:元件自己,還是使用端

放進哪一支檔案之前,要先回答更前面的一個問題:**這個值是元件自己說了算,
還是每個用它的地方各自決定?** 字級最容易判斷錯 —— 它看起來像元件外觀的一部分,
所以常常被直接寫死在元件的樣式裡。

判準是**這支元件在整個網站上有幾種樣貌**:

| 這支元件 | 字級這類值怎麼處理 | 為什麼 |
| --- | --- | --- |
| 全站只有一種樣貌的固定模組(導覽列、頁首、頁尾、麵包屑) | 寫在元件自己的樣式裡;要分斷點就定義成 css 變數 | 只有一個地方在用,值集中在元件裡最好找 |
| 到處都會用到的通用元件(錨點、頁籤、表格、表單、日期選擇器) | 不寫死,留給使用端傳入 | 同一支元件在不同頁面本來就該長得不一樣 |

**分辨方式:問「第二個地方用它的時候,這個值會不會不一樣?」**
會不一樣就留給使用端;整個網站都只有這一個地方在用,就寫在元件裡。

**上面那一欄講的是元件「對外的主字級」** —— 使用端看得到、會想調整的那一個。
元件**內部結構**的字級不在此列:日曆面板的標頭與星期列、表格的欄位標題、
分頁器的頁碼,那些是元件自己的版面,仍然由元件定義成變數。

分辨方式:**使用端會想逐一指定它嗎?** 會的是對外的字級,留給使用端;
不會的是內部結構,元件自己決定。把內部結構也開放出去的話,
使用端每放一次這支元件就要傳一堆值,而每次傳的都一樣。

兩邊做錯的代價不一樣,但都不會報錯:

- **通用元件把字級寫死了**,第二個使用端要不同字級時只剩兩條路 ——
  加一個開關(`isSmall` 這種),或在使用端用更強的選擇器蓋掉它。
  兩種都是在現有結構上再疊一層,而元件的外觀從此要看兩個地方才知道。
- **固定模組把字級開放給使用端傳**,那是多做的:只有一個使用端,
  於是每次都要傳同一組值;漏傳的那次沒有預設可用,畫面上是字突然變小。

**「定義成 css 變數」不等於「開放給使用端覆寫」。** 固定模組把字級寫成變數,
用意是三個斷點的值集中在同一處、改的時候不必翻遍整支樣式 ——
那仍然是元件自己的值,使用端不會去傳它。要開放給使用端覆寫的,
是下面幾節講的級距覆寫 class。

### 截行數(line-clamp)走同一組判準

**文字要截成幾行,與字級是同一類的值:它由版面決定,不由元件決定。**
同一張卡片放在列表裡通常只留一行,放在詳情頁可以給兩三行 ——
問「第二個地方用它的時候,這個值會不會不一樣?」答案是會,
所以通用元件不把行數寫死,留給使用端指定。

開放的方式與級距一樣:在 `***Variables.css` 定義一組覆寫 class
(`--line-1` 到 `--line-5`),元件收一個數字的 prop,用查表把它對到那組 class。

```js
// class 必須是字面值,Tailwind 才掃得到 —— 用字串拼接(`--line-${n}`)產不出樣式
const LINE_CLAMP = {
  1: '--line-1',
  2: '--line-2',
  3: '--line-3',
}
```

```css
/* ***Variables.css —— 行數是同一屬性的多個可選值,所以是一組級距 */
.m-card {
  &.\-\-photo {
    .m-card-name {
      &.\-\-line-1 {
        @apply line-clamp-1;
      }

      &.\-\-line-2 {
        @apply line-clamp-2;
      }
    }
  }
}
```

寫死行數的代價與寫死字級一樣:第二個使用端要不同行數時,只剩下加一個開關、
或在使用端用更強的選擇器蓋掉它兩條路,而元件的外觀從此要看兩個地方才知道。

**單行省略不要用 tailwind 的 `truncate`。** 它做的是「不換行 + 超出顯示省略號」,
只能一行;要改成兩行時它幫不上忙,得整句換成 `line-clamp-2` ——
也就是換一個行數就換一種寫法。`line-clamp-1` 做的是同一件事,
而且與 `line-clamp-2`、`line-clamp-3` 是同一組,改行數只動數字。

檢查:規則 `truncateClass`(建議級,不擋)。看樣式檔 `@apply` 後面的清單,
以及畫面區段裡的 class;`:class` 動態綁定裡的變數名不算 ——
行數正是靠一個叫 `truncate` 的 prop 傳進來的。

**元件內部結構的截行不在此列** —— 元件自己排的浮層、標籤、提示文字要截幾行,
使用端不會想逐一指定,那是元件自己的版面。分辨方式與字級相同:
使用端會不會想逐一指定它。

這條沒有工具在檢查:規則看得到樣式寫在哪一支檔案,看不出這支元件以後
會在幾個地方被用、各自要不要不同的字級或行數。**判斷不出來就問**,
不要挑一個看起來合理的往下做。

### 字級不吃斷點的豁免標記

尺寸值沒分斷點時可以標 `lint-breakpoint-exempt` 放行,**但字級不行**
(名字以 `-text-size` 結尾的那些)。

理由是上面那兩種字級**都不需要那個標記**:

- **固定模組**的字級寫在元件裡,而規範要求它分斷點定義成變數 ——
  照著做就通過了,不必標
- **通用元件**的字級本來就不該寫在元件裡,要留給使用端傳 ——
  標記只是把問題蓋住

放行的話,那個標記會讓「還沒決定這個值由誰定」看起來像「決定過了」,
而它蓋掉的正是唯一會提醒人去想這件事的那一筆。

### 豁免標記的名字要真的有規則在讀

規則 `unknownExemptMark`(擋)。`lint-xxx-exempt` 的名字打錯、
或那條規則後來被拿掉時,那一行**不會放行任何東西**,
讀起來卻像「這裡已經想過了」—— 而它蓋住的正是會提醒人去想的那一筆。

實際發生過:有 8 處寫著一個從來不存在的標記名,
而它宣稱豁免的那件事正好是規範明文要擋的。看的人以為那裡決定過了,
所以沒有人再去想那個值該由誰定,直到有人問起才發現。

合法的名字不另外維護清單 —— 規則直接從自己的程式碼裡看
「哪些名字真的有人在讀」。所以標記名打錯會當場被擋下來,
而一條規則被拿掉時,原本標著它的那幾行也會一起被報出來。

**豁免是一行一個。** 標在檔頭不會讓整支檔案都不檢查:

```css
:root {
  /* 這一行放行 */
  --popup-tools-pc-mx: 24px; /* lint-breakpoint-exempt: 手機改用 mt */
  /* 這一行照常檢查 */
  --popup-body-px: 8px;
}
```

整支放行的話,一個合理的例外會讓其餘幾十個變數安靜地失去檢查,
而寫標記的人以為自己只豁免了那一行。

## 二、作用域:依實際共用範圍決定

跟色票的分層邏輯一致 —— **共用的放共用檔,專屬的放專屬檔**:

- **跨模組共用** → 共用變數檔(位置定義在 `.tools/lint/project-config.mjs` 的
  `SHARED_MODULE_VARIABLES`,規則的提示訊息會直接寫出實際檔名)。
  例:`--form-element-px`(`--px-20` / `--px-15` / `--px-10`)、`--form-element-h`、
  `--form-element-rounded`,input / select / textarea 都吃同一組。
- **模組專屬** → 該模組的 `***Variables.css`。
  例:`--form-selection-icon-size` 只有勾選框與單選的那個圖示用得到,
  輸入框與下拉沒有那個圖示,所以定義在 `selectionVariables.css`,不放共用檔。

判斷方式:先看這組級距是否真的會被其他模組使用。**只有一個模組用就放模組專屬**,
不要為了「以後可能會用」提前放進共用檔。

規則 `sharedVarScope`(擋)。它掃全案的模組樣式,看每一個共用變數實際被幾個模組引用;
只有一個在用的要搬回那個模組自己的 Variables 檔,訊息會指出是哪一個模組。

留在共用檔的代價:改那個值要開兩支檔案,而那個元件被刪掉的時候,
共用檔裡這一段不會有人想到要清 —— 它看起來就跟其他真的共用的那幾組一樣。

**一個使用者都沒有的不報** —— 那是另一件事,而且剛加上去、還沒接上使用端的那一刻
也長這樣,報它只會擋住正在做的事。

## 三、寫法

```css
/* selectionVariables.css —— 原始值 + 級距覆寫 */
:root {
  --form-selection-icon-pc-size: 18px;
  --form-selection-icon-tablet-size: 18px;
  --form-selection-icon-mobile-size: 18px;
}

/* modifier 只設變數,套用寫在 selection.css —— 變數檔不放版型宣告 */
@screen p {
  .m-form {
    &.\-\-icon-size-25,
    &.p\:\-\-icon-size-25,
    &.pt\:\-\-icon-size-25 {
      --form-selection-icon-size: 25px;
    }

    &.\-\-icon-size-20,
    &.p\:\-\-icon-size-20,
    &.pt\:\-\-icon-size-20 {
      --form-selection-icon-size: 20px;
    }
  }
}
```

```css
/* selection.css —— 樣式 + 斷點對應 */
.m-form-icon {
  @apply h-[--form-selection-icon-size] w-[--form-selection-icon-size] shrink-0;
}

@screen p {
  .m-form {
    --form-selection-icon-size: var(--form-selection-icon-pc-size);
  }
}
```

### 版型檔讀的每一個變數,`:root` 都要有 base

**版型檔讀它,而它只在「可選的 class」底下被指派 —— 那就要在 `:root` 補一個 base。**

```css
/* 變數檔 */
:root {
  --anchor-h: auto; /* ← base:沒掛 --h-XX 時的樣子 */
}

@screen p {
  .m-anchor {
    &.\-\-h-40 {
      --anchor-h: 40px; /* ← 掛了才有 */
    }
  }
}
```

沒有 base 的話,沒掛那個 class 的元素讀到的是**未定義的變數**,
瀏覽器會把整條宣告丟掉。結果常常看起來是對的(丟掉 `height` 等於沒設高度),
但那是碰巧:哪天有人在別處替這個名字補了一個值,
那一批元素會同時變樣,而畫面上看不出是從哪裡來的。

**base 要填「沒掛那個 class 時本來就該有的樣子」**,不是隨便填 0:

| 變數 | base | 為什麼 |
| --- | --- | --- |
| `--anchor-px` / `--anchor-py` | `0` | 沒掛就是沒有內距 |
| `--anchor-rounded` | `0` | 沒掛就是直角 |
| `--anchor-h` | `auto` | 沒掛就是**由內容撐開** —— 填 0 會讓那一批元素整個塌掉 |

**變體標記不算「可選的 class」。** `.--checkbox`、`.--textarea` 那種是元件自己
寫在畫面區段裡的(`class="m-form-element --checkbox"`),使用端不必掛也拿不掉 ——
那底下的指派一定會生效,不需要 base。
要補 base 的是**使用端選擇性掛的那幾種**:`--h-XX`、`--px-XX`、`--rounded` 那類。

分辨方式:那個 class 是元件的 `.vue` 寫死的,還是使用端自己決定要不要掛的。

### 斷點區塊只做指派,不要在那裡覆蓋基底的值

規則 `breakpointVarOverride`(擋)。上面那段斷點對應的右邊是 `var(…)`,
那是刻意的 —— **值集中在一處,斷點區塊只回答「這個斷點用哪一份」。**

```css
/* 不要 —— 同一個變數在基底與斷點各寫一次值 */
.home-index-header {
  --home-header-mt: -56px;
}

@screen p {
  .home-index-header {
    --home-header-mt: -84px;
  }
}

/* 要 —— 各斷點的值各有名字,斷點區塊只做指派 */
.home-index-header {
  --home-header-mt: 0;
  --home-header-pc-mt: -84px;
  --home-header-tablet-mt: -56px;
  --home-header-mobile-mt: -56px;
}

@screen p {
  .home-index-header {
    --home-header-mt: var(--home-header-pc-mt);
  }
}
```

覆蓋的那一種,值散在兩個地方:要改的時候得先找齊所有寫過它的位置,
漏掉一個就是某個斷點停在舊值 —— **不會報錯,畫面上也只有那個尺寸下才看得出來。**

級距 modifier 不在這條的範圍(`&.--px-30` 那種)。那是使用端傳 class 選的,
選擇器不一樣,與基底那一個本來就不是同一個東西。

這一條與頁面、元件、集中目錄都有關 —— 哪一層寫出這種覆蓋都是同一個問題。

### 只有某一個斷點要的值,不要單獨開一個斷點名

彈窗在手機是固定寬、桌機平板自適應。寫成這樣會卡住:

```css
/* 不要 —— 那個名字只有一份,看起來卻像成套結構的一員 */
:root {
  --popup-w: auto;
  --popup-mobile-w: 328px; /* lint-breakpoint-exempt: 只有手機固定寬 */
}
```

「斷點要成套」那條會報它,於是只好標一個豁免 ——
而**豁免是給「這個值真的不必分斷點」用的,不是給「只有一個斷點要」用的**。
後者有不必豁免的寫法:

```css
/* 變數檔的 :root —— base 給中性值(auto / none / 0) */
:root {
  --popup-w: auto;
}

/* 要的那個斷點,寫在元件的 class 底下 */
@screen m {
  .m-popup {
    --popup-w: 328px;
  }
}
```

版型檔那一側也不必再寫一行對應(`--popup-w: var(--popup-mobile-w)`),
值直接在斷點區塊給了。

**那個值要寫在元件的 class 底下,不是 `@screen` 裡的 `:root`。**
寫進 `:root` 的話,它與基底那一行同名又同一層,
上一節那條會把它報成「基底與斷點各寫一次值」——
而那條的訊息會叫你替各斷點各給一個名字,正好繞回最上面那個要標豁免的寫法。

**兩個斷點要、第三個不要的那種**(桌機平板有左右間距、手機改用上間距)
則是補齊三份,用不到的那一份給 `0` —— 三份成套,名字才看得出它們是一組。

### 值改成變數之後:有顏色版本的 utility 要標 `length:`

`px-`、`gap-`、`w-` 這類只吃長度的 utility 直接寫 `px-[--x]` 就好。
**但 `border-` 與 `text-` 同時有「長度」與「顏色」兩種版本** ——
建置工具分不出 `border-[--x]` 是框線寬度還是框線顏色,一律當成顏色。

```css
/* 不標型別:同一行的兩個 border- 被判定為衝突,其中一個不會產出 */
@apply border-[--step-card-question-border] border-[--white];

/* 標出型別之後兩個才會各自產出 */
@apply border-[length:--step-card-question-border] border-[--white];
```

**寫法是 `[length:--x]`,變數名直接接在冒號後面,不要包 `var()`**
(規則 `lengthTypeVar`,擋)。`[length:var(--x)]` 產出的 CSS 其實一模一樣,
擋的理由不是它會壞,是同一件事只能有一種長相 ——
要找出全站哪些地方標了型別時,兩種寫法得搜兩次,而搜的人不會知道有第二種。

要標型別的有這幾個(都是同時有顏色版本的):

| utility | 長度時的寫法 |
| --- | --- |
| `border-` | `border-[length:--x]` |
| `text-`(字級) | `text-[length:--x]` |
| `outline-` | `outline-[length:--x]` |
| `ring-` | `ring-[length:--x]` |

**`divide-` 不在名單裡。** 它只有顏色版本:`divide-[length:--x]` 產出的還是
`border-color`,標了完全沒有作用 —— 分隔線的寬度要寫成 `divide-x-[2px]`,
那是另一個 utility 名。

**值寫成字面值的不必標。** `text-[14px]` 產出 `font-size`、`text-[#fff]` 產出
`color` —— 帶單位的數字與色碼建置工具自己分得出來,所以
`text-[14px] text-[--gray-6b]` 兩個都會產出,那是正確的寫法。
分不出來的只有變數:`text-[--x]` 看不出 `--x` 裝的是 `16px` 還是 `#6b6b6b`。

### 漏標的兩種抓法

規則 `lengthTypeHint`(擋)。這是最難靠肉眼發現的一類 ——
編譯通過、瀏覽器不報錯,畫面上只是那個字級或框線寬度沒有作用,
要拿設計稿逐項比對才看得出來。兩種判定,誰先成立就報誰:

**一、同一段裡同一個前綴有兩個以上沒標型別的變數。**

```css
/* 兩個 text- 都被當成 color —— 字級那一個不會產出 */
@apply block font-light text-[--gray-9e] text-[--nav-description-text-size];
```

不必知道變數裝什麼就判得出來:兩個都是同一個 CSS 屬性,後面的蓋掉前面的。

前綴不同的不算(`text-[--a] hover:text-[--b]` 是常態與滑過去兩個狀態,
本來就不會互相蓋掉)。

**二、單獨出現時,追那個變數的值。**

```css
@apply text-[--datepicker-type-size];   /* 值是 16px → 要標 length: */
@apply text-[--datepicker-color];       /* 值是 var(--gray-999) → 顏色,不用標 */
```

值只是指向另一個變數時會追過去(斷點那一套就是這樣寫的)。
追不到定義、或值的形狀認不出來的一律不報 ——
那一段本來就是推測,誤報一次之後整條規則就會被當成雜訊。

`gap`、`margin`、`width` 這類只有長度一種版本,不受這兩條約束。

### 斷點前綴的完整寫法

每個級距在三個 `@screen` 都要列出,且各自涵蓋會命中該斷點的所有前綴:

| 斷點 | 需列出的變體 |
| --- | --- |
| `@screen p` | `--px-24`、`p:--px-24`、`pt:--px-24` |
| `@screen t` | `--px-24`、`pt:--px-24`、`tm:--px-24`、`t:--px-24` |
| `@screen m` | `--px-24`、`tm:--px-24`、`m:--px-24` |

道理是**一個前綴涵蓋哪幾個斷點,它就要出現在那幾個區塊**:涵蓋平板與手機的
那種前綴,平板與手機兩個區塊都要列;無前綴代表所有斷點都套用,每個區塊都要有。

少列一種的後果:使用端那樣寫了,在那個斷點下**不會有任何效果** ——
畫面上是「這個間距沒生效」,而那一行 class 看起來完全正常,
很難聯想到是樣式檔少列了一個選擇器。

哪個 `@screen` 該列哪幾種前綴,定義在 `.tools/lint/project-config.mjs` 的
`BREAKPOINT_SCREENS`。各專案的斷點名與涵蓋關係都不一樣,這份文件的表格是示意,
規則讀的是那一份設定。

檢查:規則 `breakpointPrefix`(擋)。**只有父層可傳入的級距受這條約束** ——
判斷方式是「這支檔案裡某處帶過前綴」。從來沒帶過前綴的是元件自己的變體
(`--size-md` 這種尺寸變體、狀態 modifier),使用端不會寫 `p:--size-md`,
要求它列出前綴變體是誤報。

## 四、為什麼分開放不會壞

級距覆寫比斷點預設對應**多一個 class**,specificity 較高:

- 斷點對應 `.m-form-element.--radio` → `0,2,0`
- 級距覆寫 `.m-form-element.--radio.--px-24` → `0,3,0`

所以即使 `***Variables.css` 比模組 css **先**載入,級距仍然勝出,**不受 import 順序影響**。

## 五、使用端

級距 class 由元件的 `setClass` 傳入,對應到 CSS 的覆寫規則:

```html
<MFormRadio
  :config="{ isBox: true }"
  :setClass="{ element: 'p:--px-15 p:--py-24 tm:--px-10 tm:--py-15' }"
/>
```

**沒有傳就是 `:root` 的預設值**(box 的 padding 預設 `0`)。因此不需要 `--px-0` /
`--py-0` 這種級距 —— 不傳即為 0。

### 元件沒有給的東西,先問是不是該由使用端決定

**元件的樣式裡沒有處理某一件事,多半是刻意留給使用端決定的,不是漏掉。**
那時正確的做法是從使用端傳,不是在變數檔加一個新變數。

最常見的是**元件內部那幾塊之間的距離**。例如按鈕裡圖示與文字並排,
而它的樣式完全沒有 `gap` / `ml-` / `mr-`:

```vue
<!-- 元件的畫面區段:三個東西並排,但樣式不管它們之間的距離 -->
<MSvgIcon v-if="icon.position === 'left'" />
<em class="m-anchor-text">{{ props.text }}</em>
<MSvgIcon v-if="icon.position === 'right'" />
```

那是因為**每一個按鈕要的距離不一樣**:圖示大小不同、文字長短不同、
放在哪裡不同。元件給一個值的話,要不同距離的那幾個就得再寫一條去蓋掉它,
而那一條與元件的那一份相隔很遠。

所以走使用端:

```vue
<!-- 傳進去,這一個按鈕自己決定 -->
<MAnchor :setClass="{ main: 'gap-x-[4px]' }" />
```

**距離給並排的那一層,不要給其中一邊。** 圖示可以在文字左邊也可以在右邊
(`config.icon.position`),而 `ml-` / `mr-` 只對其中一種位置是對的 ——
另一種位置時那段距離跑到外緣去,文字與圖示反而貼在一起。
`gap` 由容器給,兩種位置都成立。

**全站真的都一樣**(整個站的按鈕圖示間距都是 4px)才走 `styleProject.css`
那條路。那時與元件自己的樣式同一套寫法 —— 值分三個斷點放變數檔,
版型檔讀中性的那個名字,接點只放 `@import`:

```css
/* variablesProject.css —— 原始值(與〈三〉的變數檔同一種寫法) */
:root {
  --anchor-gap-x: var(--anchor-mobile-gap-x);
  --anchor-pc-gap-x: 4px;
  --anchor-tablet-gap-x: 4px;
  --anchor-mobile-gap-x: 4px;
}
```

```css
/* commonProject.css —— 樣式 + 斷點對應(與〈三〉的版型檔同一種寫法) */
.m-anchor {
  @apply gap-x-[--anchor-gap-x];
}

@screen p {
  .m-anchor {
    --anchor-gap-x: var(--anchor-pc-gap-x);
  }
}

@screen t {
  .m-anchor {
    --anchor-gap-x: var(--anchor-tablet-gap-x);
  }
}

@screen m {
  .m-anchor {
    --anchor-gap-x: var(--anchor-mobile-gap-x);
  }
}
```

```css
/* styleProject.css —— 這一支只放 @import */
@import './variablesProject.css';
@import './commonProject.css';
```

**三個斷點的值相同也要拆成三份。** 寫死一個值的話,要改成「手機窄一點」時
得先把它搬進變數檔、補三個 `@screen` 區塊 —— 而那時這個值已經散在
好幾個地方了。規則 `styleProjectValue`(擋)看的就是這件事:
`***Project.css` 裡方括號的值一律要走變數,
只有疊放順序、行高與字距三種不必分斷點。

**這個變數要放哪一支,看來源的元件有沒有它。** `--anchor-gap-x` 來源沒有,
所以它連同讀它的樣式都放 `<變體>VariablesProject.css` 與 `<變體>Project.css`,
開之前先問設計者是不是該回報來源補;`--anchor-bg-color` 這種來源已經有的
(哪怕預設值是 `transparent`),要另一個值就在來源那支變數檔加一組級距,
不必另開檔案,也不必問人。

而這一節講的 gap 連變數都不必開:**它是每顆按鈕不一樣的東西**,
走使用端 `setClass` 就好 —— 做成變數等於替一個沒有共通值的東西挑一個預設值,
而每一個不照那個值的地方都要再寫一條去蓋掉它。

## 六、新增級距的檢查清單

**級距要幾段、各是多少,由接手的專案決定。** 來源那幾支變數檔列的是
那個站用得到的段數,不是「只能用這幾段」—— 要一個來源沒有的值就自己加一組。

級距 class 最單純:加一組就好,不必動別的地方 —— 它只是把既有的變數
換成另一個值,版型檔照樣讀同一個名字:

```css
/* <變體>Variables.css —— 把版型檔讀的那個名字換成別的值 */
@screen p {
  .m-x {
    &.\-\-bg-green,
    &.p\:\-\-bg-green,
    &.pt\:\-\-bg-green {
      --x-bg-color: green;
    }
  }
}
```

**級距指派的是「版型檔讀的那個中性名」**(`--x-bg-color`),
不是 `-pc-` / `-tablet-` / `-mobile-` 那三份 —— 那三份是預設值的來源,
由斷點對應去讀(見〈三〉)。所以同一個屬性有兩種動作,兩種都是自由的:

| 動作 | 改什麼 |
| --- | --- |
| 改 `--x-pc-bg-color` 等三份的值 | 這個站的**預設**長相 |
| 加一組級距蓋 `--x-bg-color` | 多一個**使用端可以選**的樣子 |

**而要加級距的前提是來源的版型檔讀得到那個中性名。**
判準就是這一句 —— 不是「這段樣式長什麼樣」:

| 來源的版型檔 | 加在哪 | 要不要先問 |
| --- | --- | --- |
| **有**讀 `--x-bg-color`(哪怕預設值是 `transparent`) | `variables.css` / `<變體>Variables.css` —— 自由加級距 | 不用。那本來就是元件開給使用端的介面,使用端掛 `setClass.main: '--bg-green'` 就生效 |
| **沒有**這個名字 | `<變體>VariablesProject.css`(變數)+ `<變體>Project.css`(讀它的樣式),兩支從 `styleProject.css` 接 | **要**。先問設計者:這是來源該補的缺口,還是只有這個站要 |

**級距可以自由擴增,是因為它與來源不會撞。** 它用的是來源既有的變數名,
版型檔照樣讀同一個名字;而 `--bg-green` 這個 class 名是這個站自己取的,
來源不會有同一個。所以來源日後改了那支變數檔,要合過來的時候,
那幾組級距一眼看得出是額外的,不會與來源的任何一行對不上。

`:root` 底下自己開一個名字就不一樣:**那個名字可能與來源日後加的撞**,
而撞的時候兩邊的語意不一定相同 —— 畫面不會報錯,只是某個值變成另一件事。
所以**不要在來源那幾支加新名字**。不是因為會被蓋掉
(樣式那一層整層歸這個專案,一支都不覆蓋),是因為混進去之後
**沒有人分得出來**:下一個人讀那支變數檔,說不出哪幾個是元件本來就有的介面、
哪幾個是這個站加的;來源改了那支檔案時,也說不出該合哪幾行。

檢查:規則 `componentApiAdded`(擋)比對的是來源那一份名單 ——
它報的不是「不能加」,是「位置不對」。

0. 這個值該由**誰**決定?全站只有一種樣貌的固定模組寫在元件自己的樣式裡,
   到處會用到的通用元件才留給使用端傳入 —— 後者才需要往下走這份清單。
1. 這個屬性目前有幾個值?**兩個以上**才需要進 Variables 檔。
2. 只有這個模組會用嗎?是 → `***Variables.css`;跨模組 → 共用變數檔
   (位置定義在 `.tools/lint/project-config.mjs` 的 `SHARED_MODULE_VARIABLES`)。
3. 三個 `@screen` 都補齊了嗎?各自的前綴變體都列了嗎?
4. 值本身是否已存在於同組級距?避免同一屬性出現重複或過於接近的級距。

## 七、模組 css 只能寫自己那組 class

**一支模組 css 裡,選擇器只能是這個模組自己的 class 與它的 `--modifier`。**
模組名從資料夾名推出來(`mForm` → `.m-form`),所以一支樣式該寫哪一組
一眼看得出來。

錯誤的寫法(在 `mForm` 的樣式裡寫別的模組):

```css
.m-form-element {
  @apply flex;
}

.m-popup-title {
  @apply text-lg;
}
```

正確的寫法:`.m-popup-title` 搬到 `mPopup` 自己的樣式裡。

**變體的 class 也要收斂成母體前綴。** `mSwitch` 底下的樣式寫
`.m-switch-item-header` 是對的,寫 `.m-switch-item` 以外的開頭(例如
`.m-item-header`)則不行 —— 那個名字看不出它屬於哪一個模組,
刪掉那支元件時也沒有人知道這段樣式跟著要刪。

不是 `m-` 開頭的 class(`.title`、`.active` 這種)一律不能寫在模組 css 裡。
那種名字太通用,兩支模組各自定義一次就會互相蓋掉,而蓋掉的那天不會有人通知你。

### 轉場動畫:照效果命名,放共用檔

規則 `transitionShared`(擋)。

**要寫轉場動畫時,第一件事是去共用的轉場樣式檔看有沒有現成的。**
淡入淡出、縮放、滑入、高度展開 —— 這幾種每個專案都會用到好幾次。

**沒有適合的就在那支共用檔新增一組,不要寫在元件自己的樣式裡。**
寫在元件裡的那一份別人找不到,也不會想到要去找 —— 於是同一種動畫被實作第二次、
第三次,秒數各差一點,畫面上就出現「明明都是淡入,這裡比較快」的不一致。

這與「元件的樣式放在元件自己的資料夾」不衝突,兩者分的是不同的東西:
**長相**(顏色、間距、字級)屬於那支元件,**動作**(怎麼進場、怎麼離場)是跨元件的共同詞彙。

進出場動畫的 class(畫面區段寫 `<Transition name="…">` 的那個名字加上框架的後綴)
**不收進模組前綴**,規則 `moduleScope` 對它們放行。理由是那個名字與畫面區段寫的
必須一模一樣 —— 收斂成模組前綴的話兩邊就對不上,而轉場失效不會報錯,只是動畫沒了。

**前綴用 `anim-`,不要用模組的 `m-`。** `m-` 在這套系統裡的意思是「一個模組」,
`m-backdrop` 看起來就像有一支叫 backdrop 的元件 —— 但動畫不是模組,
它沒有對應的元件資料夾,也不會有人去找它的 `.vue`。

也不要用 `transition-`:那是 tailwind 自己的 utility 前綴
(`transition-opacity`、`transition-transform`),混在一起會看不出哪個是自己寫的。

**名字照「效果」取,不照「哪支元件在用」或「擺在哪個位置」取。**

| 這樣取 | 不要這樣取 | 為什麼 |
| --- | --- | --- |
| `anim-fade`、`anim-zoom`、`anim-slide-up`、`anim-collapse` | `popup-fade`、`datepicker-bomb`、`tooltip-content` | 綁元件 |
| `anim-fade-out-late`(淡出慢半拍) | `anim-backdrop`(遮罩) | 綁角色 |

綁元件的名字只要第二支元件想用同一種動畫就會出事:畫面上會出現
`name="datepicker"` 卻不是日曆,下一個人看到會以為用錯了,
於是複製一份改名 —— 同一種動畫就有了兩份定義,之後各自演化。

綁角色(`backdrop`、`toast`、`panel`)問題一樣,而且還多綁住一個詞:
取了 `anim-backdrop` 之後,每一處遮罩的樣式都會被期待叫 `*-backdrop`,
而實際上遮罩用的動畫與別處的淡入淡出是同一種 —— 名字卻分成兩個。

**放在共用的轉場樣式檔,由進入點一次載入。** 同一種效果只留一組,
秒數在同一類效果裡統一(淡入淡出一律同一個秒數),不因為使用端不同各開一份 ——
差 0.05 秒看不出來,但兩份會各自演化。

**元件用了共用檔裡的轉場,要在元件檔頭列進搬移清單**(規則 `componentDeps`)——
那支檔案不在元件的資料夾底下,複製元件時很容易漏掉,
而漏掉之後畫面都在、功能也正常,只是切換的當下直接跳。

### 要對父層的狀態有反應時

父層掛上關聯機制的 class(`group`、`peer`),底下的元件就能對父層的 hover 有反應。
那不是別的模組,是建置工具提供的掛勾,所以寫在模組 css 裡是對的。

**寫法是把那個條件放在選擇器中段,開頭仍然是自己的 class:**

```css
.m-figure {
  &.\-\-image-scale {
    .group:hover & {
      img {
        @apply scale-110;
      }
    }
  }
}
```

**不要用 `@apply group-hover:` 那種前綴的寫法。** 它看起來更短,而且規則也不會報 ——
但**產出來的 CSS 是錯的**:巢狀展平時,那個前綴會把父層的條件接成
「元件**底下**的某個元素有那個 class」,而不是「元件的**祖先**有」。
連動就整個失效,而且從原始碼看不出來 —— 那一行寫得完全正常。

| 寫法 | 展平後 | 結果 |
| --- | --- | --- |
| `.group:hover &` 放在中段 | 父層的條件在**前面** | 正確 |
| `@apply group-hover:` | 父層的條件變成**後面的後代** | 連動失效 |

要改這種寫法時,**編譯一次看產物**再決定 —— 兩種寫法在原始碼裡長得都很合理,
差別只在展平之後。

檢查:規則 `moduleScope`(擋)。掛勾那幾個名字由建置工具定義,規則認得它們,
不必當成模組 class 去加前綴。

## 八、樣式要放在元件自己的資料夾

**一支樣式的名字對得上某個實際存在的元件時,它就屬於那個元件,
要放進那個元件資料夾底下的樣式子資料夾。** 集中目錄留給跨模組共用的變數。

留在集中目錄的話,上一節那條「只能寫自己那組 class」**不會檢查它** ——
不是報錯,是完全沒有訊息:違規數字還會因此變少,看起來像程式碼變好了。

集中目錄底下先分一層類的時候,歸屬看的是分類**底下那支元件**,不是分類本身。
分類底下有好幾支元件,答成分類的話,那幾支的樣式會全部搬進同一個資料夾,
誰的樣式是誰的就看不出來了。

分辨元件與分類層的方式:資料夾裡**直接放著 `.vue`** 的才是元件,
只放著其他資料夾的是分類層。

檢查:規則 `moduleLocation`(擋)。

### 每一支樣式都要有人 import

規則 `moduleCssUnused`(擋)。**樣式檔不會自己生效** ——
沒有任何元件 import 它的話,整支一行都不會輸出。

那是完全沒有徵狀的一種壞法:檔案還在、語法正確、全案檢查通過,
只有畫面上少了那一整批樣式。而「少了樣式」看起來常常像設計本來就長那樣。

兩種情況都是它在抓:

- **新加了一支卻忘了 import** —— 加樣式時最容易漏掉的一步
- **元件改寫時把 import 拿掉了** —— 整支樣式從此靜靜地沒有作用

真的用不到那一支了就把它刪掉,不要留著 —— 留著的話,
下一個人看到那些變數與 class 會以為它們有效。

### 元件的樣式目錄底下有哪幾種檔案

一支元件常常不只一種樣子(表單的 select、checkbox、radio 是同一個模組的變體)。
一般會長成這幾支,**兩兩成對**:

| 檔案 | 放什麼 | 誰在讀 |
| --- | --- | --- |
| `variables.css` | 整個模組共用的變數 | 底下每一支樣式 |
| `common.css` | 整個模組共用的版型 | — |
| `<變體>Variables.css` | 那一個變體自己的變數 | 同名的那一支版型 |
| `<變體>.css` | 那一個變體自己的版型 | — |

變數檔與版型檔分開,是因為兩者的改動頻率完全不同:
換一個專案時改的幾乎都是值,版型那一半原封不動。

**版型檔要拆幾支、各自叫什麼,是那個模組自己的事。** 一支複雜的元件
拆成 `header.css`、`body.css` 是正當的,不必硬塞進上面那四個名字。

**變數檔的檔名則有規定:一律以 `variables.css` 結尾**(大小寫不拘)。
載入順序那條規則(`moduleOrder`)靠這個名字認出哪幾支是變數檔 ——
名字不對的話它會被當成版型檔,而「變數要先定義完、版型才取用」
這件事對它就不再檢查。取用當下變數還沒定義,吃到的是空值,
而畫面上只是那一段樣式沒有生效,不會報錯。

元件自己 import 它要的那幾支,而且**變數檔排在版型檔之前**(見下一節)。

### 元件的樣式歸接手的專案

元件搬進專案之後,**樣式那一層完全歸那個專案**:版型、變數、變體,每一支都可以改,
整套更新時一支都不會被覆蓋(`<template>` 與 `<script>` 的邏輯則是整段跟著來源 ——
哪一部分跟、哪一部分不跟,完整的對照在元件寫法那一份規範裡)。

樣式這一側跟著成立的是三件事:

**來源那幾支變數檔只改值、只加級距。** 來源沒有的變數連同讀它的樣式
走下面那張表的第 3 層 —— 而且**開之前先問設計者**:
這是來源該補的缺口(回報來源,每個專案都拿得到),還是只有這個站要。

檢查:規則 `componentApiAdded`(擋)。它比對的是變數檔 `:root` 那一份名單 ——
級距與版型那兩層不比,所以加級距、改值都不會被報。
它報出來的意思是**位置不對**,不是「不能加」。

**只比對來源既有的那幾支檔案。** 專案自己新增的元件、自己新開的變數檔,
來源名單裡沒有那個檔案,整支跳過 —— 不然每開一支自己的樣式檔就被報一整串。

**動手之前先確認現有的那幾支做不做得到。** 由上往下試,**停在做得到的那一層**:

| 順序 | 改哪裡 | 什麼情況 |
| --- | --- | --- |
| 1 | `<變體>Variables.css`、`variables.css` | **改**來源既有的值:顏色、尺寸、間距、圓角、字級、斷點 —— 換一個專案要改的幾乎都在這一層 |
| 2 | `<變體>.css`、`common.css` | **改**來源既有的規則:變數沒開到的版型(排列方式、顯示與否、偽元素) |
| 3 | 從 `styleProject.css` 接出去的 `<變體>Project.css` / `<變體>VariablesProject.css` | **加**來源沒有的東西:新的 modifier、新的狀態、整組新的區塊 |

**前兩層是「改」,第 3 層是「加」。判準問的是「這段樣式來源有沒有」,
不是「它掛在哪一個元素上」。**

在來源既有的元素上多掛一個來源沒有的 modifier —— 例如 `.m-form-element` 上
多一個 `--box` —— 那仍然是**來源沒有的東西**,走第 3 層。
掛在既有的 class 上不代表它屬於第 2 層:第 2 層講的是
把來源既有的那幾條規則改成別的樣子,不是在旁邊加新的。

前兩層一樣不會被覆蓋(整層都歸這個專案),
所以**「怕被蓋掉」不是跳到第 3 層的理由** —— 那是這三層共同的前提,不是第 3 層的特權。
反過來也一樣:**「不會被蓋掉」不是把新東西寫進來源檔案的理由**。代價不在覆蓋,在別處:

- 下一個接手的人打開那一支,分不出哪幾條是元件庫本來就有、哪幾條是這個站加的
- 要回答「我們的樣式跟來源差多少」就得逐行比對
- 來源真的修了那一支的問題而你想拿過來時,混在一起就分不出該合哪幾行

`styleProject.css` 存在的理由就是**這個站自己的東西集中在一處**;
寫進來源的檔案等於放棄那個好處,而放棄的當下沒有任何徵兆。

**倒過來做不會報錯,所以要自己守。** 變數做得到的事寫成一條覆蓋之後,
同一個值就同時活在兩個地方,而來源那一份從此是死的:
下一個人改 `<變體>Variables.css` 不會有任何作用(被最後那一支蓋掉),
檔案裡寫著的值與畫面上量到的對不上,而沒有任何訊息說得出為什麼。
整套更新時來源調整了那幾個變數,被蓋住的那部分同樣看不出來 ——
**改對邊的人拿得到更新,改錯邊的人拿不到,而兩者的差別不在畫面上。**

這一條沒有工具在檢查,也檢查不了 —— 「你要的效果變數做不做得到」
只有看著設計稿的人答得出來。所以它寫在這裡,也寫在每一支 `styleProject.css` 的檔頭。

**新的樣式從 `styleProject.css` 接進來,不要自己在元件多加一行 `import`。**

每支元件的樣式資料夾底下都有一支 `styleProject.css`,來源那一份是空的,
而且元件已經載入它 —— 就排在所有樣式的最後:

```vue
<script setup>
import './.css/variables.css'
import './.css/common.css'
import './.css/styleProject.css'
</script>
```

這一支存在的理由是:**元件的 `<script>` 跟著來源整段覆蓋**。
自己多加的那一行寫在裡面,下一次更新就消失 —— 檔案還留著但一行都不會輸出,
畫面上是「那一整批樣式突然沒有作用」,而且不報錯。
而這一行是來源本來就有的,覆蓋之後它照樣在。

**所以這一整段只適用於「從來源來的元件」。**
專案自己寫的元件不會被任何人覆蓋 —— 要加樣式直接改它自己的樣式檔,
或在它的 `<script>` 多寫一行 import 就好,不必建接點。
建了不會報錯,只是多一支永遠空著的檔案,而下一個人看到會以為那是必要的。
(那條檢查也只在來源跑:在別的專案跑的話,他們自己寫的每一支元件
都會被報一筆,而那全是誤報。)

排在最後也是刻意的:這裡寫的值蓋得過來源的變數檔與版型檔。
`@import` 只能放在檔案最前面(css 的規矩),所以接在來源那幾支裡面的話,
反而會被那一支自己的規則蓋掉。

**這一支只放 `@import`,樣式本身寫在拆出去的那幾支裡:**

```css
/* styleProject.css */
@import './<自己的那一組>VariablesProject.css';
@import './<自己的那一組>Project.css';
```

直接寫在接點裡不會壞掉(它照樣輸出),所以單看畫面分不出來 ——
分得出來的是檔名:拆出去的那幾支一眼看得出哪些是這個站自己加的,
而全部堆在接點裡的話,這個站加了什麼要整支讀完才知道。

角括號是要換掉的部分 —— 拆幾支由那個專案決定,
**結尾兩種固定:變數檔 `VariablesProject.css`、版型檔 `Project.css`。**
前面那一段對著來源的檔名取,主樣式那一組就沿用來源的名字:

| 來源 | 這個站加的 |
| --- | --- |
| `common.css`(主樣式) | `commonProject.css` |
| `variables.css`(主樣式的變數) | `variablesProject.css` |
| `<變體>.css` | `<變體>Project.css` |
| `<變體>Variables.css` | `<變體>VariablesProject.css` |

那幾支與來源的樣式躺在同一個資料夾裡。結尾分不出歸屬的話,
下一次整套更新時沒有人說得出哪幾支是來源的、哪幾支是這個站自己加的 ——
沿用來源的命名(`<變體>Variables.css`)更糟:那正是來源會覆蓋的那一批名字。

變數那一種的結尾還有第二個作用:**整組變數規則靠它認出「這是變數檔」**。
名字不對的話它被當成版型檔,斷點要成套、命名要對齊 tailwind、
斷點不要用覆蓋寫那幾條對它一條都不作用 —— 而那幾條不作用時沒有任何訊息,
檢查照樣顯示通過。所以這一層的變數同樣要照 `:root` 定義、
三個斷點各自指派的寫法(見〈三〉)。

這支接點只接同一層自己拆出去的那幾支。外部套件的樣式與全域那幾支
走全域的樣式進入點 —— 接在這裡的話,每一支載入這個元件的地方都會再輸出一份。

檢查:規則 `styleProjectImport`(擋)。

變數檔排在版型檔之前,與元件那幾行的順序同一個道理:
變數要全部先定義完,版型才取用。

`@import` 進來的東西在建置期就被接成同一份產物,走完整條樣式鏈
(`@apply` 會展開、px 會轉 rem),產物裡不會留下 `@import`,
也不會多一次連線;同一支被兩個地方引進來只會輸出一份。

**空著是正常的,不要刪。** 元件那一行 `import` 是來源的,
檔案不在的話建置會當場失敗,而且訊息指得出是哪一支元件的哪一行 ——
那比「樣式安靜地少一批」好處理得多。

唯一仍然成立的限制是「要有人載入」:規則 `moduleCssUnused`(擋)看樣式檔
有沒有被載入 —— 拆出去的那幾支如果忘了從 `styleProject.css` 接,
整支一行都不會輸出,而畫面上只是少了一批樣式,
看起來常常像設計本來就長那樣。

## 九、變數檔要排在版型檔之前

元件 import 自己那幾支樣式時,**`***Variables.css` 一律排在版型檔之前**:

```vue
<script setup>
import './.css/variables.css'
import './.css/common.css'
</script>
```

變數要全部先定義完,版型才取用。順序反過來的話,版型取用的當下變數還沒定義,
吃到的是空值 —— 畫面上是「這個間距沒有生效」,而那一行 css 看起來完全正常。

檢查:規則 `moduleOrder`(擋)。

## 十、引用的變數一定要有定義

**引用的變數名,全案要找得到它的定義。** 兩種寫法都算:`var(--x)`,以及建置工具那種寫在方括號裡的(`text-[--x]`、`bg-[--x]`)—— 後者編譯出來就是前者,壞掉的方式一模一樣。

找不到時**不會報錯** —— 瀏覽器只是把那一整條宣告丟掉。畫面上是
「框線和底色整片不見」,而每一個檢查工具都顯示通過:那個落差很難
從結果反推原因,通常要一行一行比對才找得到。

最常踩到的時機是**把元件搬到另一個專案** —— 那邊的色票命名不一樣,
元件引用的名字一個都對不上,整批樣式安靜地失效。

兩種情況不算違規:

| 寫法 | 為什麼不算 |
| --- | --- |
| `var(--x, 20px)` 帶後備值 | 那是刻意的:變數沒有時用後備值,樣式不會消失 |
| 元件動態綁的 `:style="{ '--x': 值 }"` | 那也是定義,只是由程式在執行時給 |

檢查:規則 `unknownVar`(擋)。

## 十一、自動檢查

五條規則(`moduleVar`、`moduleScope`、`moduleLocation`、`moduleOrder`、`breakpointPrefix`),
判斷邏輯在 `.tools/lint/lint-core.mjs`,五個時機跑的是同一份判斷:

- **存檔時** —— 編輯器與開發伺服器會即時檢查,違規逐筆印在終端機。只提醒,不影響存檔。
- **AI 寫檔時** —— `.claude/hooks/enforce-conventions.cjs` 比對寫入前後的內容,
  只擋「這次新增」的違規;既有存量不影響。
- **對話時** —— 存檔時沒修掉的違規會列進對話,直到修好為止。
- **commit 時** —— pre-commit 檢查這次提交的檔案。

本機覆核:`node .tools/lint/lint.mjs <檔案或目錄>`。

五條都不自動修正。工具看得出「這裡不對」,看不出那段樣式該進哪一支檔案、
那個 class 該叫什麼名字 —— 自動改等於替開發者決定檔案結構與命名。

`moduleVar` 抓兩種情況,都是「該收進變數檔的東西留在模組 css」:

**一、同一屬性出現兩個以上不同值的覆寫 class**(例如同時有 `--px-24` 與 `--px-15`)——
那是一組級距,要搬到對應的 `***Variables.css`。
不算違規的:`***Variables.css` 與 `variables.css` 本身、單一值的覆寫 class、
以及值不是數字的狀態 modifier(`--range-start` 這種是狀態不是尺寸級距)。

**二、同一處在不同斷點寫死了不同的值**(pc 寫 `text-[14px]`、mobile 寫 `text-[13px]`)——
那是一組斷點值,要定義成 css 變數再由模組樣式做斷點對應。

判準是「**不同斷點的值不一樣**」,不是「有沒有寫字面值」——
三個斷點都寫 `text-[14px]` 只是重複,那個值根本不隨斷點變,抽成變數反而多繞一層。
不同選擇器底下的同名 utility 也不會被湊成一組。

報出來的目標檔名依變體決定:模組主樣式 `common.css` 配的是 `variables.css`,
變體樣式 `selection.css` 配的才是 `selectionVariables.css`。

## 與相鄰規範的界線

| 規範 | 管什麼 |
| --- | --- |
