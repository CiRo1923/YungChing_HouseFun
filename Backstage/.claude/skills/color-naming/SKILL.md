# 顏色變數規範:集中定義、命名一致、彩虹排序

所有顏色一律定義為 CSS 變數,依「誰會用到」分成兩種色票檔,都放在色票目錄底下。
目錄位置與檔名前綴都定義在 `.tools/lint/project-config.mjs`
(`COLOR_CSS_DIR` 與 `COLOR_CSS_PREFIX`)—— 這份文件用 `<前綴>` 指稱那個字,
不寫死,因為每個專案叫什麼不一樣。

| 檔案 | 放什麼 | 怎麼載入 |
| --- | --- | --- |
| `<前綴>.css` | **跨分組共用**的色 | 全域載入,程式一開機就可用 |
| `<前綴>{分組名}.css` | **只有那個分組要用**的色 | 由該分組的版型檔載入 |

前綴是 `color` 的專案,這兩種就是 `color.css` 與 `colorMember.css`。

分組指的是「有自己一套配色的區塊」——例如一個獨立的活動、一個問卷模組。
專案有哪幾個分組由專案自己決定,檔名就是前綴加上分組名。

新增或調整顏色時:**跨分組共用的**只改共用那一支(全域生效);
**只有一個分組要用的**改那個分組的檔案。共用色不在分組檔裡重複定義 ——
重複定義之後,改了一邊沒改另一邊,兩個分組的同一個顏色就會不一樣。

**頁面(.vue / .css)不得硬寫色碼**,一律改用 `var(--xxx)`。

## 一、命名規則:色相前綴加上取碼後綴

變數名由三段組成:**色相 + 分隔符 + 取碼**,例如 `--red-e01a` 的色相是 `red`、
分隔符是 `-`、取碼是 `e01a`。

色相有哪些、分隔符是什麼、取碼怎麼取,都定義在 `.tools/lint/project-config.mjs`
(`COLOR_HUES`、`COLOR_NAME_SEPARATOR`、`COLOR_SUFFIX_PICK`)——
**每個專案的配色與命名慣例不一樣,所以那幾項是設定,不是寫死的規則。**
下面的例子是多數專案在用的那一套預設值;要知道這個專案實際用什麼,看設定檔。

### 兩種命名方式,一個專案只能選一種

色票變數的命名分兩種,差別在**名字裡看不看得出顏色**:

| 方式 | 長相 | 色相從哪裡來 | 設定值 |
| --- | --- | --- | --- |
| 帶色相的名字 | `--red-e01a`、`--gray-9e` | 直接讀名字 | `COLOR_HUE_SOURCE = 'name'` |
| 語意名 | `--title-color`、`--btn-hover` | 從色值算 | `COLOR_HUE_SOURCE = 'value'` |

兩種都能做到「彩虹順序、每類由淺到深」,也都能擋「頁面硬寫色碼」。
差別在**人的判斷能不能被保留**:`#c09648` 在色相環上是橘,
品牌把它定義為金 —— 名字寫 `--gold-c948` 就歸金,色值算出來則是橘。
所以名字帶色相的專案要用 `name`,那是人做過的判斷,不該被工具推翻。

**同一份色票不能混用兩種。** 混在一起的話,一半的色依人的判斷分類、
另一半依色值分類,排出來的順序沒有一致的依據 —— 讀的人看到金和橘夾雜,
不知道該照哪一種去放新的顏色。混用時工具會報出兩種各有幾個,
並指出大宗是哪一種(另一批就是要跟著改的)。

設定選錯的話,超過一半的變數會走錯路徑,工具在全專案檢查時會講出來:
設成 `name` 而實際是語意名,那一批會每一個都被報「認不出色相前綴」,
排序還會把它們重排成一大群未知色;設成 `value` 而實際帶色相,
名字裡人給的語意分類會被色值算出來的結果蓋掉。

### 色相前綴

預設的十個色相:
`red` / `orange` / `yellow` / `green` / `blue` / `purple` / `gold` / `white` / `gray` / `black`

這份清單同時就是色票檔裡的排列順序(紅 → 橙 → 黃 → 綠 → 藍 → 紫 → 金 → 白 → 灰 → 黑)。
順序不對時存檔會自動排好,不必手動調整。

專案配色有粉、棕、青這類獨立色相時,加進設定的清單並擺在彩虹順序裡對應的位置 ——
不加的話,那些色會被判定為「認不出色相前綴」。

- 依實際視覺色相歸類,**不看既有(可能錯誤的)命名**。
  例:`#ced4da` 是淺灰藍 → `--gray-cdda`(不是 orange);`#0e6f86` 偏青 → 仍歸 green/blue 取其近者。
- `#000` / `#fff` 用語意名 `--black` / `--white`。

### 後綴取碼規則

下面是預設的取法。專案的命名慣例不同時改設定,規則與提示訊息會跟著算出正確的建議名稱。
常見的落差是**透明度那兩碼怎麼接** —— 有的專案直接相接(`--gray-e566`),
有的用分隔符隔開(`--gray-e5-66`),那一項是設定裡的 `alphaSeparator`。

設定與專案實際命名對不上時,那一類的取碼檢查會完全沒有結果 ——
不是報錯,是看起來全部通過。所以工具在全專案檢查時會把這種情況講出來,
訊息會指出該改哪一項設定。

| 情況 | 取法 | 範例 |
| --- | --- | --- |
| 一般 6 碼 hex | 取第 **1,3,5,6** 碼 → 4 碼後綴 | `#e2001a` → `--red-e01a`;`#c20016` → `--red-c016` |
| 灰階(r=g=b,如 `#9e9e9e`) | 取第 **1,2** 碼 | `#9e9e9e` → `--gray-9e`;`#383838` → `--gray-38` |
| 3 碼 hex(`#abc`) | 直接用該 3 碼 | `#999` → `--gray-999`;`#ddd` → `--gray-ddd` |
| 帶透明度(8 碼 `#rrggbbaa`) | 基礎後綴 + **alpha 兩碼** | `#9e9e9e04` → `--gray-9e04`;`#e2001a04` → `--red-e01a04` |
| 純黑 / 純白帶透明度 | **只有 alpha 兩碼** | `#000000b3` → `--black-b3`;`#ffffff66` → `--white-66` |

> 括號標注取碼位置的由來,例 `#e2001a`(1,3,5,6)= e,0,1,a = `e01a`。

純黑與純白用語意名 `--black` / `--white`,本來就沒有取碼後綴 ——
取碼的用途是在同一個色相裡區別不同的色,而純黑與純白各自只有一個,
沒有要區別的對象。所以帶透明度時只接 alpha,寫成 `--black-b3`,不是 `--black-00b3`。

**衝突處理**:若同色系兩色算出相同後綴,微調取碼位置使其在同色系內唯一。

### 透明度:寫進 8 碼,不用 rgba

**一個顏色就是一個變數。** 需要半透明的顏色時,在色票裡建一個 8 碼的變數,
使用端一樣只寫 `var(--xxx)`:

```css
/* 色票檔 */
--black-b3: #000000b3;      /* 70% 黑,用在彈窗遮罩 */
--gold-c94800: #c0964800;   /* 全透明的金,用在漸層終點 */

/* 使用端 */
background: var(--black-b3);
```

看名字就知道是什麼色、多透明,而且那是標準 CSS,不必靠建置工具轉換 ——
少一層轉換就少一個會出錯的地方。

**色票裡每一個變數的值就是一個色碼**,不是 `rgba()`、不是 `var()`、不是任何函式。
除了寫法一致之外還有一個實際理由:取碼命名是從色碼算出來的,
值不是色碼的話那個計算得不到結果,**那一筆的命名檢查會整個被跳過** ——
於是值寫成 `rgba()` 之後,連名字對不對都不再有人看,而畫面上顯示的是通過。

**這三種寫法都不再使用:**

| 不要 | 為什麼 |
| --- | --- |
| `--xxx-rgb: hexToRgb(#hex);` | 把色碼拆成三個數字存起來,只為了讓 `rgba()` 能用 |
| `rgba(var(--xxx-rgb), 0.4)` | 同一個顏色散成「變數 + 一個數字」,搜尋變數名找不到實際用了幾種透明度 |
| `rgba(#hex, 0.4)` | 色碼直接寫在使用端,而且要靠建置工具才展開得開 |

前兩種是同一條鏈:`hexToRgb()` 產生衍生變數,衍生變數再餵給 `rgba()`。

**後兩種存檔時會自動改掉**,不必手動處理 —— 色值與透明度都是現成的,
算得出唯一的結果。分兩種情況:

| 寫在哪 | 存檔時會發生什麼 |
| --- | --- |
| 使用端 `rgba(var(--x-rgb), 0.4)` | 換成 `var(--x-<8碼後綴>)`;色票裡還沒有那個顏色時一併補進去(補在基礎色所在的那一支,因為用得到基礎色的範圍才用得到它的半透明版) |
| 使用端 `rgba(#hex, 0.4)` | 併成 8 碼色碼,接著由「不得硬寫色碼」報出來,請人建立變數 |
| 色票裡 `--x: rgba(#hex, 0.4)` | 值換成 8 碼,**名字也跟著重算**,全站用到舊名的地方一起換掉 |

色票裡那一種為什麼要連名字一起改:名字是從色值算出來的,
色值變了名字就不再對得上。而改了名字不同步使用端的話,
那些地方會指向一個沒有定義的變數 —— 畫面上不會報錯,顏色就是不見了。

### `hexToRgb()` 要先問過才動

**這一種只提醒,不自動改。** 因為工具看不出「這個衍生變數被用在哪幾種透明度」,
也就不知道要建幾個變數。開發者說「修正」或「好」之後才處理,步驟是:

1. 從色票找出那一筆的底色,例如 `--black-rgb: hexToRgb(#000)` 的底色是 `#000`
2. 掃全站,找出每一處用到它的地方,例如某支 css 寫 `rgba(var(--black-rgb), 0.3)`
3. 每一種透明度各算一個 8 碼色值與名字:`0.3` 得到 `#0000004d`,名字是 `--black-4d`
4. 把那些變數寫進色票(放在底色所在的那一支),使用端改成 `var(--black-4d)`
5. 確認沒有地方還在讀舊的衍生變數之後,把它從色票移除

同一個底色被用在三種透明度就會得到三個變數,這是正常的 ——
一個顏色一個名字,看名字就知道是什麼色、多透明。

## 二、排序規則

**大分類依彩虹**:紅 → 橙 → 黃 → 綠 → 藍 → 紫 → 金 → 白 → 灰 → 黑。
**每一色類內部由淺到深**(以感知亮度 `0.299R + 0.587G + 0.114B`,亮者在前)。
帶透明度的變數用它的底色算亮度,所以會排在同一個底色的附近。

## 三、使用規範(頁面端)

```css
/* 不要在 .vue / .css 硬寫色碼 */
color: #e2001a;
background: linear-gradient(180deg, #e2001a, #c20016);
box-shadow: 0 4px 16px rgba(#a7afb7, 0.33);

/* 改用變數;半透明的色也是一個變數 */
color: var(--red-e01a);
background: linear-gradient(180deg, var(--red-e01a), var(--red-c016));
box-shadow: 0 4px 16px var(--gray-aab754);
```

Tailwind arbitrary value 同樣用變數:`text-[--red-e01a]`、`bg-[--white]`、`border-[--gray-cdda]`。

### 例外:JS 物件內的顏色

送往外部平台的 JS 物件(如 **LINE Flex Message** 的 `color` / `backgroundColor`)由該平台
渲染,**CSS 變數在此無效**,必須是實際 hex 字串。此類顏色允許保留 hex,但應集中為 JS 常數而非散落各處。

## 四、自動檢查

規則 `color` 與 `colorFile`,判斷邏輯在 `.tools/lint/lint-core.mjs`,
四個時機跑的是同一份判斷:

- **存檔時** —— 編輯器與開發伺服器會即時檢查,違規逐筆印在終端機。只提醒,不影響存檔。
- **AI 寫檔時** —— `.claude/hooks/enforce-conventions.cjs` 比對寫入前後的內容,
  只擋「這次新增」的違規;既有存量不影響。
- **對話時** —— 存檔時沒修掉的違規會列進對話,直到修好為止。
- **commit 時** —— pre-commit 檢查這次提交的檔案。

本機覆核:`node .tools/lint/lint.mjs <檔案或目錄>`。

檢查範圍:`.css` 全文、`.vue` 的 `<style>` 區塊與 template 的 arbitrary value
(`text-[#333]` 這種)。色票檔本身與 `.vue` 的 `<script>` 區塊不在範圍內。

### 報出來之後怎麼修

開發者說「修正」或「好」的時候直接動手,不必再問是哪一筆。
每一種的修法不同,而且**有兩條路的那幾種,方向選錯代價差很多**,
所以訊息裡已經各自指明了方向:

| 報的是什麼 | 怎麼修 | 要注意的 |
| --- | --- | --- |
| 頁面硬寫色碼 | 色票裡已有那個色值就改用 `var(--xxx)`;沒有就先到色票檔建一個變數再改 | 只是換寫法,畫面不會變 |
| 排序不符 | 不用動手,存檔或 `npm run sort:color` 會自動排好 | 只動順序,不動色值 |
| `hexToRgb()` 已不使用 | 掃全站找出它被用在哪幾種透明度,每一種各建一個 8 碼色票變數,使用端換過去,最後移除衍生變數 | 建幾個、叫什麼都要先查過全站,所以工具不自動改 |
| 已廢除的 rgb 衍生變數 | 掃全站找出它被用在哪幾種透明度,每一種各建一個 8 碼色票變數,使用端換過去,最後移除衍生變數 | 移除前先確認沒有地方還在讀它 |
| 值不是單純的色碼 | 把值改成色碼本身;要半透明就用 8 碼 | 值不是色碼時,那一筆連命名都不會被檢查 |
| 取碼建議為某個名字 | 為了避開同色系撞碼而微調的話可以不改;不是的話改成建議的名字 | 改名要同步所有使用端 |
| 取碼形狀與命名規則對不上 | 專案的取碼慣例本來就不同,改 `COLOR_SUFFIX_PICK`;是個別變數寫錯,改那個變數名 | 先看是整批還是個別 —— 整批就是設定的事 |
| 認不出色相前綴 | 專案配色有獨立色相,加進 `COLOR_HUES`;是個別變數用了語意名,改成帶色相的名字 | 加進清單要擺在彩虹順序裡對應的位置 |
| 混了兩種命名方式 | 把少數那一批改成大宗那一種(訊息會寫出大宗是哪一種) | 改名要同步所有使用端 |

**改設定與改命名是兩件事,不要弄反。** 分辨方式:
一整批變數都對不上就是設定的事(改一行設定,程式碼完全不動);
只有一兩個對不上才是那幾個變數命名寫錯(改名字,而且要同步所有使用端)。

改變數名的那幾種,要把用到它的地方全部一起改 ——
漏掉一處就是那裡的顏色變成沒有定義的變數,畫面上看不出錯誤,只是顏色不見了。
修完跑一次 `node .tools/lint/lint.mjs` 確認沒有殘留。
