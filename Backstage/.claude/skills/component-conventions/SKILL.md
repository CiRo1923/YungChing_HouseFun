# 元件檔案的形狀

**這份管的是共用元件目錄底下的 `.vue` 自己長什麼樣子** ——
它載入了什麼、開頭那幾行怎麼排。

頁面不在範圍內。頁面載入的東西依它要做的事而定,沒有固定的形狀;
元件是被重複放進畫面的零件,每一支長得一樣才好接手。

哪個目錄算共用元件,定義在 `.tools/lint/project-config.mjs` 的 `COMPONENTS_DIR`。
各專案的資料夾擺法不同,這份文件不另外抄一份路徑 ——
抄一份就會有對不上的一天,而對不上的時候規則會安靜地不再檢查任何東西。

## 〇、不是自足的元件,檔頭要列出它的搭檔

規則 `componentDeps`(擋)。**有些元件不是一個自足的資料夾** ——
彈窗、浮層這類要先掛在版面上才會顯示的,完整的一套是四塊:
元件本身、它讀的那個 store、掛在版面上會渲染它的那幾支容器,
以及它用到的轉場動畫定義在哪一支樣式檔。

只複製元件資料夾的話,搬過去不會報錯,而是安靜地少一半:

| 少帶了什麼 | 症狀 |
| --- | --- |
| 它讀的 store | import 得到、畫面也編譯得過,只是資料永遠是空的 |
| 掛在版面上的容器 | 元件**永遠不顯示** —— 要從「為什麼沒反應」一路追到「原來少了一個掛載點」 |
| 轉場的樣式檔 | 畫面都在、功能也正常,只是開關的當下直接跳、**沒有漸變** |

最後那一種最不容易發現:轉場的樣式常常收在一支共用檔案裡,
由進入點一次載入,不在元件的資料夾底下 —— 而動畫沒了不像壞掉,像是本來就沒做。

所以在元件主檔的檔頭列出那幾支:

```js
/* component-deps —— 複製這支元件時要一起帶走:
   <那支 store 的路徑>
   <掛在版面上的那幾支容器>
   <轉場樣式檔的路徑>
     <哪幾組轉場，以及少了它會怎樣> */
```

清單不必自己想,`npm run deps <元件>` 印得出來,規則的訊息也直接列出算好的。
工具算得準的有兩類:它讀的 store,以及它畫面區段裡 `<Transition name="…">`
寫死的那幾個名字對應到哪一支樣式檔。這兩類少列、或列了已經用不到的,都報;
容器那一類是人自己補的,工具不碰(「為了驅動這支元件而存在的容器」與
「剛好用到它的容器」從程式碼上分不出來,猜錯會把一堆使用端寫進搬移清單)。

動態綁定裡**引號內的字面**一樣算:`:name="isPopup ? 'a' : 'b'"` 兩個名字都讀得出來。
接變數或用樣板字串拼出來的名字才跳過 —— 那要執行起來才知道是什麼。
定義在元件自己資料夾底下的轉場也不必列,那本來就跟著元件走。

**清單跟著檔案走是重點** —— 複製過去的人不會回來跑來源專案的指令,
但他一定會打開那支檔案。

### 只帶這個專案用得到的那幾支,不要整批複製

**元件庫不是一個要整包裝進去的套件。** 那個專案用得到哪幾支就帶哪幾支,
之後要用新的再回來拿一支。

整批複製的代價不是檔案大小(沒有人用到的元件不會被打包進產物),
而是**那幾支從此要跟著維護**:

| 帶了沒在用的元件 | 會發生什麼 |
| --- | --- |
| 規範檢查掃到它們 | 每次跑檢查都要看一批與這個專案無關的訊息 |
| 樣式那一層歸專案 | 接手的人得去判斷那幾支的樣式要不要調,而它們根本不會出現在畫面上 |
| 元件庫更新時 | 同步工具照樣覆蓋它們,每次都在處理沒有人要的東西 |
| 接手的人打開元件目錄 | 看不出哪幾支是這個站真的在用的 |

**判斷方式是「使用端有沒有寫那個標籤」** —— 元件走自動註冊,
所以搜標籤名(`<MDatepicker`)就知道有沒有人用。搜不到就是沒用到。

#### 帶一支過去要連帶什麼

一支元件不是只有它自己的資料夾。`npm run deps <元件>` 印得出完整清單,
分成兩類:

```
<元件主檔的路徑>
複製這支元件時,下面這幾支要一起帶走(這份要寫進檔頭):
  <轉場樣式檔的路徑>
  <那支 store 的路徑>

它用到的別支元件
那幾個資料夾也要在,少帶的話畫面上那個位置什麼都不畫:
  <圖示那支元件的資料夾>/
```

第一類是上面那一節講的搭檔(store、容器、轉場樣式),要寫進檔頭。
第二類是**它畫面裡用到的別支元件** —— 那一類不寫進檔頭:
圖示那一支幾乎被每一支元件用到,寫進去只是在每個檔頭重複同一行。

少帶第二類的後果沒有徵兆:Vue 對解析不到的標籤只在開發模式印一行警告,
正式站是那個位置什麼都不畫 —— 圖示、箭頭、錯誤訊息就這樣安靜地消失。

#### 共用函式那一層:整支跟著來源,自己的另外開一支

元件 import 的共用函式(底線開頭的那幾支)**整支跟著來源**,
與元件的 `<script>` 是同一件事:元件在用它,所以它跟著元件一起更新。

**不要把這個專案自己的函式加進那幾支。** 加進去不會報錯,
而下一次整套更新會把整支覆蓋掉 —— 那幾個函式安靜地消失,
使用端變成 `Missing export`,而訊息只說某個名字不存在。

自己的另外開一支,檔名是「來源那一支 + `Project`」:

| 檔案 | 誰的 | 更新時 | 指紋 |
| --- | --- | --- | --- |
| `_prototype.js` | 來源 | 整支覆蓋 | 列入 |
| `_validation.js` | 來源 | 整支覆蓋 | 列入 |
| `_prototypeProject.js` | 這個專案自己的 | 不會被碰到 | 不列入 |
| `_validationProject.js` | 這個專案自己的 | 不會被碰到 | 不列入 |

這一支不必有任何人預留 import —— 用它的是這個專案自己的頁面與元件,
它們本來就是自己寫 import。(樣式那一層不一樣:那邊要有接點,
因為 import 那一行寫在元件的 `<script>` 裡,而那一段跟著來源覆蓋。)

**就地改了會被指紋抓到。** 那幾支與共用規則檔走同一套:
內容封存在 `.tools/lint/.rules-checksum.json`,`npm run rules:verify` 比對,
對不上就講出是哪一支。帶 `Project` 的那幾支不列入 —— 那是這個專案自己的,
與規則那邊的 `-project.mjs` 是同一條路。

擋的是「整支檔案的內容變了」,不是「多了哪一個函式」——
規則看得出元件用了哪幾支共用函式,看不出某一個函式是來源的還是這裡加的,
兩者在同一支檔案裡長得一樣。所以判斷方式是比對整支,
而正當的作法(自己開一支)本來就不會動到它。

### 清單寫的是來源的位置,不是目的地的位置

清單裡那幾條路徑是**這個專案**的擺法。複製到另一個專案時,
要放的是那個專案的對應位置,不是照著這串路徑建資料夾。

差別最常出現在最前面那一層:有些專案的原始碼收在一層資料夾底下,
有些直接放在專案根 —— 同一支轉場樣式,兩邊的路徑就差那一段。
其餘幾層(樣式目錄、共用那一層的名字)也各專案不同。

做法:打開目的地專案的 `.tools/lint/project-config.mjs`,
看它的樣式與 store 目錄實際填的是什麼,把檔案放到對應的那一層。
轉場樣式還要確認**進入點有載入它** —— 那支檔案不是被某支元件 import 的,
是整個專案載入一次,沒接上的話檔案在專案裡卻不會生效。

## 一、樣式一定要 import

**元件的樣式放在元件自己的資料夾裡,由元件自己載入。**

樣式收在元件資料夾底下的一層子資料夾(名稱定義在
`.tools/lint/project-config.mjs` 的 `MODULE_CSS_DIR_NAME`),
路徑用相對的 —— 那幾支就在旁邊,不必繞道 alias。

```vue
<script setup>
import './.css/variables.css'
import './.css/common.css'
import './.css/styleProject.css'
</script>
```

最後那一支是**留給接手的專案寫自己樣式的接點**,來源那一份是空的。
它排在最後,所以那個專案在裡面寫的值蓋得過來源的變數檔與版型檔;
而那一行 import 是來源就有的,整套更新之後它照樣在
(自己多加的那一行會被覆蓋掉,而樣式就安靜地不再輸出)。
空著是正常的,不要刪 —— 檔案不在的話建置會當場失敗。

**這個接點只有「從來源來的元件」才需要。** 那幾支的 `<script>` 跟著來源
整段覆蓋,所以自己在裡面加的 import 會消失 —— 接點是為了這件事存在的。

**專案自己寫的元件不需要它。** 那幾支不會被任何人覆蓋,要加樣式
直接改它自己的樣式檔、或在它的 `<script>` 多寫一行 import 就好。
加了接點不會報錯,只是多一支永遠空著的檔案,而下一個人看到會以為那是必要的。
(檢查那一條也只在來源跑 —— 在別的專案跑的話,他們自己寫的每一支元件
都會被報一筆,而那全是誤報。)

範例裡的資料夾名與檔名只是示意 —— **每個專案的樣式資料夾叫什麼、
一個模組拆幾支、元件底下有沒有再分一層(共用 / 平台 / 某個功能),都不一樣。**
實際的名稱看 `.tools/lint/project-config.mjs`;規則讀的也是那一份,
所以換一個專案時規則會跟著走,這份文件的範例不會。

**一支元件要帶走的東西在同一個資料夾裡。** 畫面、樣式、變數放在一起,
複製到別的專案時不會漏掉半邊,刪掉元件時也不會在別的目錄留下沒有人用的樣式。
樣式再收進一層,是為了讓元件資料夾第一眼只看到 `.vue` ——
一個模組常常有五六支 css,混在一起要找哪一支是元件得先略過一整片。

一支元件本來沒有自己的資料夾(直接放在分類資料夾底下)而現在要加樣式時,
**先幫它建一個同名資料夾,`.vue` 搬進去並改名 `Index.vue`** ——
名稱裡不會因此多一段(自動注入會略過 `Index` 那一層),使用端一行都不用改。

### 檔名首字大寫,主檔叫 `Index.vue`

**元件的 `.vue` 檔名一律首字大寫**(`Index.vue`、`Promise.vue`、`Oval.vue`)。
元件在別的畫面裡是一個**標籤**,而標籤的慣例就是大寫開頭 ——
檔名與標籤一致,看到標籤才知道去哪一支檔案找它。

**一個元件資料夾底下,那支「就是這個元件」的檔案叫 `Index.vue`**,
不要叫 `Main.vue`。同一層的其他 `.vue` 是它的子元件,各自取自己的名字。

```
mPopup/
  Index.vue      ← 這個元件本身
  Promise.vue    ← 它的子元件
  .css/
```

**自動注入會略過 `Index` 那一層**,所以使用端寫的是資料夾名本身
(`mPopup` → `MPopup`)。取名 `Main.vue` 的話,名字裡會多出那一段
(`MPopupMain`)—— 而那一段不帶任何資訊:讀的人看不出 `Main` 與 `Promise`
哪一個才是這個元件,得打開資料夾才知道。

**一支元件不要直接放在分類資料夾底下**(`common/mTab.vue` 那種)。
它遲早要加樣式或拆子元件,那時才建資料夾等於再改一次名、再動一次使用端;
而且直接放著的那支與資料夾形式的元件混在一起,看不出哪些是完整的模組。
一律建資料夾:`mTab/Index.vue`。

**改名會動到每一個使用端**(自動注入的名稱跟著檔名走),所以一次改完:
搬檔案、全專案換掉舊名稱、確認一個舊名字都沒剩。

**頁面的命名方向相反**(首字小寫)—— 頁面對應的是一個網址,不是標籤。
檔案系統路由的專案(檔名就是網址的一段)那裡還會放行連字號,
那是網址分隔字詞的寫法;元件不受影響,兩種專案都是大寫開頭的駝峰。
頁面那一側的完整規則見 [[page-conventions]]。

檢查:規則 `vueFileName`(擋)。

### 元件要有自己的資料夾

規則 `componentFolder`(擋)。**分類資料夾底下不要直接放 `.vue`** ——
一支元件遲早會有樣式、composable、拆出來的子元件,那時才建資料夾
就要動到每一個使用端(自動注入的名稱跟著路徑走)。

同一個模組底下好幾支是正常的(`mCard/Photo.vue`、`mForm/Input.vue`)——
那個資料夾就是元件本身,不是分類。分辨方式是資料夾名有沒有 `m` 開頭的形狀。

### 資料夾名要對得上它的 class

規則 `componentClass`(擋)。**共用元件的資料夾一律 `m` 開頭,
而且與它的組件 class 對得起來:**
資料夾 `mFigure` 對 `.m-figure`、`mSvgIcon` 對 `.m-svg-icon`。

這不只是好看 —— **模組 css 的 class 前綴就是從資料夾名推出來的**,
兩者對不上時,「只能寫自己那組 class」那條會推不出前綴而**整支檔案跳過檢查**:
不是報錯,是完全沒有訊息,那支元件的樣式從此沒有人在看。

名字不是 `m` 開頭的元件(功能取向的名字,例如一支叫「圖片」或「圖示」的),
要加樣式時連名字一起改成 `m` 開頭的形狀。**改名會動到每一個使用端**
(自動注入的名稱跟著資料夾走),所以一次改完:搬資料夾、全專案換掉舊名稱、
確認一個舊名字都沒剩。

跨模組共用的變數是例外:兩個以上的元件都要用的那幾支,放集中目錄
(`CSS_MODULES_DIR`)。放進其中一個元件的資料夾的話,另一個元件就得去
import 別人的檔案,而刪掉那個元件時會連帶弄壞它。

少了那一行,這支元件被放進別的頁面時樣式不會跟著來 ——
而它在原本那一頁看起來是正常的,因為同一頁的別支元件已經把樣式載進來了。
那種問題要換一頁才會發現,而且現場看起來像是「這一頁壞了」,
不像是「這支元件少載了一行」。

**這一條報違規,工具不自動補。** 工具看得出「這支沒有載入樣式」,
看不出這支元件的樣式該放在哪一支 css ——
自動補一行等於替開發者決定檔案要叫什麼、要不要跟別支共用。

### 轉手型元件不在這條的範圍內

有一種元件自己完全不寫 class:它把設定往下傳給另一支元件,
畫面與樣式都由被轉手的那支負責。

```vue
<template>
  <CommonCustomPopup :setClass="{ main: '--px-20' }">
    <slot />
  </CommonCustomPopup>
</template>
```

**那種元件沒有樣式可以載入**,所以規則不報它。硬要它載一支的話只有兩條路 ——
去 import 別人的樣式(刪掉那支元件時這裡跟著壞),或建一支空的樣式檔
(下一個人看到會以為裡面本來有東西被誤刪了)。兩種都比違規本身更糟。

**還有一種:寫了 class,但那幾個名字全案都沒有對應的樣式。**
外觀完全由使用端傳 `setClass` 決定,那幾個 class 只是掛載點
(給 JS 抓、給使用端當選擇器)。它同樣沒有樣式可載,所以也不報。

所以判準是**「寫出來的那幾個 class 有沒有人在定義」**,不是「有沒有寫 class」——
後者會把這種元件也報進來,而照著補的結果就是那支空檔案。

判斷看的是**靜態寫出來的 class**。動態綁定(`:class="setClass.main"`)不算 ——
那個值由使用端傳進來,樣式該由傳進來的那一方負責;
被註解掉的那一段也不算,那是死程式碼,不會產生任何樣式。

寫了自己的 class 就不是轉手型,照樣要載入樣式。

檢查:規則 `importOrder`。

## 二、import 依分組排列

順序是:**樣式 → 共用邏輯 → 共用函式 → 其他**。

```vue
<script setup>
import './.css/common.css'
import { useAnchor } from './.composables/useAnchor.js'
import { onScrollTo } from '@js/scroll.js'
import { computed } from 'vue'
</script>
```

一支檔案開頭那十幾行,每個人寫的順序都不一樣的話,
要找「這支有沒有載入某個東西」得整段看完。

**這一半不報違規,存檔時直接把順序排好。**
順序是機械式的規則,讓人照著訊息一行一行搬只是浪費時間,
而且搬的過程比工具更容易出錯。

分組的定義在 `.tools/lint/project-config.mjs` 的 `IMPORT_ORDER_GROUPS`
(每一組寫 `label` 與比對用的 `match`)。各專案的 alias 與資料夾命名不同,
寫死在規則裡的話,換一個命名的專案會把每一支元件都排錯。

自動排序有三個安全前提,少一個就可能改壞,所以工具做得保守:

| 前提 | 做法 |
| --- | --- |
| 只在連續的 import 區塊內重排 | 中間夾了任何一行別的程式碼就停在那裡,不跨過去 |
| 註解跟著它下方那一行一起搬 | 註解多半在講下面那一行是什麼,留在原地就指向了別的 import |
| 排序是穩定的 | 同一組的兩行維持原本的先後 |

分成好幾行寫的 import(路徑不在 `import` 那一行上)工具認不出來,
那種區塊整塊不動 —— 排錯一行的代價遠高於少排一次。

**只管組與組之間的先後,不管同一組裡面怎麼排。**
樣式那一組的組內順序(變數檔要排在版型檔之前)由模組樣式的規則在管,
兩條都去管組內順序的話,同一行會被指出兩種不同的修法。

### 元件那一行 import 不要寫

**元件由建置工具自動註冊,標籤直接寫就好:**

```vue
<template>
  <MPopup :config="{ mode: 'zoom' }" />
</template>
```

上面那支檔案的頂端**不寫** `import MPopup from '@components/mPopup/Index.vue'`。

名字由「資料夾 + 檔名」推出來,`Index` 那一層會被略過 ——
`mPopup/Index.vue` 就是 `MPopup`,`mForm/Input.vue` 就是 `MFormInput`。

自己寫那一行會壞三件事:

| 壞在哪 | 怎麼發生 |
| --- | --- |
| 名字會分岔 | 自動註冊的名字是固定的,手寫的可以取任何名字。同一支元件在這一頁叫 `Popup`、在那一頁叫 `MPopup`,搜尋使用端時會漏掉一半,而兩邊都能跑 |
| 搬檔案時斷得比較晚 | 自動註冊照著檔案現在的位置算,搬完就跟著變;手寫的那一行會指向一個不存在的位置,要到建置時才發現 |
| 兩份範本對不起來 | 有框架的那一份本來就自動註冊,另一份靠外掛做到同一件事(名稱規則刻意做成一樣)。一邊寫 import、一邊不寫的話,同一支元件的兩個版本永遠無法逐字對照 |

**兩種東西不在這條的範圍內,而且都一定要自己寫 import:**

- **掃描範圍外的 `.vue`** —— 點開頭的資料夾(示範檔那種)不會被自動註冊。
  那裡面的元件沒有名字可以被推導,不自己引入就完全載不到。
- **樣式** —— 它沒有「名稱」這回事,而且載入順序有意義(變數要先於版型)。

檢查:規則 `componentAutoImport`(擋)。它看的是「這一行 import 指到的檔案算不算元件」,
與「這支檔案要不要載入樣式」用的是同一份判準 ——
兩邊各認一次的話,會出現「某一種位置的元件這條管得到、那條管不到」這種落差。

這條要讀得到建置設定才知道 `@components` 這類 alias 指到哪裡。
一支建置設定都找不到的專案,它會整條略過,並列在「這幾條這次沒有作用」裡。

## 三、間隔用 css,不要靠字面空白

**兩個接連排在一行的元素之間要留空隙時,用 css(`gap` / `margin`),
不要靠原始碼裡的空白字元。** 這兩種寫法都不行:

```html
<b>甲</b> <b>乙</b>              <!-- 靠中間那個空格 -->
<span> </span>                   <!-- 空元素當間隔 -->
```

**Vue 編譯 template 時會把含換行的空白整個移除**(`whitespace` 的預設行為)。
所以中間那個空格只在「兩個元素剛好在同一行」時才留得住 ——
排版工具一折行就沒了,而原始碼看起來完全正常。
`<span> </span>` 更直接:那個空白在編譯當下就被移除,它從一開始就沒有作用。

要保留一個真的空白只有 `&nbsp;` 做得到,但那是**內容**,
不是排版 —— 文案裡本來就有的空格才用它。

規則 `spacerElement`(擋)。它抓的是「裡面只有空白的元素」這一種,
`<pre>` 與 `<textarea>` 除外(那兩種裡面的空白是內容,編譯器不會動)。

「兩個元素之間一個空格」那一種沒有規則在擋:畫面區段裡文字與元素混排是正常的,
分不出哪一個空白是刻意當間隔用的。那一種要靠自己看 —— 判斷方式是
「把這兩個元素折成兩行,畫面會不會變」,會變就是在靠空白排版。

### 空元素會被收合成自閉合,那是安全的

存檔時 `<div></div>` 會被自動收成 `<div />`。**在 `.vue` 裡這不會改變任何東西** ——
兩種寫法編譯出來的程式碼相同。

會出事的是另一件事:原生的 `.html` 檔(沒有經過 Vue 編譯的那種)
不接受非 void 元素自閉合,`<div />` 在瀏覽器眼中等於沒有關閉,
後面的兄弟節點會變成它的子節點。那一層不要寫自閉合。

**存檔沒有自動收合的話,是設定沒接上,不是寫法自由。**
那條規則在接上 prettier 的設定之後會被關掉,要自己寫回去、
而且位置要在 prettier 那一段之後 —— 放前面的話會被關掉,
設定看起來寫了卻沒有任何作用。實際的設定寫法在
`.claude/docs/規範工具-安裝到新專案.md` 的第六節。

## 四、事件一律接一支 `onXxx` 函式

規則 `eventHandler`(擋)。畫面區段的 `@事件` 綁的值只能是一支 `onXxx`:

```html
<!-- 正確 -->
<button type="button" @click="onDelete">刪除</button>
<button type="button" @click="onFieldPointerdown($event)">選取</button>

<!-- 錯誤:行為寫在屬性值裡 -->
<button type="button" @click="emits('delete')">刪除</button>
<button type="button" @click="keyword = ''">清除</button>
<div @click.self="isPopup ? onClose() : null"></div>
```

帶參數是可以的(`onFieldPointerdown($event)`)—— 位置資訊那類東西得傳進去。

**畫面區段講的是「長什麼樣子」,不是「做什麼事」。** 把行為寫在屬性值裡的話:

- 要知道這個按鈕做了什麼,得在一行 html 屬性裡讀一段程式
- 那段邏輯長出第二步時(送出前先驗證、關閉前先確認)沒有地方可以加
- 同一件事在兩個地方各寫一次,改的時候會漏掉一邊

收進 script 之後,畫面區段只剩「這個事件接到哪一支函式」,一眼看完。

**只有一行 emit 的包裝也算合規**,那正是它要的形狀:

```js
const onDelete = () => emits('delete')
```

這條不管那支函式裡寫了什麼,只看「是不是一支 `onXxx`」。

## 三之二、圖示的來源是 svg 檔,不是抄進程式碼的座標

**圖示的原始檔一律放 `_svg/`**(原始碼根底下那一層),由建置流程掃它、
產生一份 sprite,元件只引用名字:

```vue
<template>
  <MSvgIcon icon="icon_calendar" />
</template>
```

**不要把圖形座標抄進 `.vue` 或 `.js`。** 代價要到第二次才看得到:

| 做了什麼 | 後來會怎樣 |
| --- | --- |
| 加一支圖示 | 要手抄一次那一長串座標,而那串東西沒有人讀得懂、也校對不了 |
| 設計改了圖 | 要同時改原始檔與抄過去的那一份;漏掉一邊不會報錯,只是畫面上的圖形與設計稿對不起來,而兩邊的檔案看起來都有改到 |
| 圖示變多 | 那支元件膨脹成幾千行,每次打開都要捲過它們 |

**怎麼產生 sprite 兩種專案不一樣,但圖示放哪裡是一樣的。**
有框架的那一份靠框架的設定取得 sprite 的路徑與版本號;
純建置工具那一份要自己掛上外掛、自己提供路徑。
差別在「誰去產生、路徑從哪來」那一層,不在 `_svg/`。

換句話說:**看到某個專案的圖示元件裡有一大包座標,那是還沒接上建置流程的過渡狀態**,
不是可以照抄的做法 —— 照著加下去,那包東西只會越來越大。

檢查:規則 `svgIconSource`(擋)。真的必須把圖形寫進程式碼時
(隨資料變形的圖表、一次性的裝飾),在檔頭標
`lint-svg-inline-exempt: 理由` 放行。

## 四之二、`.composables/` 裡放什麼、怎麼命名

一支元件的邏輯拆出去時放這一層。**命名看它有沒有狀態:**

| 這支是什麼 | 檔名 | 為什麼 |
| --- | --- | --- |
| 有 `ref` / `computed`,或註冊了生命週期鉤子 | `useXxx.js` | 它只能在 setup 期間呼叫,`use` 就是在講這件事 |
| 純函式,沒有任何狀態 | 用它做的事命名(`formatInvoice.js`) | 它哪裡都能呼叫,也能單獨測 |

**`use` 是一個承諾,不是前綴慣例。** 在 Vue 裡看到 `useXxx`,讀的人會假設
它可能持有狀態、可能掛了生命週期鉤子,因此只能在 `<script setup>` 的
最外層呼叫。把純函式取名 `useXxx` 的話,下一個人不敢在事件處理器裡呼叫它 ——
而那正是純函式最常被呼叫的地方。

反過來也一樣:真的持有狀態的那支不叫 `useXxx`,會有人在按鈕的處理函式裡
呼叫它,那時註冊的生命週期鉤子掛不上去,而且不會報錯。

同一層底下兩種命名並存不是亂:看到 `useOcr.js` 與 `ocr.js` 放在一起,
一眼就知道前者有狀態、後者沒有。那個分辨本身就是要傳達的資訊。

**這一條沒有工具在擋。** 判準是「它有沒有狀態」,而工具只看得見
檔案裡有沒有出現 `ref` 這類字眼 —— 一支只是把另外兩支 composable 包起來的
檔案自己不會寫 `ref`,照字眼判斷會把它報成「不該叫 use」,而那是錯的。
會誤報的規則比沒有規則更糟:它會讓人開始忽略整份清單。

## 五、元件的對外介面:可以改值,不能多加

元件是整套從元件庫複製過來的,它有五個對外的介面:

| 介面 | 使用端拿它做什麼 | 方向 |
| --- | --- | --- |
| `config` | 傳設定(模式、格式、上下限) | 傳進去 |
| `defineEmits` | 照著那幾個名字綁 `@事件` | 發出來 |
| `defineExpose` | 拿著元件的 ref 直接呼叫(`inputRef.value.focus()`) | 拿出來用 |
| 變數檔 `:root` 的 css 變數 | 改值換掉顏色與尺寸 | 傳進去 |
| `setClass` | 加 class | 傳進去 |

前四個都由規則 `componentApiAdded`(擋)在看,**不可以自己多加**。
差別在「值能不能改」:

| 介面 | 改預設值 | 多加一個 |
| --- | --- | --- |
| `config` | 可以,那正是它存在的理由 | 不行 |
| `defineEmits` | **沒有值可以改** | 不行 |
| `defineExpose` | **沒有值可以改** | 不行 |
| 變數檔 `:root` 的 css 變數 | 可以,那正是它存在的理由 | **不在來源那幾支加** —— 來源沒有的變數連同讀它的樣式放 `<變體>VariablesProject.css` / `<變體>Project.css`,開之前先問設計者是不是該回報來源補 |
| 級距 class(`.--px-12`、`.--bg-green` 那組) | 可以 | **可以** —— 它只是把版型檔讀的那個中性名換成另一個值,名字照樣是來源那一個 |

後兩種連名字都不能動,而且它們壞掉的方式最安靜:

- 改了 `defineExpose` 的名字,使用端那一行呼叫一個不存在的東西 ——
  錯誤要到真的點下去那一刻才出現,而且只在那一條路徑上。
- 改了 `defineEmits` 的名字,使用端綁的那個 `@事件` **完全不會報錯**:
  Vue 對「綁了元件不發的事件」就是靜靜忽略,那一行從此不會被呼叫,
  而畫面、建置、規範檢查全部正常,只有那個功能不動。
  使用端那一側另有規則 `componentEmits`(擋)在看 —— 兩邊各守一半:
  這裡擋「元件亂改介面」,那裡擋「使用端綁了不存在的名字」。

其餘的界線三種都一樣:

| 做什麼 | 可以嗎 |
| --- | --- |
| 多加一個設定項、變數,或一個對外呼叫的名字 | 不行 |
| 把一個設定改成巢狀(`position` → `position: { x, y }`) | 不行,那是改結構 |
| 改元件的核心程式 | 不行 |

多加的那一個只有這個專案有,**元件內部不會讀它** ——
寫了不會報錯,什麼都不會發生,而下一個人會以為某個地方吃那個值。
下一次整套更新時它會被覆蓋掉,而覆蓋的當下沒有任何訊息。

改結構更隱蔽:元件內部讀的是原本那一個鍵,改成巢狀之後它拿到的是一個物件 ——
行為靜靜地變了,而程式看起來完全正常。

真的需要一個新的設定項、新的變數,或是核心行為要調整時,
那代表**元件本身要改**:回到元件庫去加 ——
加在那裡,每個專案都拿得到,而且元件內部真的會讀它。

規則靠一份名單比對(`.tools/lint/.component-api.json`)——
來源跑 `npm run rules:seal` 產生,跟著元件一起複製過來。
記的是**名字**不是內容:改值不會被報,只有多出來的名字會。

### 整套更新時,哪一部分會被覆蓋

上面那一節講的是「能不能改」,這一節講的是「改了之後,下一次從元件庫更新會不會被蓋掉」。
兩個問題的答案不一樣,而**每個專案都會在第一次同步的時候撞到這件事**:

| 元件的哪一部分 | 下一次整套更新 |
| --- | --- |
| `<template>` | **整段覆蓋**,結構要與元件庫那一份逐字相同 |
| `<script>` 的邏輯 | **整段覆蓋** |
| `<script>` 裡 `config` 的預設值 | 不覆蓋,那幾個值是這個專案自己的 |
| 樣式子資料夾底下那幾支(版型、變數、變體) | **一支都不覆蓋**,整層都是這個專案自己的 |
| 樣式那一層的 `styleProject.css` | **不覆蓋**,那是留給這個專案寫自己樣式的接點 |

**樣式不跟著元件庫走。** 元件庫那一份的樣式只是它自己驗證環境裡的樣子 ——
顏色、間距、圓角、字級、斷點,每個站都不一樣。照著覆蓋的話,
這個站的元件會變成另一個站的長相,而覆蓋的當下沒有任何訊息,
畫面就是突然長得不對。

分界線的理由是兩段東西回答的是不同的問題:

- `<template>` 與 `<script>` 是「這支元件怎麼運作」。修過的 bug 要靠它們流到
  每個專案,各改各的就收不到 —— 而收不到的時候不會有徵兆,
  只是那個專案一直帶著一個已經修好的問題。
- 樣式是「這個站長什麼樣子」,本來就該各自不同。
- `config` 的預設值與變數檔的值介於中間:**名字**跟著元件庫
  (多一個、少一個都由規則 `componentApiAdded` 擋),**值是各專案自己填的** ——
  那正是它們存在的理由,覆蓋掉的話每次更新都要重填一次。
  變數檔裡的級距(三個 `@screen` 區塊裡的 `.--px-12` 那組)則連名字都歸專案:
  它只是把既有的變數換成另一個值,版型檔照樣讀同一個名字。

所以設定同步工具的時候,元件資料夾底下的樣式那一層要整層排除。
排除的寫法看那個專案的同步工具怎麼設計,但「要排除」這件事是固定的。

### setClass 不給預設值

規則 `setClassDefault`(擋)。**樣式由使用端決定,元件不先替它決定。**

```js
// 不要 —— 元件先給了一份
const setClass = computed(() => {
  return {
    main: 'flex items-center',
    ...props.setClass,
  }
})

// 要 —— 列出有哪幾個位置可以傳,值留空
const setClass = computed(() => {
  return {
    main: '',
    header: '',
    ...props.setClass,
  }
})
```

元件給了預設值的話,使用端傳進來的那一份是**附加在後面**,不是取代:
兩份 class 同時存在,誰贏要看產出的先後順序。想拿掉元件那一份的人
會發現怎麼傳都蓋不掉,最後只能寫一個更強的選擇器或加 `!` ——
那是往上疊,而不是把決定權交回去。

**列出鍵、值留空字串是可以的**,那是在告訴使用端「這支元件有哪幾個位置
可以傳 class」—— 介面說明,不是樣式決定。拿掉的話模板裡的 `setClass.header`
會變成 undefined:畫面不會壞,但從程式上看不出有哪幾個位置。

元件自己的版型寫在它的樣式模組裡(那是 `.m-xxx` 那一組 class),
不是寫進 setClass 的預設值。

## 與相鄰規範的界線

元件會被好幾份規範同時看到,各自管的是不同的事:

| 規範 | 管什麼 |
| --- | --- |
| **這一份**(component-conventions) | 元件自己的檔案形狀:載入了什麼、開頭那幾行怎麼排 |
| tailwind-usage | 元件的 template 裡**寫什麼 class**:只留組件自身 class 與 `--modifier`,排版與尺寸寫進元件自己的 css |
| page-conventions | 元件與資料的關係:元件一律不能直接 import api,資料由使用它的頁面傳進來或寫進 store |
| import-alias | import 的**路徑**怎麼寫:離開自己資料夾的相對路徑改用 `@` alias |
| composable-order | `useXxxStore()` / `useXxxActions()` 這些**宣告**的順序,存檔時自動排 |

分辨方式:這一份看的是「import 哪些東西、排在第幾行」,
import-alias 看的是「那一行的路徑字串怎麼寫」,
composable-order 看的是「import 底下那些宣告的順序」。
