**比一比那兩頁的標題誤植 2026-09-30 那一版已經修好了** —— p45 現在麵包屑、

設計稿是桌面的「會員中心.pdf」。要看某一頁時用 poppler 轉圖:
`pdftoppm -f <頁> -l <頁> -png -scale-to 1600 <pdf> <輸出前綴>`。
要找某一頁在第幾頁:用 `pdftotext` 整份抽成文字,桌機版的主標題就在側欄第一項
「通知總覽」的前一行,手機版看麵包屑那一行(`首頁 會員中心 XXX`)。

**欄位缺漏已通知後端,等 api 更新後重新比對。** 不在這裡列清單 ——
api 會改(通知那支就補過一輪,`house` 還從 `HouseCard` 換成了 `BuyListItem`),
列了很快就與實際對不上。做某一頁之前,拿規格書那一節的介面對照表
與當下的 swagger 逐項對一次,那才算數。

**清單頁的功能按鈕一律前端寫死,不吃 api 的 `actions`。**
按鈕有哪幾顆、文字是什麼、順序怎麼排,都照規格書那一節的「功能」欄寫在元件裡。

這樣做的理由是**畫面的責任歸屬**:少一顆按鈕、順序不對、文字改了,
看程式碼就知道是哪一行;靠 `actions` 畫的話,同一個畫面在不同環境會長得不一樣,
而且查起來要先去看後端回了什麼。`ActionLink` 的 `key` 值域到現在仍未定義
(swagger 上三個欄位都是沒有說明的 string),靠它挑按鈕等於靠一個沒有人保證的值。

需要網址的按鈕(例如另開某個頁面)用路由組,不從 `actions.target` 取。

### 做之前要知道的共同慣例

這幾條是通知、密碼管理、帳號管理做下來定案的,新的頁面照著走就不必重新問。

**檔案怎麼切。** 一頁拆成三層:`Content.vue` 放驗證與送出、`Form.vue` 放欄位、
`popup/Complete.vue` 放成功彈窗的內容。彈窗元件的位置看它給誰用:
只有這一頁用就放 `_components/<頁面>/popup/`,整個大單元共用才放 `_components/popup/`。

**版面。** 內容元件自己帶寬度(桌機 `p:max-w-[400px]`)與手機的白底卡片
(`m:rounded-[10px] m:bg-[--white] m:p-[20px]`),頁面那一層不傳 class;
與標題的間距靠 `PageMemberCenterHeader` 自己的 `mb`,不要在使用端加 `mt`。

**兩邊對不上的時候照誰。** 規格書、桌機設計稿、手機設計稿、api 是四份來源,
彼此常有出入。裁決順序固定成下面這樣,不然每一頁都要重新討論一次,
而且同一種衝突在不同頁可能做出相反的決定。

| 對不上的是 | 照哪一邊做 | 一定要做的事 |
|---|---|---|
| 設計稿與規格書 | 設計稿 | 補進 `docs/會員中心-規格與設計待確認.pdf`,列出兩邊各寫什麼 |
| 桌機與手機的設計稿 | 桌機 | 同上,補進那份文件 |
| 畫面上的欄位與 api | api | 欄位有沒有、叫什麼由 api 決定;標籤上的字是文案,要問設計 |

**照設計稿做不等於那一份就是對的。** 補文件是這條規則的一半,不是附帶事項 ——
沒有補的話,規格書與畫面的差異就永遠停在那裡,驗收時才被發現,
而那時已經沒有人記得當初為什麼那樣做。

**api 回來的錯誤訊息放 store。** 那是 api 給的東西,不要用元件的 `ref` 保管再靠
props 往下傳 —— 放在那一層的 `apiResult`,要顯示它的欄位自己去讀
(`stores/member/center.js` 的 `password` 層就是這樣)。

**唯讀常數不要走 `storeToRefs`。** `readonly({...})` 既不是 ref 也不是 reactive,
`storeToRefs` 不會為它建立 ref,解構出來是 `undefined`,用到 `.value` 就當場丟錯。
直接從 store 取。

**另開物件明細頁一律用分頁名稱 `houseDetail`,不用 `_blank`。**
規格書多處寫「另開物件明細頁」。`_blank` 是每點一次就多開一個分頁 ——
一份清單連看十筆就是十個分頁。具名分頁只佔用一個,第二筆之後換掉那個分頁的內容。

**字串要一字不差。** 這個名稱目前寫在各個使用端,不是從某一處取來的;
拼成別的字就會各開各的分頁,而畫面上看不出異常,也沒有任何檢查會報。
新的清單頁要另開明細時,照抄 `houseSubscribe/content/card/Title.vue` 那一段。
