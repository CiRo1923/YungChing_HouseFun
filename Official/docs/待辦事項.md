## 換頁遮罩還沒在瀏覽器上看過

`plugins/pageLoading.client.js` 改由 Nuxt 的換頁生命週期驅動:
`page:start` 打開遮罩、`page:finish` 關上。在那之前是 router 守衛,
守衛只看得到「導航開始」,關的時機要每一頁自己負責,漏掉一頁就會一直蓋著。

程式面已經完成,**但還沒有實際在瀏覽器點過**。要看的是兩件事:

| 要確認 | 怎麼看 |
| --- | --- |
| 遮罩出現與消失是成對的 | 從列表點進物件明細、再用瀏覽器上一頁回來,遮罩不會殘留 |
| 取資料期間都在遮罩底下 | 明細頁的資料出現之前,畫面不會先閃一次空的版面 |

`page:start` 在頁面的 setup 開始時觸發,`page:finish` 在它(含 `await`)完成之後,
所以頁面取資料的那一段應該整段被蓋住 —— 這一點只有實際看過才算數。

### 做之前要知道的共同慣例

這幾條是通知、密碼管理、帳號管理做下來定案的,新的頁面照著走就不必重新問。

**檔案怎麼切。** 一頁拆成三層:`Content.vue` 放驗證與送出、`Form.vue` 放欄位、
`popup/Complete.vue` 放成功彈窗的內容。彈窗元件的位置看它給誰用:
只有這一頁用就放 `_components/<頁面>/popup/`,整個大單元共用才放 `_components/popup/`。

**版面。** 內容元件自己帶寬度(桌機 `p:max-w-[400px]`)與手機的白底卡片
(`m:rounded-[10px] m:bg-[--white] m:p-[20px]`),頁面那一層不傳 class;
與標題的間距靠 `PageMemberCenterHeader` 自己的 `mb`,不要在使用端加 `mt`。

**文案。** 會員中心的錯誤訊息與按鈕文字一律以 C203-1 規格書為準,
設計稿與規格書對不上時照規格書;欄位以 api 為準,設計稿的標籤只是示意。

**api 回來的錯誤訊息放 store。** 那是 api 給的東西,不要用元件的 `ref` 保管再靠
props 往下傳 —— 放在那一層的 `apiResult`,要顯示它的欄位自己去讀
(`stores/member/center.js` 的 `password` 層就是這樣)。

**唯讀常數不要走 `storeToRefs`。** `readonly({...})` 既不是 ref 也不是 reactive,
`storeToRefs` 不會為它建立 ref,解構出來是 `undefined`,用到 `.value` 就當場丟錯。
直接從 store 取。

### 勾選的機制

卡片的勾選方塊走 mForm checkbox 的 **group 模式**:整組共用 `name="messageIds"`、
`v-model` 綁同一個 `selectedIds` 陣列、每一顆用 `config.value` 標明自己是哪一筆。
`Card.vue` 自己不持有選取狀態,用 `defineModel` 把整份陣列轉給裡面的 checkbox ——
選取的是整份清單的狀態,不是單張卡片的。

**不能用 `isJoin`。** 那個設定會把陣列串成逗號字串,而 `BatchDeleteRequest.ids`
要的是 `string[]`;`MessageRecordItem.id` 本來就是 `string`,直接送出不必轉換。

批次列那一顆全選是 `mode: 'boolean'` —— 它是控制整組的開關,不是組內的一個選項。

### API

C 端只有兩支;`app/password-reset/*` 那三支是舊版 App 專用,**這裡不接**。

| API | 送出 | 回傳 |
|---|---|---|
| `POST /member/auth/password-reset/request` | `mobilePhone`、`verificationChannel` | `success`、`resetToken`、`expireAt`、`message` |
| `POST /member/auth/password-reset/confirm` | `mobilePhone`、`verificationCode`、`resetToken`、`newPassword`、`confirmPassword` | `success`、`requireRelogin`、`message` |

**驗證碼是 confirm 才驗的**,`request` 只發碼 —— 所以步驟 1 的「下一步」只能檢查格式。
**已定案:維持三頁,confirm 回驗證碼錯誤時導回步驟 1 並帶出錯誤訊息。**

發送限制與註冊驗證共用 60 秒冷卻 + 手機每日 / IP 每小時上限;
**超限回 400 帶 `message`**,沒有獨立的 429。
400 的欄位為 `code` / `message` / `details` / `failedAttempts` / `remainingAttempts` / `unlockAt`,
其中 `failedAttempts` / `remainingAttempts` 只在驗證碼錯誤時回傳 ——
程式就是以此判斷「該不該把人導回步驟 1」。

`verificationChannel` 傳字串 `sms` / `line`,值集中在 store 的 `verificationChannels`。

`developmentVerificationCode`:開發設定開啟時後端不寄簡訊、改由 200 回傳測試碼,
程式直接帶入驗證碼欄位(正式環境不回這個欄位,不必自己判斷環境),與 upgrade / 註冊同一套寫法。

錯誤呈現一律走 mForm 內建那套(`--error` 紅框 + `m-form-error`),比照 member 其他單元。
