以下六項是前端在串接時,從 swagger 判斷不出來、或缺少欄位的地方。 每一項列出位置、目前的狀況、對畫面的影響,以及需要後端提供什麼。 欄位能補說明的,請直接寫進 swagger 的 description 與 example, 之後接手的人也查得到。

2 搜尋訂閱清單的 limit 說明

會員中心服務(member)

1. 搜尋訂閱的 conditionPath 是什麼格式

位置 GET /api/{version}/member/subscriptions/search 回應的 SearchSubscriptionItem.conditionPath(string)
狀況 沒有說明也沒有範例。看不出它是完整網址、只有篩選條件那一段路徑,還是查詢字串。
影響 卡片上的「查看」要帶使用者回到當時的買屋搜尋結果。前端目前直接把這個欄位當網址使用; 格式不對的話,按鈕會連到不存在的頁面,而且要實際點下去才會發現。
需要 說明格式,並提供一筆實際的值(例如一組含縣市、總價、房數的條件)。

2. 搜尋訂閱清單的 limit 代表什麼

位置 GET /api/{version}/member/subscriptions/search 回應的 SearchSubscriptionListResponse.limit(integer)
狀況 沒有說明。分頁資訊另外在 paging 裡,所以它不是每頁筆數。 物件訂閱那支的對應欄位是 compareLimit(一次最多比較幾筆), 但搜尋訂閱沒有比較功能,推測可能是訂閱數上限。
影響 前端目前沒有使用。若是訂閱上限,畫面可能需要顯示或在達到上限時提示。
需要 說明這個數字的意思。

3. 通知的欄位裝的是什麼

位置 GET /api/{version}/member/notifications 回應的 NotificationItem
狀況 五個分頁共用同一個形狀,差別靠哪幾個欄位有值。除了 newListingCount 之外,其餘欄位都沒有說明與範例。判斷不出來的是: title 是不是整句標題、subtitle 放什麼、 tags 是哪一類的標籤。
影響 通知卡片的主體(標題、副標、標籤那幾行)還沒辦法做。
需要 兩筆實際的 response:一筆 category=0、一筆 category=2。 有了範例,上面三個欄位前端可以自己判斷,不必再逐一確認。

4. 物件卡 HouseCard 沒有 hfid

位置 HouseCard,用在 BuyObjectSubscriptionItem.house(物件訂閱管理) 與 MessageRecordItem.house(留言紀錄)
狀況 HouseCard 只有 id。通知那支用的 BuyListItem 同時有 id 與 hfid,兩者是不同的值。
影響 物件訂閱管理的「留言」要沿用買屋頻道的留言流程 (POST /api/{version}/buy/messages),它的 houseId 吃的是 hfid。HouseCard 給不出這個值,所以留言按鈕目前沒有接功能。
需要 在 HouseCard 補上 hfid;或說明 HouseCard.id 能不能直接當作買屋留言的 houseId。 CreateMessageRequest.houseId 本身也沒有說明,一併補上會更清楚。

5. 清單上的 actions 值域沒有定義

位置 ActionLink(key、title、target, 皆為 string),出現在通知、留言紀錄、各種訂閱清單的每一筆資料
狀況 三個欄位都沒有說明,key 會有哪些值也沒有列出。
影響 前端目前不使用:每張卡片有哪些按鈕、文字與順序,都照規格書寫在畫面上, 需要網址的按鈕由前端的路由組出來。這樣同一個畫面在不同環境不會長得不一樣。
需要 若這組欄位有預期的用途,請說明 key 的值域與 target 的格式; 若沒有,請確認前端可以不使用。

會員登入服務(member auth)

6. 忘記密碼的驗證碼沒有「可重送時間」

位置 POST /api/{version}/member/auth/password-reset/request 回應的 MemberAuthPasswordResetRequestResponse
狀況 回應只有 expireAt(重設用 token 的到期時間)。 註冊與會員升級那幾支發送驗證碼的 api,回應都有 resendAvailableAt。
影響 「重新發送」的倒數現在只能拿 expireAt 來算, 倒數的長度是 token 的效期,不是重送的冷卻時間,與另外兩條流程的行為不一致。
需要 在這支的回應補上 resendAvailableAt,格式與註冊、升級那幾支相同。
