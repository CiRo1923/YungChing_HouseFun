# 修問題要治根,不要往現行結構上疊

**優先順序:第 4 順位。** 低於「無法判斷就一律問」、「動手之前先讀一次規範」
與「規範自己也不能有兩份」,高於「註解與文件的寫法」,以及每一條命名與樣式規範。

低於「規範自己也不能有兩份」的理由:治根的做法如果會讓同一件事變成兩份,
那個「治根」本身就製造了新的問題 —— 先確認不會重複,再談怎麼治根。

也就是說 —— 治根的做法如果需要揣測任何邏輯,那就不能自己動手,
要先問開發者。「為了治根而自己補一段邏輯」是不允許的。

規範工具指出違規、或發現既有寫法有問題時,**提出的做法要處理成因**,
不是在現在的結構上再加一層讓它「看起來合規」。

疊上去的當下總是比較快,而且每一次都只多一點點 —— 多一個 prop、多一個 if、
多一支 wrapper。問題是它們不會消失:下一個人接手時看到的是十層,
而每一層當初都有各自的理由,於是沒有人敢動任何一層。

## 什麼叫「疊上去」

這些都是:

| 疊法 | 典型長相 |
| --- | --- |
| 多包一層 | 元件外面再包一個元件,只為了改一個樣式或補一個預設值 |
| 多一個 prop | 為了讓同一支元件應付第二種情境,加 `isXxx` 開關 |
| 多一個 if | action 裡加「如果是從 A 頁來的就……」 |
| 多一份狀態 | 兩邊資料對不上,就再存一份自己的 |
| 多一個特例 | 「這一支 api 比較特別,使用端自己處理」 |
| 補在下游 | 上游給的資料形狀不對,在每個使用端各自轉一次 |

共同的徵狀是:**改動集中在使用端,而成因在來源端沒有被碰到**。

## 治根長什麼樣

- 元件為了第二種情境要加開關 → 先看那是不是**兩個元件**,或那段樣式該進 CSS 模組的 modifier
- action 要加「誰在呼叫」的判斷 → 那段邏輯屬於**頁面**,不屬於 action(見 [[store-conventions]])
- 兩邊資料對不上 → 修**資料的來源**,不是在兩邊各自轉
- 每個使用端都在做同一件轉換 → 那件事應該發生在**上游一次**
- 同一段判斷出現第三次 → 抽出來,但抽的是**判斷本身**,不是再包一層呼叫

## 做不到的時候

治根有時要動的範圍比當下的任務大很多(改元件介面、改 api 回傳形狀、
改 store 分層)。那不是硬做的理由,但**也不是默默疊上去的理由**。

照 [[no-assumption]] 的做法:**說明成因、給出治根與權宜兩條路各自的代價,
讓開發者決定**。選了權宜的話,把「為什麼現在不治根、之後要怎麼處理」
寫進 `.claude/docs/待辦事項.md`,不要只留一行 `// 暫時` 就過去。

## 為什麼特別寫成一條

規範工具只看得到「這一行違規」,看不到「為什麼會寫成這樣」。
照著提示逐行改,很容易改出「規則過了,但結構更糟」的結果 ——
那正是規範想避免的事情本身。
