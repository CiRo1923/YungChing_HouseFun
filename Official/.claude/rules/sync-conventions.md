# 規範複本一律整包同步

`.claude/rules/`、`.claude/skills/`、`.claude/hooks/`、`.tools/lint/` 這幾處
是另一份規範的複本。它們的價值在於「兩邊真的一樣」——
一旦這邊自己改過,就再也說不出「同步完成」是什麼意思:
差異到底是對方新增的,還是這邊當初改的?沒有人分得出來,
而分不出來的那一天起,同步這件事就失去意義了。

所以做法固定成三件事。

## 一、每一次都重新讀來源的每一支檔案,比對整份內容

用來源目錄的實際內容跑一遍,不要憑記憶、不要用上一輪的比對結果、
也不要看檔案的修改時間判斷「這支沒動過」。
對方可能在上一個指令之後才改,而修改時間相同不代表內容相同。

不要自己列一份「要比對哪幾支」的清單 —— 那份清單會過期,
而漏掉的那一支不會有任何徵兆,只會讓人以為「那邊還沒做」。

**比對的是整份檔案的內容,不是只看匯出的名稱。**
只比名稱的話,這幾種差異一個都看不到,而它們都會改變行為:

| 看不到的差異 | 為什麼名稱比對掃不到 |
| --- | --- |
| 同名的函式裡面換了判斷 | 名字一樣,規則已經不同 |
| 常數、正則、清單的內容變了 | 那些沒有匯出,名稱清單裡不會出現 |
| 提示訊息與註解改了 | 那是給人看的說明,改了要跟著更新 |
| 新增或刪掉的私有輔助 | 不匯出,所以看不到 |
| 測試案例的內容變了 | 自我驗證跟著規則走,少了就測不到新規則 |

做法是整個目錄逐支比對整份內容,把有差異的每一支都打開看過,
再決定它屬於「要整包取用」還是「要回報的差異」。

## 二、整包覆蓋,不要自己修改

取來源的版本就是整份取用。**不要**在取用之後做這些事:

- 改名字讓它接得上這邊的舊叫法
- 把這邊多出來的函式接回檔尾
- 補一段判斷讓它適用這邊的寫法
- 為了讓它能跑而調整呼叫端

那些都是「自己改寫」,做了就回到上面說的分不出差異的狀態。
取用後接不上的話,那是要回報的事實,不是要就地解決的問題。

## 三、設定值以外的差異一律先問

唯一可以跟著這個專案調整的是**設定值**(目錄位置、檔名前綴、
色相清單、取碼規則那類),而且**改之前要先向開發者確認**。

其餘的一律先問:規則的判斷邏輯、函式與規則代號的名稱、檔名、
這邊多出來或少掉的檔案。把差異列出來,說明各自的後果,
等開發者決定 —— 不要自己選一個看起來合理的做下去。

## 不在複本範圍內的幾支

這幾支是這個專案自己的,**已經確認過保留**,不必跟來源比對,
也不要在每一輪同步時重新列出來問一次:

| 檔案 | 為什麼是這個專案自己的 |
| --- | --- |
| `.tools/lint/project-config.mjs` | 設定檔本身,值就是要跟著專案走 |
| `.tools/lint/diff-output.mjs` | 比對建置產物的 CSS,來源沒有這個指令 |
| `.githooks/pre-commit` | 這個 repo 底下並排放著多個專案,要依 staged 路徑的第一層分派;來源假設 repo 根就是專案根,整包取用會去 repo 根找工具而整支掛掉 |
| `.claude/hooks/sync-conventions.cjs` | 這條規則的提醒本身 |
| `.claude/rules/sync-conventions.md` | 這份文件 |
| `.claude/rules/` 底下記錄待辦的那幾份 | 待辦是這個專案的進度,不是規範 |
| `.claude/skills/` 底下講專案功能的那幾支 | 錯誤頁、彈窗、路由、共用元件同步、日期選擇器、相片排序、捲軸留白那些,講的是這個專案怎麼運作 |

判斷方式:**它講的是「規範怎麼寫」還是「這個專案怎麼運作」?**
前者要跟來源一致,後者是這個專案自己的內容,來源本來就不會有。

新增這類檔案時補進上面這張表 —— 沒補的話,下一次同步會把它當成
「要回報的差異」重新列出來,而那個問題上一次已經回答過了。

## 自動提醒

寫入複本範圍內的檔案時,`.claude/hooks/sync-conventions.cjs` 會把上面三件事
帶進對話。它只提醒、不阻擋 —— 擋下來只會讓人想繞過。
