# 無法判斷就一律問

**這是權限最高的一條,優先度高於其他所有規則。**
任何一條命名、樣式、結構的規範,與這條衝突時都以這條為準。

規則之間的完整順序是:

| 順位 | 規則 | 管什麼 |
| --- | --- | --- |
| 1 | **無法判斷就一律問**(這一份) | 判斷不出來時停下來問,不自己創建邏輯與檔案 |
| 2 | **規範自己也不能有兩份** | 動規範系統之前先確認沒有另一處在講同一件事 |
| 3 | **修問題要治根** | 處理成因,不在現行結構上再疊一層 |
| 4 | **註解與文件的寫法** | 寫出來的文字怎麼寫 |
| 5 | 各類命名與樣式規範 | api、store、頁面、css 各自的寫法 |

兩份規則的做法衝突時,順位小的優先。順位 2 高於 3 的理由是:
治根的做法如果會讓同一件事變成兩份,那個「治根」本身就製造了新的問題。

**邏輯一律不自己創建。** 判斷條件、預設值、錯誤處理、資料轉換 ——
只要是「需求沒說、程式碼也看不出來」的,就停下來問,由開發者決定。

那些寫錯了看得出來,揣測出來的邏輯寫錯了**看起來會像是對的**,通常要到上線後才被發現。

看到規範沒寫、程式碼看不出來、或兩種做法都說得通的情況,**停下來問**,
不要選一個看起來合理的往下做。這包含:

- 規範沒涵蓋到的情況
- 規範涵蓋到了,但套用在這個案例上有兩種讀法
- 工具報了違規,但照著改會影響行為(不只是換寫法)
- 文件與實際程式碼對不上,不知道哪邊才是對的

## 問的時候要寫清楚三件事

**一、確切位置。** 讓對方不用自己找:

- 哪一頁(檔案路徑)
- 哪一個 store、哪一層
- 哪一個 function
- 哪一個變數、哪一個欄位

寫「某個頁面的資料有問題」對方無從判斷;寫
「`views/member/Setting.vue` 的 `onSubmit` 裡,`setting.OptionItem` 這個欄位」
才知道在說什麼。

**二、選項與各自的代價。** 把看到的兩三種做法、各自會動到什麼、
代價是什麼列出來,讓對方一眼能決定。不要只丟一句「請問要怎麼做」。

**三、建議的方向。** 不是只把問題丟回去 —— 說明你判斷哪一種比較合適、為什麼。
對方可以不採納,但要有個起點。

## 三個「不要」

| 不要 | 說明 |
| --- | --- |
| **不揣測邏輯** | 需求沒寫、程式碼看不出來的判斷條件,不要用「應該是這樣」補上。 |
| **不自行建立邏輯** | 不要為了讓流程看起來完整而補一段沒人要求的處理(預設值、fallback、錯誤轉導、資料轉換)。 |
| **不自行建立檔案** | 不要順手新增元件、store、工具檔、設定檔。要多一支檔案就先說,由開發者決定放哪、叫什麼。 |

## 判斷不出來時的做法

**直說「這個我判斷不出來」,列出選項與各自的後果,然後停下來等回答。**
不要假裝有把握,更不要寫一版然後補一句「暫時這樣」。

猜錯的代價不對稱:猜對省一次提問,猜錯要回頭改邏輯、改元件、
改每一個使用端,而且中間那段時間大家都以為它是對的。

## 常見的岔路(這些一律要問)

- 某個狀態沒定義時要顯示什麼、要不要擋
- API 回傳空值 / 失敗時的行為
- 邊界值算不算(含頭含尾、0 要不要視為未填)
- 既有的死程式碼是要重寫還是刪掉
- 樣式或欄位「看起來沒用到」是預留還是遺留
- 兩份寫法不一致時,哪一份才是對的

## 例外

只有**這四種**可以直接動手,其餘一律先問:

1. 使用者明確說了要怎麼做
2. 純機械式的改名 / 搬移,不改變任何行為
3. 修正明確的錯誤(語法錯誤、拼字錯誤)
4. 規範工具指出的違規,**而且照著改只是換一種寫法、不影響行為**

第 4 種要看清楚:**同樣是工具報的違規,有兩種情況,做法相反。**

| 情況 | 例子 | 做法 |
| --- | --- | --- |
| 照著改只是換寫法 | 命名改一個字、路徑改用 alias、色碼改成變數、宣告換位置 | 直接改 |
| 照著改會動到行為 | 資料要從頁面搬進 store、api 回傳形狀要變、元件介面要改 | 先問,說明成因與代價 |

分辨方式:**改完之後,程式做的事情有沒有變?** 沒變就直接改;
只要牽涉到「資料放哪裡」「什麼時候取」「壞掉的時候怎麼辦」,那就是行為,要先問。
