# 建置指令與環境

規則 `buildCommands`(擋)。

## 三個環境，三個固定的指令名

| 指令 | 送去哪裡 | 讀哪一份設定 |
| --- | --- | --- |
| `npm run dev` | 開發（本機起 dev server） | `.env.dev` |
| `npm run deploy` | 測試機 | `.env.deploy` |
| `npm run build` | 正式機 | `.env.build` |

**名字是固定的，不可以換成 `publish`、`release`、`prod`、`stage` 那類。**

## 為什麼名字不能各專案自己取

打 `npm run build` 的時候，要能**當場確定**那是正式機而不是測試機。

每個專案各取各的名字，唯一的辦法是每次先打開 `package.json` 讀一遍。
而漏讀一次的代價是**送錯環境** —— 那件事不會報錯，
指令跑完一樣顯示成功，要等有人發現正式站出現測試資料才知道。

交接的人、剛進專案的人、半年後回來的自己，都要能不查就知道。

## `--mode` 與指令名要同名

```json
"dev": "vite --mode dev",
"deploy": "vite build --mode deploy",
"build": "vite build --mode build"
```

兩邊同名才看得出這個指令讀的是哪一份環境設定。不同名的話，
改了某個環境的設定卻沒有生效時，沒有人會想到是這裡 ——
他會去找建置工具的快取、找 CI 的設定，最後才發現指令讀的是另一份。

**建置工具沒有 `--mode` 這個旗標時，這一項不適用。**
有的專案靠環境變數帶，有的工具根本沒有這個概念 ——
規則只在指令裡實際出現 `--mode` 時才比對它，不會為了一套專案沒在用的慣例報違規。

## 環境設定三份要成套

`.env.dev`、`.env.deploy`、`.env.build`。

缺一份不會報錯：建置時那些變數讀到的是空的，
結果是網域或金鑰變成預設值，而**畫面看起來一切正常** ——
要到打 api 失敗、或更糟的是打到了錯的環境，才會發現。

**完全不用 `.env.<環境名>` 這套的專案，整項略過。**
規則的判斷是「這個專案已經有其中一份了嗎」—— 一份都沒有就是它用別的方式帶設定，
那是它的選擇，不是缺漏。

## 其他指令不受這條約束

檢查、排序、安裝掛鉤、產生報表那些想叫什麼都可以。
這條只認上面那三個名字對應到哪三個環境。

## 裝到新專案時

新專案是**從零開始**的：三個指令一個都還沒有，規則會直接報出來。
那不是誤報，是安裝清單的其中一項 —— 把三個指令補上、
環境檔照著建，這條就過了。

指令的內容（用哪個建置工具、部署那一步做什麼）由專案自己決定，
規則不碰 —— 它只看名字與環境對不對得起來。
