# 顏色變數規範:集中定義、命名一致、彩虹排序

所有顏色一律定義為 CSS 變數,依「誰會用到」分成兩種色票檔,都放在色票目錄底下。
目錄位置與檔名前綴都定義在 `.tools/lint/project-config.mjs`
(`COLOR_CSS_DIR` 與 `COLOR_CSS_PREFIX`)—— 這份文件用 `<前綴>` 指稱那個字,
不寫死,因為每個專案叫什麼不一樣。

| 檔案 | 放什麼 | 怎麼載入 |
| --- | --- | --- |
| `<前綴>.css` | **跨分組共用**的色 | 全域載入,程式一開機就可用 |
| `<前綴>{分組名}.css` | **只有那個分組要用**的色 | 由該分組的版型檔載入 |

前綴是 `color` 的專案,這兩種就是 `color.css` 與 `colorMember.css`。

分組指的是「有自己一套配色的區塊」——例如一個獨立的活動、一個問卷模組。
專案有哪幾個分組由專案自己決定,檔名就是前綴加上分組名。

新增或調整顏色時:**跨分組共用的**只改共用那一支(全域生效);
**只有一個分組要用的**改那個分組的檔案。共用色不在分組檔裡重複定義 ——
重複定義之後,改了一邊沒改另一邊,兩個分組的同一個顏色就會不一樣。

**頁面(.vue / .css)不得硬寫色碼**,一律改用 `var(--xxx)`。

## 一、命名規則:`--{色相}-{後綴}`

### 色相前綴

`red` / `orange` / `yellow` / `green` / `blue` / `purple` / `gold` / `white` / `gray` / `black`

這也就是色票檔裡的排列順序(紅 → 橙 → 黃 → 綠 → 藍 → 紫 → 金 → 白 → 灰 → 黑)。
順序不對時存檔會自動排好,不必手動調整。

- 依實際視覺色相歸類,**不看既有(可能錯誤的)命名**。
  例:`#ced4da` 是淺灰藍 → `--gray-cdda`(不是 orange);`#0e6f86` 偏青 → 仍歸 green/blue 取其近者。
- `#000` / `#fff` 用語意名 `--black` / `--white`。

### 後綴取碼規則

| 情況 | 取法 | 範例 |
| --- | --- | --- |
| 一般 6 碼 hex | 取第 **1,3,5,6** 碼 → 4 碼後綴 | `#e2001a` → `--red-e01a`;`#c20016` → `--red-c016` |
| 灰階(r=g=b,如 `#9e9e9e`) | 取第 **1,2** 碼 | `#9e9e9e` → `--gray-9e`;`#383838` → `--gray-38` |
| 3 碼 hex(`#abc`) | 直接用該 3 碼 | `#999` → `--gray-999`;`#ddd` → `--gray-ddd` |
| 帶透明度(8 碼 `#rrggbbaa`) | 基礎後綴 + `-` + **alpha 兩碼** | `#87b90d66` → `--green-8b0d-66`;`#e5e5e54d` → `--gray-e5-4d` |
| 純黑 / 純白帶透明度 | 沒有基礎後綴,只留 **alpha 兩碼** | `#0000001a` → `--black-1a`;`#ffffff4d` → `--white-4d` |

> 括號標注取碼位置的由來,例 `#e2001a`(1,3,5,6)= e,0,1,a = `e01a`。

**alpha 前面那個連字號是必要的** —— 黏在一起會分不出哪幾碼是色碼、哪幾碼是透明度:
`--gray-334d` 到底是「`#33334d` 這個顏色」還是「`#333333` 加三成透明」?
加了 `-` 就沒有歧義。純黑白本來就不帶色碼後綴,不會混淆,所以維持原樣。

alpha 兩碼的換算是 `Math.round(透明度 × 255).toString(16)`。
常用對照:`0.1→1a`、`0.2→33`、`0.3→4d`、`0.4→66`、`0.5→80`、`0.7→b3`。

- **衝突處理**:若同色系兩色算出相同後綴,微調取碼位置使其在同色系內唯一。
- **透明色一律用 8 碼 hex,不要 `-rgb` 衍生變數**。`rgba(var(--xxx-rgb), 0.4)`
  這種寫法會被規則抓出來,改用對應的 8 碼 hex 變數(`var(--black-1a)`)。
  `hexToRgb()` 的 PostCSS 機制還在,但只為既有程式碼保留,不要新增呼叫端。

## 二、排序規則

**大分類依彩虹**:紅 → 橙 → 黃 → 綠 → 藍 → 紫 → 金 → 白 → 灰 → 黑。
**每一色類內部由淺到深**(以 WCAG 相對亮度,亮者在前)。
同一個顏色的不同透明度,**透明度低(看起來較淺)的在前**。
色系之間空一行。

註解不會被排序打散:`/* 紅色 */` 這種色系標頭會固定放回該色系的最前面,
其他說明性的註解跟著它下方那一行變數一起移動。

## 三、使用規範(頁面端)

```css
/* 不要在 .vue / .css 硬寫色碼 */
color: #e2001a;
background: linear-gradient(180deg, #e2001a, #c20016);
box-shadow: 0 4px 16px rgba(0, 0, 0, 0.1);

/* 改用變數 —— 透明色走 8 碼 hex 的變數,不用 rgba() */
color: var(--red-e01a);
background: linear-gradient(180deg, var(--red-e01a), var(--red-c016));
box-shadow: 0 4px 16px var(--black-1a);
```

Tailwind arbitrary value 同樣用變數:`text-[--red-e01a]`、`bg-[--white]`、`border-[--gray-cdda]`。

### 例外:JS 物件內的顏色

送往外部平台的 JS 設定物件(例如地圖套件的樣式設定、傳給第三方服務的訊息格式)由該平台
渲染,**CSS 變數在此無效**,必須是實際 hex 字串。此類顏色允許保留 hex,
但應集中為 JS 常數而非散落各處。

**判斷依據是「這段是不是 CSS」,不是「這是不是第三方套件」。** 用普通 CSS 去覆蓋
第三方注入的 DOM(例如地圖元件產生的那些 class)仍然是 CSS,色票變數在那裡讀得到,
照規範走;只有真的當成 JS 物件傳出去的才是例外。

## 四、自動檢查

規則 `color` 與 `colorFile`,判斷邏輯在 `.tools/lint/lint-core.mjs`,
四個時機跑的是同一份判斷:

- **存檔時** —— 編輯器與開發伺服器會即時檢查,違規逐筆印在終端機。只提醒,不影響存檔。
- **AI 寫檔時** —— `.claude/hooks/enforce-conventions.js` 比對寫入前後的內容,
  只擋「這次新增」的違規;既有存量不影響。
- **對話時** —— 存檔時沒修掉的違規會列進對話,直到修好為止。
- **commit 時** —— pre-commit 檢查這次提交的檔案。

本機覆核:`node .tools/lint/lint.mjs <檔案或目錄>`。

檢查範圍:`.css` 全文、`.vue` 的 `<style>` 區塊與 template 的 arbitrary value
(`text-[#333]` 這種),以及白名單內的建置設定檔 —— 那裡的 `boxShadow` 之類設定
最後會變成產物裡的 CSS 宣告,寫死色碼同樣是違規。

**色票檔本身也在範圍內,只是規則不同**:它本來就該有顏色,所以「不得硬寫色碼」對它豁免;
但「命名」「排序」「不要用 `rgba(var(--x-rgb), …)` 與 `hexToRgb()`」這幾條照樣檢查 ——
那裡正是這些寫法的原生棲地。

一般的 `.js` 不在範圍內:雜湊、識別碼、二進位遮罩裡的 hex 會全部變成誤報。
要納入新的建置設定檔就加進那份白名單,不要把 `.js` 整類拉進來。
