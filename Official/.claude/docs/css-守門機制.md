# 規範守門機制（本專案實作）

這份說明的是「**規範怎麼被自動檢查**」——有哪些規則、判斷什麼、接到哪幾個觸發時機。
判斷邏輯只有一份，五個時機共用它。

其他三件事各自有專門的文件，這份不重複寫：

| 想知道什麼 | 看哪裡 |
| --- | --- |
| **怎麼裝到另一個專案** | `.claude/docs/規範工具-安裝到新專案.md` |
| **某一類程式該怎麼寫** | `.claude/skills/`：`api-conventions`（api）、`store-conventions`（store 與 actions）、`page-conventions`（頁面）、`color-naming` 與 `css-module-variables`（css）、`import-alias`、`composable-order` |
| **跨規則的共同前提** | `.claude/rules/`：無法判斷一律問、修問題要治根、規範不能有兩份、註解與文件的寫法 |

## 檢查的規則

範圍那一欄寫的是**通則**（頁面目錄、元件目錄、api 目錄…），不是實際路徑 ——
每個專案的資料夾擺法不一樣，這份文件會跟著規範系統整套複製到下一個專案，
寫死路徑的話搬過去就是錯的敘述。**實際路徑看 `.tools/lint/project-config.mjs`**，
規則讀的也是那一份，所以換專案時規則會跟著走，這份文件不必改。

Store 規則的判斷寫在 [.tools/lint/rules-store.mjs](../.tools/lint/rules-store.mjs)，規範內容見共用文件庫的 `Store規範.md`。

`storeScope` 的例外清單目前有 `common` / `project` / `popup` / `json` / `lineLiff` / `petFair`（跨頁面基礎建設）。`storeLayer` 的層名取頁面檔名首字小寫（`Detail.vue` → `detail`），分類資料夾不佔一層；同一個頁面群裡有好幾支同名頁面時，那幾支才用分類資料夾多包一層分辨（`missions.detail` / `pets.detail`）。可用 `/* lint-store-layer-exempt: 理由 */` 放行那份資料確實屬於別的層的情況。

API 規則的判斷寫在 [.tools/lint/rules-api.mjs](../.tools/lint/rules-api.mjs)，規範內容見共用文件庫的 `API規範.md`。

api 目錄底下可以再分一層「服務」（各自的網域與 token），那一層要有自己的 `.config.js`——規則靠它分辨「服務層」與「單純分類」：有設定檔的那一層就是資源，沒有的話資源仍是檔名。

`apiScope` 的資料夾清單是**動態讀頁面目錄的第一層**，不是寫死的——新增資料夾時規則會自動跟上。不屬於任何資料夾的檔案寫進設定檔的 `STANDALONE_APIS`（`.tools/lint/project-config.mjs`），目前有 `project`（跨資料夾共用）、`json`（靜態 json 不打後端）、`petFair`（獨立功能）。

要加例外時改的是那份設定，不是規則檔裡的 `ALLOWED_STANDALONE`——後者是規則從設定長出來的，改它等於在規則裡寫死這個專案的東西，換一個專案就是錯的。store 那邊同理，設定項是 `STANDALONE_STORES`。

`projectName` 是**全站規範**，不屬於 CSS，判斷寫在 [.tools/lint/rules-global.mjs](../.tools/lint/rules-global.mjs)，由 `lintFile` 一起合併輸出。

### 只有這個專案需要的規則

上面那張表是**每個專案都拿到的**那一套。只有這個專案需要的規範，放在 `.tools/lint/rules-project.mjs`——有就讀、沒有就跳過，本專案目前沒有這支檔案。

那支檔案匯出檢查函式、標題、提示與驗證案例，形狀與別的規則檔一樣。兩個硬性要求，自我驗證會擋：**代號以 `project:` 開頭**（不加的話有一天會與共用的規則撞名，而那時同一個代號底下有兩種判準）、**每一條都要有案例**（規則與案例放在同一支檔案，改了規則忘了改案例才不會沒有人發現）。

分辨要放哪邊：**別的專案會不會也想要這一條？** 不會就放專案自己那支——硬加進共用的那一套，不需要的專案會被迫每次標例外。

來源整套覆蓋時不會動到這支檔案（它不在來源裡），所以專案自己的規則不會被蓋掉。

### `ruleTampered`：共用規則只有來源能改

規則是每個專案拿到的同一套。在某個專案改了它，那個專案的檢查結果就與別人不同——而且改動會在下一次整套更新時被蓋掉。蓋掉的當下沒有人會發現，只知道「本來不報的東西怎麼又開始報了」，而原因在幾個月前的另一次更新裡。

來源封存每一支共用規則的指紋（`npm run rules:seal`），清單跟著規則一起複製出去；非來源專案比對不符就報。**來源那邊不比對**——規則本來就在那裡長，每改一行都報一次等於不能工作。

指紋涵蓋 `.tools/lint/` 底下所有 `.mjs`，**含產生指紋的那一支自己**——排除它的話，改掉它就能讓比對永遠通過，那是一道只有知道的人才找得到的後門。

不列入的是專案自己的那幾支：設定檔 `project-config.mjs`（每個專案的值本來就不一樣），以及**檔名以 `-project.mjs` 結尾的**——專案自己的規則 `rules-project.mjs`、專案自己的小工具都是這個形狀。它們本來就不在來源裡，列入的話會被報成「多出來的」，而那個專案一點問題也沒有。

用檔名判斷而不是讓專案自己填一份排除清單：清單交給專案填的話，把共用規則填進去就繞過了整道保護，而從設定看不出那是繞過還是正當的一項。改名想繞過也不行——原本那一支會被報成「被刪掉了」。

違規掛在 `project-config.mjs` 這一支上報，不是每一支被改過的檔案各報一次——後者在整套沒更新的情況下會一次洗出十幾筆，訊息裡本來就列得出是哪幾支。

沒有指紋清單時不比對，那是還沒封存過的狀態；一律報「每一支都被改過」只會讓人把整條規則關掉。

要調整檢查行為的正當路徑有兩條，都不必動共用規則：設定值改 `project-config.mjs` 的既有項目，只有這個專案要的規範寫進 `rules-project.mjs`（代號以 `project:` 開頭）。

### `ruleCrashed`：規則自己壞掉了

這一條抓的不是程式碼的問題，是**檢查工具自己的問題**：某一條規則執行時拋了例外。

單條規則壞掉不會讓整個檢查停擺（其他規則照跑），但**它會被報出來**。安靜地跳過的話，那條規則從此不抓任何東西，而畫面上顯示的是通過——一顆看不見的未爆彈，通常要到幾個月後有人發現「這種寫法怎麼一直沒被擋」才會查到。

最常見的成因是**搬了函式卻沒搬它的 import**。那種漏接在載入時不會報錯，要執行到那一行才爆；而很多規則的路徑是條件式的（例如「色票檔有衍生變數時才走到」），平常跑全專案掃描根本到不了。

預防的那一道在 ESLint：`.tools/**/*.mjs` 在檢查範圍內（見 `eslint.config.mjs`），`no-undef` 會在**存檔當下**就指出是哪一個名字沒有定義。收到 `ruleCrashed` 時先跑 `npx eslint .tools/` 看，多半一眼就找得到。

兩道合起來：ESLint 在寫的時候擋，`ruleCrashed` 在跑的時候兜底。

### `configItem`：專案設定檔只改值，不新增項目

專案設定檔是規則與專案之間的介面：一邊是規則（換專案完全不動），另一邊是這個專案的資料夾怎麼擺。**介面的形狀由規則那一側決定**——規則讀什麼，設定檔才有什麼。

每個專案只做一件事：把既有的項目改成自己的值。自己多加一項的話，沒有任何規則會讀它——不是「設定沒生效」的錯誤訊息，是完全的安靜，而下一個人看到它會以為某條規則吃這個值。這條抓的就是那種項目：**設定檔匯出的名稱，規範系統底下沒有任何程式碼用到它**（說明文件不算「用到」，那是在介紹它）。被設定檔自己拿去組出別的項目的中介值不算，那種拿掉之後別的項目就算不出來。

反方向（刪掉或改名）不必抓：規則 import 的名稱不存在時，那條規則會直接壞掉，本來就看得見。

**來源專案只提醒，不擋。** 規則與設定在來源那邊是一起長出來的，先加設定、再改規則去讀它，中間必然有一段「還沒有人用」的狀態——擋下來只會讓人繞過檢查。判斷方式是拿設定裡的 `SOURCE_PROJECT_NAME` 與這個專案的 `PROJECT_NAMES` 比對，對得上就是來源；每個專案安裝時本來就要把專案名稱換成自己的，換掉之後兩者自然對不上。全專案檢查的開頭會講出這次算哪一種身分。

### `projectName`：不寫死專案名稱

**這條只管規範系統自身**——檢查工具、skills、hooks，以及規範自己的說明文件（`.claude/docs/`）。那些檔案會整批複製到下一個專案，名稱寫進去之後搬過去就變成錯的敘述，而且從內容看不出哪幾句是「本專案限定」。網域、路徑、識別字一律走環境變數或設定檔。

**原始碼不在範圍內。** 頁面標題、頁尾品牌名、會員條款裡的品牌名稱是內容本身，不是被寫死的設定——那些檔案不會複製到別的專案，寫出品牌名才是正確的。一併納入的話，清單會被大量正當文案淹沒，真正該擋的那幾筆反而看不到。

**名稱清單要人維護**（`project-config.mjs` 的 `PROJECT_NAMES`，填名稱本身即可，中間的空格與連字號由規則自己處理），**只填本專案自己的名稱**——把別的專案名稱列進來，等於把別人的專案名寫死在這支檔案裡，正好是這條規則要防的事。

### `absolutePath`：不寫某一台機器上的路徑

**這條的範圍比上面那條大，原始碼也算。** 絕對路徑跟品牌名稱性質不同：它不是內容，是只在某一台開發機上成立的位置——每個人的專案擺法不同，作業系統也不一定一樣（磁碟機代號 vs 家目錄），別人 clone 下來直接壞掉，build 也不會過。寫在原始碼裡同樣是錯的，所以不限縮。

<!-- lint-absolute-path-exempt: 這一段在說明規則抓哪幾種路徑形狀，必須寫出那些形狀本身 -->

四種形狀都抓：磁碟機代號、家目錄／掛載點、`file://`、往上跳三層以上的相對路徑（那已經跳出專案根，指到的是別的專案）。

### `plainText`：不用 emoji 與裝飾符號

寫給人讀的文字裡不放 emoji，也不放拿來裝飾的符號。客戶會看到這些文字——畫面上的文案、交付的文件、交接時對方讀的註解——那是正式的工作文件，不是聊天訊息。

要強調就把理由寫出來。圖示只說「這裡很重要」，理由才說得出「為什麼重要、不照做會怎樣」。

| 不要 | 改成 |
| --- | --- |
| `⚠️ 這裡必須同時滿足三個條件` | `注意：這裡必須同時滿足三個條件` |
| `✅ 正確的寫法` / `❌ 錯誤的寫法` | `正確的寫法：` / `錯誤的寫法：` |
| `🔧 已自動排序` | `已自動排序` |

**兩種情況不算裝飾，規則不抓：**

一、**工具在終端機印出來的狀態**（通過、違規、擋下、提醒各一個記號）。那不是文件，是程式跑起來當下的回饋；一排訊息裡要能一眼分出哪幾筆有問題。

放行的條件有兩個，要**同時**成立：這個字元在狀態記號的清單裡，而且它寫在字串裡。要印出來的訊息一定包在引號中，註解與文件裡的則不是。所以 `print('⚠ 有 3 項前提不存在')` 放行，而 `// ⚠️ 這裡要小心` 會被抓。

**只有印出來的那一份合法**——同一個記號寫進註解或文件就是裝飾，照樣抓。印出來的那一份幫讀者分辨狀態；寫在註解裡則沒有那個作用，只剩「這裡很重要」的語氣。

**「在引號中」不是通行證。** 不在清單裡的符號寫在字串裡一樣會被報：`print('🔧 已自動排序')` 照抓，因為那個圖示沒有幫讀者分出哪一筆有問題，只是把一句話裝飾了一次。要放行一個新的狀態記號是規則本身要改，把它加進清單。

二、**對照表裡表示「變成」的箭頭**（`舊名稱 → 新名稱`）。那是資訊本身，不是裝飾——換成文字反而讓整欄對不齊、更難讀，所以不分場合都放行。

三、**畫面上給使用者看的文字**（元件與頁面 `<template>` 裡的內容）。那是內容本身：標題、按鈕上的字、提示語——要不要放一個圖示由設計與文案決定，不是規範系統要管的事。

**畫面區段裡的註解不在此列，照樣抓。** 那是寫給接手的人讀的，與程式碼旁邊的註解沒有兩樣——放行的話，同一句話只要寫進畫面區段就繞過了整條規則。

範圍是規範系統整層（每一種檔案，說明文件尤其是——那一層會整批複製到下一個專案），加上原始碼裡的 `.css`、`.js`、`.ts`、`.vue`。這一條在原始碼裡看的是註解，而註解就出現在那幾種檔案裡。

放行有兩種方式，用途不一樣：

| 方式 | 用在什麼情況 | 影響範圍 |
| --- | --- | --- |
| 檔頭標 `lint-plain-text-exempt` 並寫明理由 | 這一份檔案本身要寫出那些符號 | 那一份檔案 |
| 設定 `PLAIN_TEXT_EXCLUDED_DIRS` 列出目錄 | 整個目錄的文字不是這個團隊在寫的：整包複製進來的元件、產生器吐出來的檔案 | 那幾層底下的全部檔案 |

判斷方式：**這裡的文字，我們改得動嗎？** 改得動就是要修；真的改不動（下次更新會被整包覆蓋）才列進設定。設定比對的是從專案根算起的路徑，不是資料夾名——別處另一個同名資料夾照常檢查。排除的範圍會列在檢查結果的開頭，那幾層的其他檢查照常適用。

兩份清單分別是 `rules-global.mjs` 的 `TERMINAL_MARKS`（狀態記號，只在字串裡放行）與 `ARROW_MARKS`（箭頭，一律放行）。確實需要保留別的符號時（例如在說明規則本身），檔頭標 `lint-plain-text-exempt` 並寫明理由，整份跳過——標記要寫在註解裡，程式碼裡的字面值不算。

範圍是原始碼與規範系統自身。專案自己的文件那一層有自己的檢查工具，見下面說明。

### `selfContained`：讀者不必離開現在這一段

「同上」「同 2」「參考第三節」這類寫法不行——它們把資訊留在別的地方，強迫讀者跳走。

讀的人多半帶著一個具體問題來，從搜尋結果或某一節的中間開始看，沒有「上一段」可以參照。被送去另一個地方之後，還要自己找回原本在看什麼——跳兩次就放棄了。

同一件事出現在很多地方時，挑一個地方寫完整，其餘各自寫一段短的。內容重複完全沒問題，重複遠比指涉好：同一句話在三個地方各寫一次，讀者三次都讀得懂；寫成「同上」則是三個地方都讀不懂。

**指向別的檔案不算**（「完整清單見某某文件」）。那是有用的補充，前提是這一段自己要講的已經講完了。這條抓的是「指向同一份文件裡的別處」。

中文句子裡詞與詞之間沒有空格，所以規則不能要求這些詞前面一定是標點——「這段的規則同上」的「同上」前面就是一個中文字。有誤報風險的用前置或後置排除處理：「相同 2 個條件」「不同 3 種寫法」的「同」屬於前面那個詞，「同理心」也不算。

### 專案自己的文件：這一套工具完全不碰

專案根的 `docs/` 放的是寫給這個專案的內容（規格、對照表、會議紀錄那類）。那一層**有自己的檢查工具**，檢查連結有效、側欄一致、排版慣例那些文件專屬的事。

兩套工具掃同一層的話，判準會各自演化：同一份文件被兩邊報不同的東西，修好一邊另一邊還在報，最後兩邊都被忽略。文件的事歸文件的工具管。

另一個理由是誤報：那一層本來就要寫出這個專案叫什麼、檔案實際放在哪、引用一段不合規範的範例程式碼。拿程式碼的規則去檢查只會產生整片誤報。

那一層用什麼格式寫也不受限制——排除是整層的，與副檔名無關。

排除寫在 `lintText` 的入口，不是各條規則各擋一次——那是所有規則的唯一匯合點，擋在那裡才保證每一條都適用，日後新增規則也不必記得再加一次。

**寫那一層的時候，文字規範仍然要照著做**（不用 emoji、不用「同上」、只寫邏輯不寫贅述、讓非工程師讀得懂）。沒有這套工具擋，不代表可以隨便寫。

規範系統自己的說明文件不放那裡，放在 `.claude/docs/`，照樣受全部規則檢查。

### `moduleScope`：一支模組 css 只寫自己那組 class

class 前綴由**元件的資料夾名**推出（`mForm/` → `m-form`、`mDatePicker/` → `m-date-picker`）——也就是樣式那一層**外面**的那個資料夾，不是樣式資料夾本身。該元件底下的選擇器只能是這個前綴、`--modifier`（含 `p:` 這類斷點前綴）與 `j` 開頭的 JS hook class。

這條同時管**變體收斂**：組件放在某模組的子資料夾底下，它就是那個模組的變體，class 要跟著母體走——`mItem/` 底下出現 `.m-switch-item-header` 會被抓，應該是 `.m-item-switch-header`。只搬資料夾而 class 不動，「看到 class 就能找到檔案」就失效了。

推不出模組名（資料夾不是 `m` 開頭駝峰）時整支跳過，不亂猜。

### `variable`：三個面向

**一、命名對齊 tailwind utility**，不要記第二套詞彙：

| 不要寫 | 要寫 | | 不要寫 | 要寫 |
| --- | --- | --- | --- | --- |
| `-width` | `-w` | | `-radius` / `-border-radius` | `-rounded` |
| `-height` | `-h` | | `-font-size` / `-text` | `-text-size` |
| `-padding` | `-p` | | `-line-height` | `-leading` |
| `-margin` | `-m` | | `-letter-spacing` | `-tracking` |
| `-background` | `-bg` | | `-z-index` | `-z` |

**二、級距用實際數值，不要 `sm` / `md` / `lg`**。`--size-md` 看不出到底多大，要翻到 Variables 檔才知道；而且要加一個中間值時整組都得改名（sm 和 md 之間塞不進東西）。`--size-40` 直接讀得出來。

**三、斷點**——分成兩條檢查：

| 檢查 | 抓什麼 |
| --- | --- |
| 該分卻沒分 | Variables 檔 `:root` 內的尺寸值沒有拆斷點 |
| 分了但不成套 | 有 `-pc-X` 卻缺 `-tablet-X` 或 `-mobile-X` |

**判定看的是「值」不是名字**：

| 要分斷點 | 不用分 |
| --- | --- |
| 帶長度單位且不是 0：`15px`、`1.5rem`、`50%`、`10vw` | 顏色（`var(--色票)`、hex、`transparent`、`inherit`） |
| | `0` / `0px` / `auto` / `none` / `100%`（滿版用 `w-full`，不繞變數） |
| | 無單位數字：`z-index`、`line-height` 比例、`font-weight` |
| | 值是 `var(…)`——那是斷點對應或狀態切換，不是原始值 |

只看 Variables 檔的 `:root`。modifier 的具體值（`&.--px-24 { --x-px: 24px }`）由各 `@screen` 段落對應，本來就不必在名字裡帶斷點。確實只有單一斷點需要時，檔案內標 `/* lint-breakpoint-exempt: 理由 */` 放行。

### `theme` 的黑名單依據

`tailwind.config.js` 的 `theme` 底下（非 `extend`）是整組覆寫，內建 key 會全部消失——寫了不報錯，但產不出任何 CSS。

| 設定 | 本專案的值 | 因此不存在 |
| --- | --- | --- |
| `screens` | `m` / `t` / `tm` / `pt` / `p` / `pMin` / `pMax` / `mLandscape` / `notsupport` / `firefox` / `IE` | `sm:` `md:` `lg:` `xl:` `2xl:` |
| `fontSize` | `vmp` / `vmt` / `vmm` / `vmmls` | `text-xs` ~ `text-9xl` |
| `boxShadow` | `content` / `default` / `default-light` | `shadow-sm` ~ `shadow-2xl`、`shadow-inner`、`shadow-none`（`shadow` 本身可用） |
| `fontFamily` | **未覆寫** | —（`font-sans` 等正常可用） |

**「本專案的值」那一欄不必人工維護**——工具直接讀 `tailwind.config.js`（值寫在別支檔案再 import 進去時會追過去），所以改了設定，提示訊息會自己跟上。上表是給人看的對照，不是判斷依據。

需要人維護的只有「因此不存在」那一欄（`project-config.mjs` 的 `TAILWIND_THEME_OVERRIDES.dead`）——那列的是 **tailwind 自己的預設值**，與專案無關，換專案不必改，升級 tailwind 大版本時才要調。

### `themeNaming`：重新定義的值不要再用 sm / md / lg

`theme` 整組覆寫之後，那一類的內建值全部消失，專案要自己重新定義一套。重新定義時又寫成 `sm` / `md` / `lg`，等於把剛拿掉的問題原樣搬回來：

- 看到 `shadow-md` 仍然不知道那是多深的陰影，要翻設定檔
- 要在 `sm` 與 `md` 之間加一階時，整組都得改名，連帶每一個使用端
- 它跟 tailwind 內建的同名值長得一模一樣，接手的人分不出這是專案自訂的還是內建的

改用說得出用途的名字（`content` / `default`）或實際數值。

判準與 `variable` 的「級距不用 `sm` / `md` / `lg`」是**同一份清單**（`lint-core.mjs` 的 `T_SHIRT_SIZE`），差別只在檢查的位置：`variable` 看 CSS 模組的變數與 modifier，`themeNaming` 看樣式設定檔。

範圍是**專案根目錄的設定檔**（`tailwind.config.js`，以及值拆出去的那一支）。`extend` 底下不算——那是補充，內建值都還在，用 tailwind 自己的級距名是正常的。

確實要沿用既有命名時，在檔頭標 `lint-theme-naming-exempt` 並寫明理由，整份跳過。

### `variable` 的斷點檢查

`--x-pc-px` 存在時，`--x-tablet-px` 與 `--x-mobile-px` 也必須有——漏一個那個斷點會靜靜讀不到值。只看同一支檔案；確實只有單一斷點需要時，在檔案內標 `/* lint-breakpoint-exempt: 理由 */` 即可放行。

### `tailwind` 的判定方式

採**已知清單**而非反向排除——寧可漏抓罕見 utility，也不要把專案自訂 class 誤報。

- 合法：`m-` 開頭的組件 class、`--` 開頭的 modifier／狀態、`j` 開頭的 JS hook class
- 判定前先剝掉 variant 前綴（`p:` / `hover:` / `group-hover:`），`bg-[url(a:b)]` 這種中括號內的冒號不切
- 動態綁定 `:class` 只取引號包住的字面 class，變數與三元運算無法靜態判讀
- `<!-- -->` 註解掉的 template 是死程式碼，不算違規
- 同一個 class 在一支檔案內只報一次
- 只看 `<template>`，`<style>` 內的 `@apply flex` 不算

另有兩項無條件自動修正：**色票檔排序**、**空的規則區塊移除**（`.foo {}` 產物不會有輸出）。

`.vue` 的 `<script>` 區塊不擋——送往 LINE Flex 等外部平台的色值必須是實際 hex，CSS 變數在那裡無效。

## 五層觸發

| 層 | 檔案 | 時機 | 對誰生效 |
| --- | --- | --- | --- |
| dev server | [.tools/lint/dev-server-plugin.mjs](../.tools/lint/dev-server-plugin.mjs)（各框架自己接，職責見下方） | 跑開發伺服器時存檔 | 所有人 |
| 編輯器 | [.vscode/settings.json](../.vscode/settings.json) 的 `emeraldwalk.runonsave` | 存檔（沒跑 dev 也生效） | 所有人 |
| AI 寫檔 | [.claude/hooks/enforce-conventions.cjs](../.claude/hooks/enforce-conventions.cjs)（PreToolUse，**阻擋式**） | AI 助理寫入前 | **只有 AI 助理** |
| 對話 | [.claude/hooks/css-guard-prompt.cjs](../.claude/hooks/css-guard-prompt.cjs) | 每次送出訊息 | 只有 AI 助理 |
| commit | [.githooks/pre-commit](../.githooks/pre-commit) | `git commit` | 所有人 |

**唯一會擋下違規的是 AI 寫檔那層，而它只對 AI 助理生效。** 用助理的人寫錯會被擋下來，手動改的人只看到提醒——同一份規範，兩種人的強制力不一樣。

那一層擋的也只是**這次改動新增的違規**，既有存量照樣放行，否則 AI 連碰都不能碰既有檔案。

commit 那層目前只提醒，但**有一種情況會擋：規則自己的驗證沒過**。兩者的差別在於「擋下來之後做得到嗎」——既有的違規存量清不完，擋下來只會逼人繞過整個 hook；而規則壞掉是一兩行的事，當場修得完，何況它不修的代價是「規則安靜地不再檢查任何東西，而畫面顯示通過」。

**存量清乾淨之後，commit 那層要改成違規也擋**（把 `exit 0` 改成累計失敗再離開）。那時它擋不到任何人，卻能讓「新寫的程式碼一律合規」變成事實。改的時候不要留跳過的旗標——一個「緊急時可以跳過」的開關會在幾週內變成「每次都加」。

那支 hook **不含任何規則判斷**，全部委派給 `.tools/lint` 引擎（`lintText`）。原本是五支各自寫判斷的 `enforce-*.cjs`，規則有兩份實作遲早會漂移，而且漂移時的現象是「AI 被擋但人存檔通過」，不會有人發現。

### dev server 那層要長什麼樣

**每個專案的建置工具不一樣**（Vite、Nuxt、webpack），掛外掛的方式也不同，所以這一層**沒有一支可以直接複製的檔案**。但它的職責在每個專案都一樣，只有四件事：

| 做什麼 | 為什麼 |
| --- | --- |
| 監看存檔 | 用 watcher 而不是模組圖的更新事件——後者只對「已經進模組圖」的檔案觸發，存到當前頁面沒載入的元件時完全沒有反應 |
| 去抖 | 一次存檔會觸發好幾個事件（格式化、自動修正、編輯器的原子替換各寫一次檔），不去抖的話同一份警告連印三四次 |
| 執行 `node .tools/lint/guard-file.mjs <檔案>` | 那支是為這件事設計的介面：吃一個檔案路徑，自動修正該修的，把結果印到標準輸出 |
| 把輸出原樣印出來 | 訊息長什麼樣由引擎決定 |

**這一層絕對不要 import 引擎的內部函式。** 自己組一份「排序 + 檢查 + 印出」的話，引擎調整介面時那支外掛會在載入當下就失敗——而那一層平常沒有人盯著它有沒有活著，要到有人主動測試才會發現。

範圍（哪些副檔名要檢查）也讀 `.tools/lint/project-config.mjs` 的 `SCANNABLE_EXTENSIONS`，不要自己寫一份清單：漏掉一種，那類檔案存檔時就完全不會被檢查，而且沒有任何徵兆。

編輯器那層需要擴充 `emeraldwalk.RunOnSave`（已列入 [.vscode/extensions.json](../.vscode/extensions.json)）。沒裝也不影響開發——dev server 執行中時 vite 外掛會做同樣的事。

## 對話層的行為

存檔層是單向的，接不到回答。一份待處理清單是兩層之間的接力棒——它放在哪由檢查引擎決定（`.tools/lint/shared.mjs` 的 `PENDING_CACHE_FILE`），兩層都讀同一個設定，不各寫一份：

- 存檔時有違規 → 檔名寫進清單
- 每次送出訊息 → 重新檢查清單裡的檔案 + 工作區有改動、且在可檢查副檔名範圍內的檔案（範圍由 `.tools/lint/project-config.mjs` 的 `SCANNABLE_EXTENSIONS` 決定）
- **只有該檔已經沒有違規時才會被移除**——所以不修就會一直被列出來

清單每一輪都會出現（不去重），但**不會主動彈問句**。說「修正」時直接動手。

## 改規則時

判斷邏輯依類別分在 [.tools/lint/](../.tools/lint/) 底下：CSS 相關在 `lint-core.mjs`，其餘各有一支（`rules-global.mjs`、`rules-api.mjs`、`rules-store.mjs`、`rules-page.mjs`、`rules-code.mjs`）。每一條規則就是一個 `check` 函式，加進所屬檔案的 `CHECKS` 陣列，由 `lint-core.mjs` 的 `lintText` 合併輸出。

**專案特定的設定（目錄位置、名稱清單、色票位置）一律寫在 [.tools/lint/project-config.mjs](../.tools/lint/project-config.mjs)，不要寫進規則裡**——那是換一個專案唯一需要改的檔案，規則檔寫死之後搬過去就是錯的。

**改完一定要跑 `npm run test:css`。** `lint:css` 通過只代表「現在的程式碼沒有違規」，不代表「規則還有效」——改壞一條 regex 之後全案照樣通過，那條規則會靜靜失效。自我驗證是反過來測工具本身：餵違規進去必須被抓、餵合法寫法進去必須放行，每條規則至少兩個案例。
