# 規範工具:安裝到新專案

這份是**安裝步驟** —— 把這套規範與檢查工具搬到另一個專案,照著做到可以執行為止。

想知道「有哪些規則、怎麼運作」看 `.claude/docs/css-守門機制.md`;
想知道「某一類該怎麼寫」看 `.claude/skills/` 底下對應的那一份。

裝完會得到什麼:寫程式的時候,不符合團隊規範的寫法會在**存檔當下**就被指出來,
而不是等到 code review 或上線後才發現。

---

## 〇、開始之前要先問清楚的事

**這一節要在複製檔案之前走完。** 下面每一項在各專案都不一樣,
而且設錯的後果不是報錯,是**一整批誤報**或**一整條規則安靜地不再檢查**——
兩種都很難從結果反推原因。

判斷不出來就問開發者,不要先猜一個往下做。工具能自己偵測的那幾項,
裝好之後跑一次全專案檢查就會告訴你設錯了,但先問過比較省事。

| 要確認的 | 怎麼看 | 設錯會怎樣 |
| --- | --- | --- |
| 這個專案的網址從哪裡來 | 看路由是自己寫一張表(路由檔裡逐筆寫 `path`),還是由檔案位置決定(頁面目錄擺什麼檔名,網址就是什麼) | 填成自己寫路由表、而實際是檔案系統路由的話,那一批頁面會整批被要求把檔名改成駝峰 —— 而那種專案的檔名就是網址,照著改等於改網址,既有的連結與搜尋引擎收錄的位置都會失效 |
| 頁面、store、api、色票、CSS 模組各在哪個目錄 | 看專案的資料夾結構 | 那一類規則完全掃不到檔案,結果顯示通過 |
| 資源資料夾在第一層還是第二層 | 頁面目錄的第一層資料夾底下,有沒有直接放 `.vue`。有就是第一層,沒有就是第二層 | 每一支 api 與 store 都被報「對不上資料夾」 |
| 做不做響應式 | CSS 模組裡有沒有 `@screen` 或寬度 media query | 不做卻設了斷點:每個尺寸值都被要求拆三份;做了卻沒設:該分斷點的不會被報 |
| 色票命名帶色相還是語意名 | 打開色票檔看變數名:`--red-e01a` 是帶色相,`--title-color` 是語意名 | 設成帶色相而實際是語意名時,每一個變數都被報「認不出色相前綴」,排序還會把整份檔案重排 |
| 透明度兩碼怎麼接、取碼取哪幾碼 | 看色票裡帶透明度的變數:`--gray-e566` 是直接相接,`--gray-e5-66` 是用分隔符 | 那一類的取碼檢查完全沒有結果,而畫面上看起來全部通過 |
| 有沒有並行載入的共用函式 | 搜尋專案有沒有把多個請求一起發出的那支函式 | 沒有卻留著設定:每一頁的 onMounted 都被報 |
| 有沒有「文字不是這個團隊在寫」的目錄 | 找整包複製進來的元件、產生器吐出來的檔案 —— 那種地方出現圖示不是寫的人選的,下次更新還會被整包覆蓋 | 不列進 `PLAIN_TEXT_EXCLUDED_DIRS` 的話,那幾層每次都報一批改不了的違規,而一直報改不了的東西會讓整條規則被略過 |
| 有沒有自動產生、又會進版控的清單 | 找元件或 store 的自動注入清單(建置工具在背景監看原始碼目錄,看到新檔案就登記進去) | 不列進 `GENERATED_FILES` 的話,每跑一次規則自己的驗證,那份清單就多出幾行指向探測檔的登記 —— 探測檔早就刪了,那幾行會跟著 commit 擴散出去,而看到的人找不到那些名字是什麼 |
| store 每一層放哪些欄位 | 打開任一支 store 看 | 這一項不必設定 —— 規則只看「有沒有對應的層」,層裡面放什麼不管 |
| 端點字串長什麼樣 | 看 api 檔裡 `fetchApi.get('…')` 的第一段 | 這一項不必設定 —— 端點裡的 `api` 字樣一律不計入函式名 |

對應的設定項都在 `.tools/lint/project-config.mjs`,下面兩節會逐一說明。

**裝好之後一定要跑一次 `npm run lint:css`**(全專案掃描)。
結果最後會列出「哪幾條規則這次沒有作用、因為什麼」——
那一段就是在講上面這些項目有沒有設對。沒有列出任何一項才算裝好。

## 一、需要複製的五個目錄

從已經裝好的專案整個複製過來,不要挑檔案:

| 目錄 | 裡面是什麼 |
| --- | --- |
| `.tools/lint/` | 判斷邏輯。所有規則、規則自己的驗證,以及開發伺服器的外掛都在這裡 |
| `.claude/` | 給 AI 助理讀的規範與 hook(規則說明、寫檔前的檢查),以及規範自己的說明文件(`.claude/docs/` —— 那一層有兩種,見下方) |
| `.githooks/` | commit 前的檢查 |
| `.vscode/` | 沒跑開發伺服器時的存檔守門(見第六節),與建議安裝的擴充套件 |
| `.vite/autoImport/` | 元件與 store 的自動注入設定 —— 有一支 `project.js` 要改成這個專案的值,見第二節 |

**`.tools/` 根層還有兩支要一起帶,但那一層不能整層搬** —— 各專案自己的腳本
(打包、發佈那類)也住在那裡,整層覆蓋會把它們蓋掉。要帶的是這兩支:

| 檔案 | 做什麼 |
| --- | --- |
| `.tools/install-git-hooks.mjs` | 讓 commit 前的檢查生效(`npm run hooks:install` 跑的就是它) |
| `.tools/component-deps.mjs` | 列出複製一支元件時要一起帶走哪幾支檔案(`npm run deps`) |

漏掉的徵狀是「規則訊息叫人跑的指令不存在」——
不會報錯,要真的去跑那一行才會發現。

**開發伺服器的外掛放在 `.tools/lint/` 裡,不要搬到專案的外掛目錄。**
各框架對目錄名有自己的約定 —— 例如 Nuxt 的 `plugins/` 放的是應用程式的
執行期 plugin,把建置外掛放進去會被當成那一種載入。放在規範工具自己的目錄底下
就不會撞到任何框架的約定,而且「規範工具的東西都在這兩個目錄」也比較好交接。

### 這幾支不要複製

上面說「整個複製、不要挑檔案」,但有三種東西是例外 ——
它們長在那幾個目錄裡,內容卻只屬於原本那個專案:

| 不要複製 | 為什麼 |
| --- | --- |
| `.tools/lint/project-config.mjs` | 那份專案的資料夾怎麼擺。第二節會從既有的那一份改值,不是整支覆蓋 |
| `.claude/settings.local.json` | 個人按過的權限記錄 |
| `.claude/__css-self-test__/` | **規則自我驗證的探測檔** —— 見下方 |

**探測檔那一項最容易中招。** 規則的自我驗證(`npm run test:css`)會在
`.claude/` 底下實際建出三十幾支 `probe-*.md` / `.mjs`,跑完自己清掉——
但**在那幾秒之內**它們就跟規範檔案放在同一層。同步的時機剛好落在那個區間,
就會整批被複製走。

那些檔案的內容是「各種違規長什麼樣子」,看起來卻像正常的規範檔案:
複製過去之後,下一個人不知道那是什麼,也不敢刪。

自己寫同步工具的話,把那個目錄名加進排除清單。手動複製的話,
先確認來源沒有在跑測試。

**為什麼不把探測檔改建到別處**:那幾則驗的就是「規範系統這一層的規則有沒有
掃到」——`.md` 的說明文件、skills、rules 都會整批複製到下一個專案,
沒被掃到的話,裡面寫死的專案名稱與某台機器的路徑不會有人發現。
建到掃描範圍以外的話,那幾則永遠不會命中,而畫面上看起來像規則壞了。

### 「不要挑檔案」是字面意思

自己寫同步工具、或用某種只認幾種副檔名的複製方式時,最容易漏掉的是
`.tools/lint/` 底下那份**指紋清單**(`.rules-checksum.json`)——
它是 json,而多數人寫的篩選只列了程式與文件的副檔名。

漏掉它不會報錯,而且徵狀看起來像是別的問題:規則檔明明是剛從來源原封不動
複製過來的,檢查卻說「這支被改過」(規則 `ruleTampered`)。因為比對的對象是
那份落後的舊清單,而它與新規則本來就對不上。

清單與規則是一組的 —— 來源每次改完規則會重新封存,兩邊要一起帶走。

### 這個專案自己的紀錄不放在複製範圍裡

還有多少存量、哪幾支待處理、為什麼某一項先擱著 —— 那些是**這個專案的現況**,
每一個數字與檔名換一個專案就全部對不上。它們放在專案根的 `docs/`,
不在上面那四個目錄裡,所以整套複製時不會跟著走。

這樣分不是為了整齊:那種文件搬過去的後果不是報錯,是**讀的人先花時間去找
那些檔案**,找不到之後才會意識到這一整份不是在講自己的專案。
而且它會一直掛在那裡,既不會有人更新,也不會有人發現它是錯的。

裝好之後跑一次全專案檢查,再在自己的 `docs/` 建一份。

其餘的目錄裡沒有任何專案專屬的內容 —— 專案名稱、目錄位置、色票、alias
都不寫在裡面,所以可以整批搬。自動注入那一套的目錄位置也一樣,
它讀的是同一份設定(`.tools/lint/project-config.mjs`),
只有 `project.js` 那幾個值要照這個專案改。

## 二、告訴工具「這個專案的目錄長什麼樣」

**唯一需要改的設定是 `.tools/lint/project-config.mjs`。**

每個專案的資料夾擺法不一樣 —— 有的頁面放 `src/views`,有的放 `pages`;
有的 store 在 `src/stores`,有的在根目錄。把那幾個位置改成這個專案的實際路徑:

**只改值,不要自己新增、刪掉或改名任何一項。** 項目有哪些由規範工具的來源決定 ——
規則讀什麼,設定檔才有什麼。自己多加的那一項沒有任何規則會讀它,不會報錯,
什麼都不會發生,而下一個人會以為某條規則吃那個值。工具會擋下這種項目
(規則 `configItem`)。需要一個新的設定項時,那代表規則本身要改,
停下來說明是哪一條規則在這個專案判錯了,由開發者決定要不要加進來源。

**第一項要改的是專案名稱。** `PROJECT_NAMES` 換成這個專案的名字 ——
不換的話,「不寫死專案名稱」那條會去抓一個與這個專案無關的字,
而它自己的名稱反而不會被抓。同時這也是工具判斷「誰是來源」的依據:
設定裡的 `SOURCE_PROJECT_NAME` 寫著來源專案的名字,與 `PROJECT_NAMES` 對得上
就是來源(來源可以新增設定項,只會收到提醒);換成新專案的名字之後兩者對不上,
新增設定項就會被擋。全專案檢查的開頭會講出這次算哪一種身分。

### 框架:決定頁面檔名可以怎麼取

```js
export const PROJECT_FRAMEWORK = 'vite'   // 'vite' 或 'nuxt'
```

這一項回答的是**網址從哪裡來**:

| 填 | 路由怎麼來 | 頁面檔名 |
| --- | --- | --- |
| `vite` | 自己寫一張路由表,逐筆寫 `path` | 駝峰(`cardOrderStatus.vue`)—— 檔名只是內部的名字,改它不會動到網址 |
| `nuxt` | 檔案系統路由:檔名就是網址的一段 | 放行連字號(`actual-subscribe.vue`)—— 那是網址分隔字詞的寫法 |

**頁面目錄的資料夾跟著同一套走** —— 那兩個位置放的其實是同一個東西
(一個頁面可以是 `detail.vue`,也可以是 `detail/index.vue`),
分成兩套標準的話,同一個名字寫成資料夾就過、寫成檔案就報。

填 `nuxt` 時,底線與連續大寫仍然擋 —— 底線不是網址分隔字詞的慣例,
而大寫在有的伺服器上不分大小寫,同一個畫面會有兩個網址進得去。
元件兩種都一樣(首字大寫的駝峰):元件是標籤,不是網址。

**該填 `nuxt` 卻填了 `vite` 的後果最重**:那一批頁面會整批被要求改成駝峰,
而照著改就是把網址改掉 —— 既有的連結會失效,搜尋引擎收錄的那一份
會指到不存在的位置。值填錯字(`Nuxt`、`nuxt3`)時,全專案檢查的開頭會講出來。

### 目錄位置

```js
export const VIEWS_DIR = 'src/views'              // 頁面
export const STORE_DIR = 'src/stores'             // 狀態宣告
export const ACTIONS_DIR_NAME = '.composables'    // 行為(放在 store 目錄底下)
export const API_DIR = 'src/scripts/_api'         // api 定義
export const COMPONENTS_DIR = 'src/components'    // 共用元件
export const MODULE_CSS_DIR_NAME = '.css'         // 元件的樣式(放在元件資料夾底下)
export const CSS_MODULES_DIR = 'src/assets/css/_modules'  // 跨模組共用的變數
export const COLOR_CSS_DIR = 'src/assets/css/_common'     // 色票檔放哪
export const COLOR_CSS_PREFIX = 'color'           // 色票檔的檔名前綴
export const SRC_DIR = 'src'                      // 原始碼根目錄
export const SHARED_MODULE_VARIABLES = 'mForm/variables.css'  // 跨模組共用的級距變數檔
```

`COLOR_CSS_PREFIX` 決定「哪些檔案算色票檔」:共用色票是 `<前綴>.css`,
各分組是 `<前綴><分組名>.css`。前綴是 `color` 時就是 `color.css` 與 `colorMember.css`;
專案把共用色票叫 `theme.css` 的話,這裡改成 `theme` 就整套跟著走。

**與專案實際命名對不上時,掃不到任何色票檔** —— 顏色檢查、排序、撞色比對
會全部安靜地不再有結果,而且看起來像是全部通過。

### 色票的命名長什麼樣

**換專案時這幾項一定要打開色票檔對過一遍。** 色票命名的差異是各專案之間最大的一塊,
而設定對不上的後果不是報錯,是整類檢查安靜地失效、或是自動排序把檔案重排成一團。

```js
// 色相從哪裡判斷:'name'(從變數名認)或 'value'(從色值算)
export const COLOR_HUE_SOURCE = 'name'

// 色相清單,這份順序就是色票檔的排列順序
export const COLOR_HUES = ['red', 'orange', /* … */ 'gray', 'black']

export const COLOR_NAME_SEPARATOR = '-'   // 色相與取碼之間放什麼
export const COLOR_RGB_SUFFIX = '-rgb'    // 已廢除的衍生變數後綴,用來認出舊寫法

// 取哪幾碼、帶透明度時 alpha 怎麼接
export const COLOR_SUFFIX_PICK = {
  normal: [1, 3, 5, 6],
  grayscale: [1, 2],
  short: [1, 2, 3],
  alphaSeparator: '',
}
```

**先決定 `COLOR_HUE_SOURCE`,其他幾項跟著它走。** 打開色票檔看變數名:

| 色票長這樣 | 選哪一個 | 為什麼 |
| --- | --- | --- |
| `--red-e01a`、`--gray-9e` | `'name'` | 名字帶色相字樣,分類就寫在名字裡,直接讀出來 |
| `--title-color`、`--btn-hover` | `'value'` | 名字看不出顏色,分類只能從色值算 |

選 `'name'` 的專案要接著確認另外幾項:分隔符是不是 `-`、取碼位置是不是那一套、
透明度那兩碼怎麼接(`--gray-e566` 直接相接就是空字串,`--gray-e5-66` 要填 `-`)。
色相清單也要對過 —— 專案配色有粉、棕、青這類獨立色相時要加進去,
不加的話那些色會全部被判定為「認不出色相前綴」。

選 `'value'` 的專案不必管取碼那幾項:名字本來就不帶色相,取碼檢查會自動跳過,
但彩虹排序與「頁面不得硬寫色碼」照常運作。

設錯了會怎樣:設成 `'name'` 而實際是語意名的話,**每一個變數都會被報「認不出色相前綴」,
而且排序會把整份檔案重排成一大群未知色**(那是自動改檔);設成 `'value'` 而實際帶色相的話,
名字裡人給的語意分類會被色值算出來的結果蓋掉(`#c09648` 專案叫金,色相環算出來是橘)。

不必自己記得檢查 —— 全專案檢查時,工具會比對設定與色票的實際命名,
超過一半對不上就在結果旁邊講出來。但**那是事後提醒,照著上面的表先選對比較省事**。

### 元件的 import 分組

```js
// 共用元件目錄底下的 .vue,import 依這個順序排;都不符合的排在最後(「其他」)
export const IMPORT_ORDER_GROUPS = [
  { label: '樣式', match: '\\.css$' },
  { label: '共用邏輯', match: '\\.composables/' },
  { label: '共用函式', match: '^@js/' },
]
```

`match` 是比對 import 路徑的正規表示式字串。各專案的 alias 與資料夾命名不同,
所以這是設定 —— 寫死在規則裡的話,換一個 alias 命名的專案會把每一支元件都排錯。

**第一組固定是「樣式」那一組**,元件沒有載入這一組的任何一支就會被報違規
(元件的樣式要由元件自己 import,少了那一行,它被放進別的頁面時樣式不會跟著來)。
所以這個陣列的第一項要放樣式,順序不能跟其他組對調。

分組順序本身不報違規,存檔時直接排好。

### 檢查範圍

```js
// 會被檢查的副檔名。少列一種,那種檔案就完全不會被檢查,而且不會有徵兆
export const SCANNABLE_EXTENSIONS = ['vue', 'css', 'js', 'mjs', 'cjs', 'md']

// 規範管得到的目錄 —— 原始碼,加上規範自身所在的地方
const SCOPE_DIRS = [SRC_DIR, '.claude', '.tools', 'plugins', 'docs', '.githooks']
```

**副檔名這一份有三處,改一處就要三處一起改。** 另外兩處沒辦法讀這份設定
(一個是 shell、一個是 json),只能人工對 —— 而且對不上的時候不會報錯,
那一類檔案就是安靜地不再被檢查:

| 位置 | 能不能讀設定 |
| --- | --- |
| `.tools/lint/project-config.mjs` 的 `SCANNABLE_EXTENSIONS` | 唯一來源 |
| `.githooks/pre-commit` 篩 staged 檔案的那一行 | 不能,檔案裡有註解指回來源 |
| `.vscode/settings.json` 的 `match` | 不能,檔案裡有註解指回來源 |

**安裝時一定要打開後面兩處對一遍。** 最常漏的是 `.js` ——
api、store、actions 全是 `.js`,漏掉等於那三區完全沒有守門,
而畫面上不會有任何徵兆。

### 建置設定的檔名

```js
// 由前往後找,用第一個存在的那一支。「離開自己資料夾要用 alias」那條規則要讀它
export const BUILD_CONFIG_FILES = ['vite.config.js', 'vite.config.ts', /* … */]

// alias 路徑裡的變數(例如 `src/${CONFIG.fonts}`)去哪裡取值
export const PROJECT_CONFIG_FILES = ['config.js', 'config.mjs', 'config.ts']
```

一支建置設定都找不到時,`importAlias` 那條會被略過 ——
檢查結果旁邊會列出「這幾條這次沒有作用」,不會安靜地顯示通過。

### 這個專案自己的東西

```js
// 不對應任何頁面資料夾的 store 檔名(跨頁面的基礎建設:彈窗、登入、靜態資料)
export const STANDALONE_STORES = ['common', 'project', 'popup', /* … */]

// 不對應任何頁面資料夾的 api 檔名,以及對不上時一律放的那一支
export const STANDALONE_APIS = ['json', /* … */]
export const SHARED_API_FILE = 'project'

// 端點固定帶的前綴段(版本段、服務名那種),不計入函式名。沒有就留空陣列
export const API_NAMING_IGNORED_SEGMENTS = []

// 被 tailwind 設定「整組覆寫」掉、實際不存在的內建 class
// dead 列的是 tailwind 自己的預設值 —— 與專案無關,多數情況照抄就好
export const TAILWIND_THEME_OVERRIDES = {
  screens: { label: '斷點', dead: ['sm', 'md', /* … */] },
}
```

tailwind 的 theme 寫在 `extend` 底下是「補充」(內建的值都還在),
直接寫在 `theme` 底下是「整組覆寫」(那一類的內建值會全部消失)——
消失之後寫那些 class 不會報錯,但產不出任何 CSS,很難查,所以工具會提醒。

**「這個專案實際可以用哪些值」不必寫在設定裡** —— 工具直接讀
`tailwind.config.js`(值拆到另一支檔案再 import 的話會追過去)。
在這裡抄一份的話就要人工同步,而忘了同步不會報錯,
只會讓提示訊息開始指著一個已經改掉的名字叫人去用。

`dead` 只有升級 tailwind 大版本、預設值有增減時才要調。
專案沒有整組覆寫的類別,工具讀得到,不必在這裡宣告。

規則檔案本身不需要改任何一行 —— 它們都是讀這份設定。

### 自動注入的 marker 對照表

`.vite/autoImport/project.js` 是那一套唯一要改的一支:

```js
// 頁面目錄底下的資料夾名 → 注入名稱裡要換成什麼
export const markers = { _components: '', _pages: 'Page' }
```

**只有落在這幾個資料夾裡的 .vue 會被自動注入**,一般的路由頁不納入。
值是空字串代表移除那一層(`Member/_components/Foo` 注入成 `MemberFoo`),
其餘字串則是替換(`_pages` 換成 `Page`,注入成 `MemberPageFoo`)。

**沒有那種資料夾的專案留一組空的 `{}`**,不要保留別人的值 ——
對照表裡有專案實際沒有的資料夾名時不會報錯,那一項只是永遠用不到,
而下一個人會以為這個專案有那一層。

目錄位置那幾個值不必在這裡改,那一套讀的是 `project-config.mjs` 的同一份。

**這份對照表與設定裡的 `COMPONENT_FOLDERS` 不是同一件事**,兩者都在講
「頁面目錄底下的資料夾」,但問的問題不同:

| 設定 | 問的是 | 影響 |
| --- | --- | --- |
| `COMPONENT_FOLDERS`(`project-config.mjs`) | 那一層裡的 .vue 該用元件的規範還是頁面的規範 | 規範檢查怎麼判 |
| `markers`(`project.js`) | 那一層在自動注入的名稱裡要換成什麼字 | 元件用不用得到,以及叫什麼名字 |

所以同一個資料夾名可能只出現在其中一邊。放頁面的那一層
(例如一個叫 `_pages` 的資料夾)要有 marker 才注入得到,
但它裝的是頁面,不該列進 `COMPONENT_FOLDERS` ——
列進去的話,那些頁面會開始被元件的規範檢查,而那些規則對頁面是錯的。

## 三、要裝的套件

這幾個每個專案都要有 —— 少了哪一個,對應的那件事就沒有人做,
而且多半不會報錯,只是結果悄悄地不一樣。

| 套件 | 做什麼 | 少了會怎樣 |
| --- | --- | --- |
| `prettier` | 排版 | 每個人的編輯器排出不同的格式,diff 裡混著大量與改動無關的行 |
| `eslint` + `eslint-plugin-vue` + `eslint-config-prettier` | **只負責把空元素收合成自閉合**(見第六節)。規範判斷不歸它管,那是 `.tools/lint` 的事 | `<div></div>` 與 `<div />` 兩種寫法並存,搜尋、比對、複製的時候同一種東西長得不一樣 |
| `svgo` | 壓縮 SVG | 設計匯出的 SVG 帶著編輯器的中繼資料,一支肥好幾倍 |
| `sharp` + `image-minimizer-webpack-plugin` | 壓縮點陣圖 | 圖片原檔直接進產物,首屏要等的東西大好幾倍 |
| `tailwindcss` | utility class 與 theme | 樣式規範那幾條(`tailwind`、`theme`、`themeNaming`)整組失去對象 |

**`tailwindcss` 用 3.x,不要升上去。** 4.x 改掉了設定檔的形狀
(theme 從 JS 設定改成 CSS 指示詞),而規則是讀那份 JS 設定算出
「哪幾類被整組覆寫、各類還剩哪些值」的 —— 升上去之後那幾條會讀不到東西,
結果是安靜地全部通過。

**`prettier` 的 `htmlWhitespaceSensitivity` 留預設值(`css`),不要改成 `ignore`。**
預設值會保護接連排在一行的元素之間那個有意義的空白;改成 `ignore` 之後
排版工具會自由折行,而 Vue 編譯時把含換行的空白整個移除 ——
畫面上是兩段文字黏在一起,原始碼看起來完全正常。
(間隔本來就該用 css 做,那樣怎麼折行都不會壞。)

圖片壓縮固定用 `sharp` 搭 `image-minimizer-webpack-plugin`:
其他壓縮器要嘛依賴系統裝的二進位檔(換一台機器就壞),
要嘛在 CI 上裝不起來 —— 而那是最需要它的地方。

### 自動注入那一套要的兩個套件

第一節要整套複製過去的 `.vite/autoImport/`,兩支檔案各自依賴一個套件:

| 套件 | 誰在用 | 做什麼 |
| --- | --- | --- |
| `unplugin-vue-components` | `.vite/autoImport/components.js` | 元件不必 import 就能當標籤用,並產生型別宣告 |
| `unplugin-auto-import` | `.vite/autoImport/index.js` | 常用的 api(`ref`、`computed` 那些)不必逐支 import |

**沒裝的話不是安靜地失效,是建置工具載入設定時就找不到模組**,
dev server 起不來 —— 所以這一項不會拖到後面才發現。

框架本身就做了自動注入的專案不複製那個目錄,這兩個套件也就不用裝。

### 有表單驗證的專案要裝的兩個套件

畫面上有要填的欄位(登入、註冊、資料修改、問卷)就會用到:

| 套件 | 做什麼 |
| --- | --- |
| `vee-validate` | 驗證的框架 —— 欄位元件、錯誤訊息元件,以及註冊規則的 `defineRule` |
| `@vee-validate/rules` | 現成的規則(必填、email、長度、數字範圍那些) |

**兩支要一起裝。** 只裝框架的話,每一條規則都要自己寫一遍 ——
「必填」「email 格式」這種每個專案都一樣的判斷,各專案各寫一份,
錯就錯在細節上(空白字元算不算填了、email 的容錯到哪裡),而且不會有人發現。

**規則在一支檔案裡集中註冊**,不要各表單各自 `defineRule`:
同一條規則被註冊兩次時,後註冊的那一份會蓋掉前面的,
而兩邊的訊息或判斷只要有一點不同,同一個欄位在兩頁就會有兩種行為。

共用的表單元件直接用這一套的欄位與錯誤訊息元件,
所以**複製那些元件過去的專案一定要裝**,否則元件載入時就找不到模組。

沒有任何要填的欄位的專案(純展示、純列表)不必裝。

## 四、加上指令

在 `package.json` 的 `scripts` 補這幾行:

```json
{
  "scripts": {
    "lint:css": "node .tools/lint/lint.mjs",
    "test:css": "node .tools/lint/self-test.mjs",
    "test:shapes": "node .tools/lint/test-shapes.mjs",
    "sort:color": "node .tools/lint/guard-file.mjs --write",
    "deps": "node .tools/component-deps.mjs",
    "rules:seal": "node .tools/lint/checksum.mjs --write",
    "rules:verify": "node .tools/lint/checksum.mjs",
    "hooks:install": "node .tools/install-git-hooks.mjs",
    "postinstall": "npm run hooks:install --silent"
  }
}
```

各自做什麼:

| 指令 | 做什麼 |
| --- | --- |
| `npm run lint:css` | 掃描全專案。後面可以接檔案或目錄,只檢查那些 |
| `npm run test:css` | 驗證規則本身還有效(改過規則之後要跑) |
| `npm run test:shapes` | 驗證同一份案例在幾種專案擺法下結果相同(**改過驗證案例之後要跑**) |
| `npm run sort:color` | 把色票檔重新排序(只動順序,不動色值) |
| `npm run deps <元件>` | 列出「複製這支元件時,要一起帶走哪幾支檔案」 |
| `npm run rules:seal` | 重新封存共用規則的指紋(**只有來源專案要做**) |
| `npm run rules:verify` | 比對共用規則與指紋清單,列出對不上的那幾支 |
| `npm run hooks:install` | 讓 commit 前的檢查生效 |
| `postinstall` | 別人 clone 下來裝套件時,自動把上面那件事做好 |

### 三個環境的指令也要在

上面那幾個是規範工具自己要的。除此之外,**每個專案都要有這三個指令**,
名字固定,規則 `buildCommands` 會檢查:

| 指令 | 送去哪裡 | 讀哪一份設定 |
| --- | --- | --- |
| `dev` | 開發(本機起 dev server) | `.env.dev` |
| `deploy` | 測試機 | `.env.deploy` |
| `build` | 正式機 | `.env.build` |

**新專案一開始一個都沒有,所以這條會直接報三筆** —— 那不是誤報,
是這份安裝清單的其中一項。補上就過了。

名字不可以換成 `publish`、`release`、`prod` 那類:打 `npm run build` 的時候
要能當場確定那是正式機,而不是先打開 `package.json` 讀一遍 ——
漏讀一次的代價是送錯環境,那件事不會報錯,指令跑完一樣顯示成功。

指令**內容**由專案自己決定(用哪個建置工具、部署那一步做什麼),規則不碰。
只有兩件事會被檢查,而且都只在專案已經在用那套慣例時才檢查:
指令裡有 `--mode` 的話那個值要與指令名相同;有 `.env.<環境>` 檔的話三份要成套。
完整說明在寫法規範的 build-commands。

### 指紋:共用規則只有來源能改

`.tools/lint/` 底下的規則是每個專案拿到的同一套。在某個專案改了它,
那個專案的檢查結果就與別人不同,而且改動會在下一次整套更新時被蓋掉 ——
蓋掉的當下沒有人會發現,只知道「本來不報的東西怎麼又開始報了」。

來源專案用 `npm run rules:seal` 把每一支共用規則的指紋寫進
`.tools/lint/.rules-checksum.json`,那份清單跟著規則一起複製出去。
非來源專案的檔案與清單對不上時,規則 `ruleTampered` 會報出來
(掛在 `project-config.mjs` 這一支上報,訊息裡列出是哪幾支對不上)。

不列入指紋的是專案自己的那幾支,也就是每個專案可以動的東西:
設定檔 `project-config.mjs`,以及**檔名以 `-project.mjs` 結尾的**——
專案自己的規則 `rules-project.mjs`、專案自己的小工具都是這個形狀。
自己多一支工具時照這個命名,才不會被報成「多出來的」。

**來源那邊不比對**,規則本來就在那裡長,每改一行都報一次等於不能工作。

沒有指紋清單時不比對,那是還沒封存過的狀態。這件事會講出來 ——
全專案檢查的前提清單會寫「`ruleTampered` 這次沒有作用」,
`npm run rules:verify` 也會說「還沒有指紋清單,這次沒有比對任何一支」,
不會顯示成「一致」。

來源改完共用規則之後要記得重新封存 —— 忘了的話,那份清單一到別的專案
就會全部對不上,而那邊其實一個字都沒動。

`.tools/install-git-hooks.mjs` 這支要一起複製過去(它在 `.tools/` 底下,
第一步整個目錄複製時就有了)。

## 五、掛上開發伺服器的外掛

這一步讓「存檔當下就看到提醒」生效。在建置設定(Vite 專案是 `vite.config.js`)
加兩行:

```js
import { cssGuard } from './.tools/lint/dev-server-plugin.mjs'

export default {
  plugins: [
    // …原本的其他外掛
    cssGuard(),
  ],
}
```

外掛只在開發模式生效,不影響正式建置,也不會擋掉任何東西。

### 這一層不只是提醒,它會改寫檔案

**存檔的當下,有六件事是直接改好的,不是報給你自己改:**

| 自動修正 | 改什麼 |
| --- | --- |
| 色票排序 | 色票檔依規則重排(只動順序,不動色值) |
| 已廢除的 rgba 寫法 | 轉成 8 碼色票變數 |
| 空的規則區塊 | 從 `.vue` / `.css` 移除 |
| 宣告順序、import 分組 | 重新排好 |
| `onMounted` 裡的請求 | 用並行載入的包裝函式包起來 |
| 從 `apiDefault` 還原 | 補上深拷貝 |

**rgba 那一項會動到別的檔案** —— 色票裡還沒有那個顏色時一併補進去,
色值變了連帶要改名的,全站使用端一起換。只改使用端而不補變數的話,
那一行會指向一個沒有定義的變數:畫面上不會報錯,顏色就是不見了。

知道這件事很重要,有兩個理由:

- **存檔之後檔案內容與你剛才打的不一樣是正常的**,不是編輯器或別的工具在搗亂
- **有幾條規則的訊息寫著「存檔時會自動包好」「存檔時自動排序」** ——
  那幾句話的前提就是這一層有接上。沒接上的話訊息照樣那樣寫,
  而使用者等著它自動發生,永遠等不到

---

## 六、沒跑開發伺服器時也要接上(選配)

上一步讓「開發伺服器執行中」的存檔會被檢查、也會自動修正。
沒有跑開發伺服器的時候那一層不在,所以存檔什麼都不會發生 ——
要補上的話,在編輯器設定加一段。

**兩層走的是同一支程式**(`guard-file.mjs`),所以自動修正的那六件事
在兩層是一樣的:色票排序、rgba 轉成 8 碼、空區塊移除、宣告與 import 排序、
`onMounted` 的請求包起來、`apiDefault` 補深拷貝。
兩層都沒接上時,那幾條規則的訊息仍然寫著「存檔時會自動包好」,
而實際上不會有任何事發生。

以 VSCode 搭配 Run On Save 擴充為例,`.vscode/settings.json`:

```json
{
  "emeraldwalk.runonsave": {
    "autoClearConsole": true,
    "commands": [
      {
        "match": "\\.(vue|css|m?js|cjs|md)$",
        "cmd": "node \"${workspaceFolder}/.tools/lint/guard-file.mjs\" \"${file}\""
      }
    ]
  }
}
```

`match` 的副檔名要與 `.tools/lint/project-config.mjs` 的 `SCANNABLE_EXTENSIONS` 一致 ——
這個設定檔沒辦法讀那份設定,只能人工對。少列一種,那種檔案存檔時就完全不會被檢查,
而且不會有任何徵兆。

`.githooks/pre-commit` 裡篩選檔案的那一行也是同樣情況,一起對。

### 空元素要收合成自閉合 —— 這一項一定要自己設

**`<div></div>` 一律收成 `<div />`。** 不設的話,同一個專案裡兩種寫法並存:
有人手寫成對標籤、有人寫自閉合,而排版工具兩種都不動 ——
之後搜尋、比對、複製一段過來的時候,同一種東西長得不一樣。

**從 0 開始的專案不會自動有這個行為。** eslint 的 vue 外掛本來有這條
(`vue/html-self-closing`),但**接上 prettier 的設定之後它會被關掉** ——
那份設定把所有「排版類」的規則一律關閉,這條也在裡面。
所以要自己寫回去,而且**位置一定要在 prettier 那一段之後**。

要裝的套件:`eslint`、`eslint-plugin-vue`、`eslint-config-prettier`。
設定檔命名為 `eslint.config.mjs`(不是 `.js`)—— 專案的 `package.json`
有沒有 `"type": "module"` 會決定 `.js` 被當成哪一種模組,
`.mjs` 在兩種底下都是 ESM,所以同一份設定檔可以直接複製到別的專案。

```js
import pluginVue from 'eslint-plugin-vue'
import plugPrettier from 'eslint-config-prettier'

export default [
  // 建置產物不是原始碼。不排除會拖慢掃描,還會報一批「規則不存在」
  { ignores: ['.output/**', '.nuxt/**', 'dist/**'] },

  ...pluginVue.configs['flat/base'],
  plugPrettier,          // ← 這一段會把 vue/html-self-closing 關掉
  {
    files: ['**/*.vue'],
    rules: {
      'vue/html-self-closing': [
        'error',
        {
          html: { void: 'always', normal: 'always', component: 'always' },
          svg: 'always',
          math: 'always',
        },
      ],
    },
  },
]
```

**規範檢查不要開在這裡。** 上面只取 `flat/base`(解析 `.vue` 所需),
刻意不帶 `pluginJs.configs.recommended` 與 `flat/essential` ——
規則的唯一判準是 `.tools/lint`,在 eslint 再開一套等於同一件事有兩份判準,
而兩份遲早會各自演化。自閉合歸 eslint 是因為它是**排版**,不是規範判斷。

用自動注入的專案更要注意:`ref` / `computed` / `useXxx` 都沒有顯式 import,
`no-undef` 會把每一個都報成未定義,那全是誤報。

**設定檔的檔頭註解不要用 `eslint` 當開頭。** 以那個字開頭的區塊註解會被當成
inline 設定註解去解析,整支設定檔報 `Failed to parse JSON` ——
訊息指的是設定檔第 1 行,看起來像 JSON 壞了,實際上是註解的第一個字。

加一個指令,讓不開編輯器的時候也能整包修:

```json
"lint:vue": "eslint . --fix"
```

**放在 `plugPrettier` 前面的話,它會被後面那一段關掉** ——
設定看起來寫了,實際上沒有任何作用,而且不會有任何訊息。
改完之後隨便找一支元件寫一個 `<div></div>` 存檔,有收合就是接上了。

存檔時要真的套用,編輯器那側還要開自動修正:

```json
{
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```

**這個收合在 `.vue` 裡是安全的**:`<div></div>` 與 `<div />` 編譯出來的
程式碼相同。原生的 `.html` 檔(沒有經過 Vue 編譯的那種,例如專案根的進入頁)
則相反 —— 那一層不要寫自閉合,瀏覽器會把後面的兄弟節點看成它的子節點。
上面的設定只作用在 `.vue`,不會動到 `.html`。

## 六之二、一個 repo 裝了不只一個專案時

前面幾節都假設「一個 repo 一個專案」—— repo 根就是專案根,`.tools/lint/` 就在根層。
**一個 repo 裝了兩個以上的專案時(例如 `Project/Nuxt/` 與 `Project/Vite/`),
五層守門裡有三層會靜靜失效。**

規範工具是**每個專案各裝一套**的:目錄擺法、框架、色票位置都寫在各自的
`project-config.mjs` 裡。所以同一種寫法在一邊違規、在另一邊合規是正常的。
但下面這三層是從 **repo 根**執行的,它們拿到一個檔案路徑之後,
必須自己判斷「這支檔案屬於哪一個專案」:

| 層 | 從哪裡執行 | 不處理的話 |
| --- | --- | --- |
| 編輯器存檔 | 編輯器的工作區根 | `node .tools/lint/guard-file.mjs` 找不到檔案 |
| AI 寫檔前 | Claude Code 的啟動目錄 | hook 把 repo 根當專案根,找不到引擎就**安靜放行** |
| 送出對話訊息 | Claude Code 的啟動目錄 | hook 把 repo 根當專案根,找不到引擎就**安靜放行** |

**失效的樣子是「檢查都通過了」,不是報錯。** AI 可以連續改上百支檔案而一次都沒被擋下,
看起來像是寫得很乾淨。

開發伺服器外掛與 commit 前那兩層不受影響:前者跑在各專案自己的建置設定裡;
後者(`.githooks/pre-commit`)已經內建了往上找專案根的處理。

### 判準只有一條,放在一個地方

往上找,**第一個有 `.tools/lint/lint.mjs` 的目錄就是那支檔案的專案根**。
這條判準寫在 repo 根的 `.tools/project-roots.mjs`,三層都讀它。

`.githooks/pre-commit` 裡另有一份(shell 寫的,沒辦法 import 那支)——
那邊改了這裡要跟著改,反之亦然。

### 要在 repo 根補的三支

| 檔案 | 做什麼 |
| --- | --- |
| `.tools/project-roots.mjs` | 「專案根在哪」的唯一判準 |
| `.tools/lint-dispatch.mjs` | 編輯器存檔的派工 —— 找出專案、進到那裡、把參數轉交給該專案的 `guard-file.mjs` |
| `.claude/hooks/enforce-conventions.cjs`<br>`.claude/hooks/css-guard-prompt.cjs` | 兩支 hook 的派工 —— 把 stdin 原樣轉交給該專案的同名 hook |

然後 repo 根的 `.vscode/settings.json` 把 `cmd` 改成 `node .tools/lint-dispatch.mjs "${file}"`,
`.claude/settings.json` 掛上那兩支 hook。

**派工層一律不做規則判斷。** 判斷有第二份實作的話,改了一邊就開始漂移,
而漂移的那段時間沒有人會發現 —— AI 寫檔被擋、但人自己存檔通過,或反過來。

**也不要把子專案那兩支 hook 複製到 repo 根。** 它們用 `__dirname` 往上兩層當專案根,
複製過去之後會把 repo 根當專案根,找不到 `.tools/lint/` —— 然後安靜放行。

### 各專案自己那一份要留著

`Project/Nuxt/.vscode/`、`Project/Nuxt/.claude/settings.json` 這些**單專案版要保留**,
它們才是「複製到新專案就能用」的那一份。派工層是這個 repo 多出來的一層,
複製到單專案的 repo 時不要帶過去。

### `git status` 的路徑基準

送出訊息那一層掃的是 `git status --porcelain`,而 **git 回的路徑一律相對 repo 根**,
不是相對專案根。直接拿去接專案根會組出 `Project/Vite/Project/Vite/…` 這種不存在的路徑,
整批被過濾掉 —— 一樣是什麼都掃不到、而且沒有徵兆。

`css-guard-prompt.cjs` 用 `git rev-parse --show-prefix` 把前綴剝掉。
一個 repo 一個專案時那個前綴是空字串,行為完全一樣,所以這段不必分兩種寫法。

## 七、確認裝好了

依序跑這兩個指令:

```
npm run test:css     # 規則自己的驗證,要全部通過
npm run lint:css     # 掃全專案,列出目前的違規
```

**`npm run test:css` 全部通過才算裝好。**
它會餵違規的寫法進去確認抓得到、餵正確的寫法進去確認不誤報 ——
通過代表每一條規則都還在正常運作。

跑的時候會在專案裡暫時建立一些名字帶 `self-test` 的檔案與資料夾,
結束時自動刪掉。中途中斷的話,下次執行會先清乾淨再跑。

`npm run lint:css` 列出來的違規是**現況**,不是安裝失敗。新專案應該是 0;
既有專案接進來時會有一批存量,那是正常的,可以逐步處理。

### 存檔守門要實際存一次檔才知道接上了沒

**上面那兩個指令跑的是規則引擎本身,不經過存檔那一層。**
開發伺服器的外掛與編輯器的設定都沒接上時,兩個指令照樣全部通過 ——
看起來與裝好了完全一樣,而實際上存檔時不會有任何事發生:
不會提醒,也不會自動修正。

所以要自己存一次檔試:

1. 隨便找一支 `.css`,加一個空的規則區塊(`.probe {}`),存檔
2. **那一段應該當場消失**,而且終端機(開發伺服器那層)或編輯器的輸出面板
   (編輯器那層)會印出這支檔案的檢查結果
3. 兩件事都沒發生的話,回上面兩節看哪一層沒接上;
   只有其中一層有反應是正常的 —— 那取決於當下有沒有在跑開發伺服器

測完把那個空區塊刪掉(如果它沒有被自動移除的話)。

## 七之二、之後要新增一份規則或一類寫法規範時

兩份清單(有哪些共同前提、有哪些寫法規範)都是**從目錄長出來的**,
所以新增一份之後不必再去別處補一行 —— 放進去就會自動出現在提醒裡。

**動手之前,先判斷這條屬於哪一類**(樣式、元件、頁面、狀態、api、
不分檔案類別的程式寫法、或是不限某一類檔案的工作方式),再去那一類既有的那一份
確認沒有人在講同一件事;找到相近的就擴充那一份,不要另開新的。
分類決定了要去哪裡找,沒先分類就搜尋等於用幾個關鍵字碰運氣,
碰不到就以為沒有,於是同一件事變成兩份。
分類的完整清單與判斷方式寫在 `.claude/rules/no-duplicate-rules.md`。

**新增一份共同前提**:在 `.claude/rules/` 放一支 `.md`,檔頭寫這幾個欄位。

```markdown
---
name: 檔名不含副檔名
scope: project
priority: 5
summary: 一句話說明這條在管什麼
---

# 這條規則的標題
```

`priority` 是與其他規則衝突時的順位,數字小的優先;`summary` 是提醒裡會印出來的那一句。
兩個欄位都要寫 —— `priority` 缺了會排到最後,`summary` 缺了會退回用標題,
那句話通常太短,看的人不知道這條在要求什麼。

**新增一類寫法規範**:在 `.claude/skills/` 開一個資料夾,裡面放 `SKILL.md`,
檔頭的 `summary` 寫一個極短的分類(像是「api」「頁面」「css 顏色」),
提醒裡會印成 `資料夾名(summary)`。

改完跑一次 `npm run test:css` —— 裡面有一則專門確認這兩份清單讀得到、
欄位齊全、而且依順位排好。清單壞掉時提醒會變成空的,那一則就是用來擋這件事的。

### skill 寫「檢查:規則 X」的話,那條規則要同一批寫入

skill 的檔頭常寫著「檢查:規則 `formGroupValidate`(擋)」。
**那條規則、它的自我驗證案例、以及這份 skill,三者要在同一次改動裡完成。**

先放 skill、規則晚幾分鐘再補的話,中間那段時間工具裡是一份
「說有檢查、實際上沒有」的規範 —— 而那正是規範系統最該避免的狀態。
同步的人剛好在那個區間抓走,拿到的就是那一份。

**不會有任何徵兆**:`lint` 照樣通過(沒有那條規則可跑),
`test:css` 也照樣通過(沒有對應的案例),skill 讀起來一切正常。

反過來也一樣 —— 規則先進去、skill 還沒寫,那條規則會擋下寫入,
而訊息叫人去看的那份 skill 不存在。

### 只有這個專案需要的規範

新規範分兩種,放的位置不同:

| 這條規範 | 放哪裡 |
| --- | --- |
| 每個專案都適用 | 加進對應的規則檔(`rules-global` / `rules-api` / `rules-store` / `rules-code` / `rules-page`),並在來源那邊改 |
| **只有這個專案需要** | `.tools/lint/rules-project.mjs`,有就讀、沒有就跳過 |

分辨方式:**別的專案會不會也想要這一條?** 不會就放專案自己那支 ——
硬加進共用的那一套,不需要的專案會被迫每次標例外。

那支檔案匯出四樣東西:

```js
export const PROJECT_CHECKS = [checkXxx]              // 檢查函式
export const PROJECT_RULE_TITLE = { 'project:xxx': '標題' }
export const PROJECT_RULE_HINT = { 'project:xxx': '怎麼修' }
export const PROJECT_CASES = [{ rule: 'project:xxx', … }]  // 驗證案例
```

兩個硬性要求,自我驗證會擋:

- **代號以 `project:` 開頭** —— 不加的話,有一天會與來源的規則撞名,
  而那時同一個代號底下有兩種判準,看訊息的人分不出是哪一種
- **每一條都要有案例** —— 規則與案例放在同一支檔案,改了規則忘了改案例才不會沒有人發現

來源整套覆蓋時不會動到這支檔案(它不在來源裡);反過來,這支檔案裡的東西
也不要複製回來源,那是這個專案的需求。

### 案例的結果不可以隨專案擺法而不同

驗證案例會寫出探測檔,而探測檔的位置是用設定組出來的。設定在每個專案
長得不一樣,有兩種差異會讓案例失準:

| 差異 | 會發生什麼 |
| --- | --- |
| 原始碼放在哪 | 有原始碼那一層的專案,專案根不是原始碼,探測檔不會被原始碼那幾條規則掃到;原始碼直接放專案根的則會被一起掃,案例多報幾筆 |
| 目錄值幾段 | 案例挑了某一個設定項來造內容時,那一項在另一種專案可能短到規則刻意不抓,於是永遠驗不到東西 |

兩種都是「看到的人以為規則壞了,實際上是案例綁死了某一種擺法」。

`npm run test:shapes` 把幾種擺法各跑一次,比對結果是不是一樣 ——
這個專案自己的擺法,加上兩種假想的(原始碼自成一層、原始碼放專案根且
目錄值只有一段)。**來源專案只有一種擺法,自己跑 `test:css` 永遠不會
遇到這種落差**,要到另一個專案複製過去才會發現。改過驗證案例之後跑一次,
把問題留在來源這邊解決。

每一種擺法都跑在**複製出來的一份空骨架**上,不碰這個專案:設定檔完全不動
(中途失敗也不會留下被改過的設定),探測檔也不會寫進專案的目錄。
骨架裡沒有這個專案的頁面與色票,所以有幾則可能在**每一種**擺法都不會過 ——
那不是這支要找的東西,它找的是「只在某幾種擺法沒過」的那幾則。

不一樣的那幾則,兩種常見的成因:案例沒有指定 `rule`(只計自己那一條),
或是案例內容挑了某一個設定項來造。

**加了自己的規則不會讓既有的案例失敗。** 來源那一批案例的探針
(一段刻意寫壞的程式碼)常常同時命中好幾條規則,而那些案例寫的時候
不可能預期到這個專案之後會加什麼。所以沒有指定 `rule` 的案例
一律不計 `project:` 開頭的規則 —— 不這樣做的話,自己加兩條規則就會有
一批既有案例開始失敗,而訊息看起來像是那幾條規則壞了。

專案自己的規則由 `PROJECT_CASES` 驗,那裡每一則都用 `rule` 指定是哪一條,
所以不受這個排除影響 —— 該報的照樣驗得到。

### 專案自己的工具:檔名以 `-project.mjs` 結尾

除了規則之外,專案常常還會有只有它要的小工具 —— 自己的比對腳本、自己的報表。
那些一樣放在 `.tools/lint/`,但**檔名要以 `-project.mjs` 結尾**
(例如 `diff-output-project.mjs`)。

兩個作用:看檔名就分得出哪幾支是這個專案的、哪幾支是每個專案都有的;
而且這個結尾是指紋保護認得的形狀 —— 共用規則受指紋保護,
`-project.mjs` 結尾的與設定檔不列入,不會被報成「多出來的」。

沒照這個命名的話,那支工具每一次檢查都會被 `ruleTampered` 報一次,
而那個專案其實一點問題也沒有。

### 新增規則的驗證案例時:期待值一律從設定算

案例裡的**探針內容與期待的字串,只要那個字來自設定就一定要取設定值**,
不能照著這個專案的樣子寫死。

寫死不會在來源這邊出事 —— 這裡的設定剛好就是那個值,案例照樣通過。
出事的是別的專案:它的設定不一樣,於是案例去比對一個它沒有的字,
看起來像規則壞了,實際上規則是對的,錯的是案例。
那種失敗每一次都要人去追,而追到最後發現「規則沒問題」。

| 不要 | 改成 |
| --- | --- |
| `keyword: '搬進 project.js'` | `keyword: \`搬進 ${SHARED_API_FILE}.js\`` |
| `keyword: 'stores/'` | `keyword: \`${STORE_DIR.split('/').pop()}/\`` |
| `keyword: 'awaitAllPromise'` | `keyword: PARALLEL_AWAIT_HELPER.name` |
| `keyword: 'red'`(色相清單裡的某一色) | `keyword: HUE_LIST_TEXT`(比對整份清單) |
| 探針寫 `--probe-pc-px`(斷點名) | 從 `BREAKPOINTS` 組出來 |
| 探針建在 `${VIEWS_DIR}/資源`(資源層數) | 依 `VIEW_RESOURCE_DEPTH` 決定放第幾層 |

判斷方式:**這個字換一個專案會不會變?** 會變就從設定取。

檢查自己有沒有漏:把設定裡的某一項暫時改成別的值,跑一次 `npm run test:css`,
再改回來。跟著設定走的案例照樣通過,寫死的那幾則會當場失敗。

## 八、裝好之後,什麼時候會看到提醒

同一份判斷邏輯,五個時機各自觸發:

| 時機 | 對誰生效 | 行為 |
| --- | --- | --- |
| 編輯器存檔 | 所有人 | 違規逐筆印在輸出面板。**只提醒,不影響存檔** |
| 開發伺服器執行中存檔 | 所有人 | 違規印在終端機。同樣只提醒 |
| AI 助理寫檔前 | **只有 AI 助理** | 比對寫入前後,**只擋這次新增的違規**;既有存量不影響 |
| 每次對話開始 | 只有 AI 助理 | 把還沒處理的違規列給它看 |
| commit 前 | 所有人 | 檢查這次提交的檔案。規範違規**只提醒**;規則自己壞掉**會擋** |

### 現在只有一層會擋,那是刻意的

**唯一會擋下違規的是「AI 助理寫檔」那一層,而它只對 AI 生效。**
用助理的人寫錯會被擋下來,手動改的人只看到提醒 ——
同一份規範,兩種人的強制力不一樣。

這不是漏掉,是「擋下來之後做得到嗎」的取捨:一個專案接手時
往往已經有幾百筆既有違規,那時 commit 一律擋的話,任何人碰到那些檔案
都動不了,結果一定是有人去繞過整個 hook —— 那時連真正嚴重的問題也不會被擋。

**commit 前唯一會擋的是「規則自己的驗證沒過」**:規則改壞了不會報錯,
只是安靜地不再檢查任何東西,而畫面上顯示通過。那種問題要幾個月後
才有人發現,而修它通常是一兩行的事,當場做得完 —— 擋得住、也擋得有意義。

### 存量清完之後要把它改成擋

**這是每個專案的目標,不是可選項。** 存量歸零之後,
把 `.githooks/pre-commit` 最後的 `exit 0` 改成累計失敗再離開,
那時它擋不到任何人,卻讓「新寫的程式碼一律合規」變成事實。

**改的時候不要留跳過的旗標。** 一個「緊急時可以跳過」的開關,
會在幾週內變成「每次都加」,那時規範等於不存在,而大家還以為有守門。

## 九、可能會遇到的狀況

**`npm run test:css` 有案例失敗**

先看失敗訊息裡的規則代號。如果是剛改過的規則,那是規則被改壞了。
如果沒改過任何規則卻失敗,多半是 `project-config.mjs` 的目錄位置與專案實際不符 ——
規則找不到要比對的目標。

**commit 時沒有看到任何提醒**

`npm run hooks:install` 沒跑到,或是這個資料夾不是 git repo。
重跑一次那個指令,它會告訴你結果。

**存檔時沒有反應**

沒跑開發伺服器、也沒裝編輯器擴充的話,存檔本來就不會觸發。
可以先用 `npm run lint:css <檔案>` 手動確認規則是通的。

**一個 git repo 底下放了多個專案**

commit 前的檢查是 repo 層級的設定,只能指向一個目錄。
那種情況下,各專案的 `.githooks/pre-commit` 內容要保持一致。
